## 1. 出発点：再現だけでは足りない、が「飾り」を足すのも違う

独自機能として「LED を光らせる」「音を鳴らす」「キャラクター性を持たせる」といった演出は
いつでも足せるが、**プロジェクトの難所（§NFR-1 の時間予算）を1ミリも助けない。**

一方で、既存ドキュメントを読み返すと、**「測る」と書いてあるのに「どう測るか」が
どこにも書かれていない**箇所が大量にある。

| 出典 | 要求されている測定 | 収集手段 |
|---|---|---|
| [development-environment.md §13.1](./development-environment.md#131-実測する項目) | FPS・CPU・レイテンシを**段階別に**分解して計測 | **未定義** |
| [requirements.md M1](./requirements.md#8-段階的開発マイルストーン) | 飛行時間・検出遅れ・予測誤差など 7 項目 | **未定義** |
| [requirements.md M2](./requirements.md#8-段階的開発マイルストーン) | 移動距離・電圧降下・スリップなど 14 項目 | **未定義** |
| [requirements.md NFR-7](./requirements.md#nfr-7-キャッチ成功率-最終的な合否条件) | N 回投擲の成功率 | **未定義** |
| [development-environment.md §6](./development-environment.md#6-record--replay-を将来設計に含める) | Record / Replay（「重要な開発方針」と明記） | **フォーマット未定** |

つまりこのプロジェクトには、**本体とは別に「観測・再現・評価のための基盤」が丸ごと必要**であり、
そこがまだ空白になっている。ここを独自機能の中心に据える。

> **方針**: 独自機能は**演出ではなく道具**とする。
> 「M1〜M4 を実行するために必要だが、元動画には存在しないもの」を作る。
> 結果として、それがそのままデモとしても成立する。

## 2. 全体像：Throw Record を中心に置く

3つの柱をバラバラに作らず、**「1回の投擲＝1つの記録（Throw Record）」という単一スキーマ**で束ねる。

```
   [シミュレータ]      [実機ライブ]        [記録の再生]
        |                   |                   |
        +---------+---------+---------+---------+
                            |
                     Throw Record
              （1投擲の全経過を表す共通スキーマ）
                            |
        +---------+---------+---------+---------+
        |                   |                   |
   ダッシュボード       リプレイ表示        ベンチマーク
```

これは [development-environment.md §7](./development-environment.md#7-realsense-依存部分を将来的に分離する) の
「RealSense 依存部と処理部を疎結合にする」という方針を**一段上のレイヤへ拡張**したものである。
入力元が live / recorded / simulated のどれであっても、下流の表示・評価は同じコードで動く。

**副次的な効果**: [development-environment.md §15](./development-environment.md#15-現時点で確定していること--していないこと) で
「未確定」とされている **Record / Replay のデータ形式**が、この Throw Record の定義によって決まる。

### Throw Record に含める想定内容（未確定）

| 区分 | 内容 |
|---|---|
| メタ | 記録ID、日時、ソース種別（live / replay / sim）、レイアウト、対象物の種類 |
| 観測 | 検出された3D位置の時系列（サンプル列） |
| 予測 | 時刻ごとの予測落下地点・予測落下時刻・残差（信頼度） |
| 指令 | 移動体へ送った目標座標の系列 |
| 実挙動 | オドメトリ、各輪の指令値と実速度、バッテリ電圧 |
| 結果 | 実際の落下地点、キャッチ成否（[NFR-7](./requirements.md#nfr-7-キャッチ成功率-最終的な合否条件)）、失敗理由 |
| 計測 | 段階別レイテンシ（[§13.1](./development-environment.md#131-実測する項目)） |

## 3. 柱1: 軌道シミュレータ ★最優先候補

**ブラウザ上で仮想的にゴミを投げ、予測と移動体の追従を再現する。**

- 技術: TypeScript ＋ Canvas / WebGL。配信は Hono（静的配信＋API）。
- 入力: 投擲位置・初速・角度・ばらつき、Depth ノイズ、検出遅れ、制御周期。
- 内部: 放物運動 → ノイズ付与 → 予測アルゴリズム → 3輪オムニの運動モデル（加速度上限・最高速度・減速）。

### なぜこれが最優先か

このプロジェクト最大のリスクは
**「そもそも時間予算内に間に合うのか」（[NFR-1](./requirements.md#nfr-1-短時間移動性能-主評価軸)）が
機体を作り終わるまで分からないこと**である。シミュレータはこれを**ハード完成前に**評価できる。

出力として最も価値があるのは、軌跡のアニメーションではなく**キャッチ可能領域の可視化**である。

```
    必要横移動量 [m]
      ^
  0.8 |  ×  ×  ×  ×          × = 間に合わない
      |  ×  ×  ×  ○          ○ = 間に合う
  0.4 |  ×  ○  ○  ○
      |  ○  ○  ○  ○
  0.0 +--------------------> 持ち時間 [s]
        0.3  0.5  0.7  0.9
```

この図があれば、[requirements.md §7-1](./requirements.md#7-未決事項次に決めること) の
**「投擲レイアウトをどう決めれば成立するか」を机上で設計できる。**
[drivetrain-spec.md §12](./drivetrain-spec.md#12-m2-で性能不足だった場合の調査順序) の改善順序7
「投擲レイアウトと必要横移動量の見直し」も、勘ではなく図の上で検討できる。

さらに [NFR-6](./requirements.md#nfr-6-到達時の静定) の
「停止して待つ / 通過キャッチを許容する」の比較も、**実機を壊さずに**試せる。

### ⚠️ 最大の落とし穴

**シミュレータは前提を入れた分しか返さない。** 楽観的なパラメータを入れれば
「余裕で間に合う」という誤った安心が出力される。これは実機を作った後に発覚すると最も痛い。

対策として、**シミュレータは M1 / M2 の実測値で較正されるまで「参考」扱いとする**ことを運用ルールにする。

| 段階 | シミュレータの位置付け |
|---|---|
| M1・M2 前 | 感度分析の道具。**絶対値を信用しない** |
| M1 実測後 | 検出遅れ・予測誤差の実測値を反映 |
| M2 実測後 | 加速度・最高速度・スリップの実測値を反映 |
| 較正後 | レイアウト設計・改善検討に使える |

## 4. 柱2: テレメトリとライブダッシュボード（IoT 的側面）

**Pi と ESP32 が計測値を送出し、開発PC上のサーバが収集・可視化・保存する。**

- 技術: Hono（収集API・WebSocket 配信）＋ ブラウザUI。保存は NDJSON もしくは SQLite。
- 送出元: Raspberry Pi 4（段階別レイテンシ・FPS・検出結果）、ESP32（電圧・エンコーダ・PWM・保護動作）。

### 満たせるもの

- [development-environment.md §13.1](./development-environment.md#131-実測する項目) の 10 項目
- [requirements.md M2](./requirements.md#8-段階的開発マイルストーン) の 14 項目
  （特に「急加速時の最低電圧」「スリップ」「ドライバ発熱」は**走行中でないと測れない**）
- [development-environment.md §4](./development-environment.md#4-raspberry-pi-4-向けの設計方針) の
  「GUI 表示を本番処理の必須要件にしない」——**Pi は headless のまま、表示は別マシンのブラウザ**という
  構成が自然に達成される

### 安全機能としての側面

[requirements.md M3](./requirements.md#8-段階的開発マイルストーン) で必要とした
**物理的な非常停止手段**を、ここに統合できる。

- スマホ／PC のブラウザから **arm / disarm / 即時停止**
- ダッシュボードとの接続断そのものを [FR-10](./requirements.md#2-機能要件fr) のフェイルセーフ判定に利用

> ただし**ブラウザ経由の停止を唯一の非常停止手段にしない。** Wi-Fi に依存する停止手段は、
> Wi-Fi が落ちる状況（＝まさに暴走しうる状況）で機能しない。物理スイッチとの併用を前提とする。

### 守るべき制約

[development-environment.md §4](./development-environment.md#4-raspberry-pi-4-向けの設計方針) は
「低レイテンシ優先」「不要な処理を減らす」と明記している。**テレメトリはこれに真っ向から反する追加負荷**である。

したがって以下を要件とする。

| # | 制約 |
|---|---|
| 1 | 送出は **fire-and-forget**（UDP もしくはローカル追記）。**送信完了を待たない** |
| 2 | 集計・可視化・保存の重い処理は **Pi 上で行わない** |
| 3 | テレメトリは**実行時に無効化できる** |
| 4 | **テレメトリ ON / OFF で end-to-end latency が有意に変化しないこと**を実測で確認する |

制約4 を満たせない場合、テレメトリは**測定対象を歪める**ため、計測器としての価値を失う。

## 5. 柱3: 投擲アーカイブとアルゴリズム・ベンチマーク

**すべての投擲を Throw Record として蓄積し、Web で再生・比較・採点する。**

- リプレイビューア: 3D 表示、タイムライン、**予測落下地点が時間とともにどう収束したか**の重ね描き
- ベンチマーク: 蓄積した N 件の記録に対し、複数の予測アルゴリズムを一括実行して採点

### 評価指標の例（未確定）

| 指標 | 意味 |
|---|---|
| 最終予測誤差 | [NFR-5](./requirements.md#nfr-5-位置精度暫定目標) |
| 落下時刻の予測誤差 | [NFR-6](./requirements.md#nfr-6-到達時の静定) |
| 予測が許容誤差内に収束するまでの時間 | [NFR-3](./requirements.md#nfr-3-予測レイテンシ暫定目標) |
| 誤検出率 | [FR-11](./requirements.md#2-機能要件fr) |
| キャッチ成功率 | [NFR-7](./requirements.md#nfr-7-キャッチ成功率-最終的な合否条件) |

### なぜ必要か

[development-environment.md §6](./development-environment.md#6-record--replay-を将来設計に含める) は
Replay を「重要な開発方針」としているが、**Replay できるだけでは「良くなったか」は分からない。**
同一データに対する採点があって初めて、アルゴリズム変更の可否を判断できる。

投擲は**ばらつきが大きく再現性が低い**ため、実機で毎回投げ直して比較する方式は成立しない。
記録に対する自動採点は、この分野では**事実上必須の開発インフラ**である。

## 6. 本体側のオリジナル機能候補（道具ではなく機能）

上記3つは開発基盤であり、「製品としての独自性」は別に検討する余地がある。

### 6.1 ★推奨: 投擲傾向の学習による待機位置の最適化

蓄積した Throw Record から**落下地点の分布を学習**し、**投擲される前に**最も有利な位置で待機する。

- 元動画は「投げられてから動く」。こちらは「**投げられる前に、動く距離が最小になる場所にいる**」。
- **NFR-1 の必要横移動量そのものを減らす**ため、独自機能でありながら**本体性能の底上げになる。**
- [drivetrain-spec.md §12](./drivetrain-spec.md#12-m2-で性能不足だった場合の調査順序) の改善順序7
  （投擲レイアウトの見直し）を、**手動調整ではなくデータ駆動で行う**位置付け。
- 投擲者ごとに癖が違えば、**人ごとの待機位置**へ発展させられる。

> これは柱3（アーカイブ）が存在して初めて成立する。**基盤と本体機能が噛み合っている**点で、
> 他の候補より筋が良いと考える。

### 6.2 その他の候補（優先度低）

| 候補 | 評価 |
|---|---|
| 連続投擲・複数個キャッチ | 難度が跳ね上がる割に、独自性は「回数」に留まる |
| 予測信頼度の LED 表示 | 安価で分かりやすい。デモ映えする。**柱2 の副産物として実装できる** |
| 効果音・音声 | 実装は容易だが工学的価値はない。最後に検討 |
| ゴミの種類判別（分別） | 別プロジェクト級。**スコープ外とする** |

## 7. 検討したが採用しない案

| 案 | 不採用の理由 |
|---|---|
| **ROS 2 を導入し rviz / rosbag を使う** | 柱2・柱3 は事実上 rosbag + rviz の再実装であり、標準品が存在するのは事実。しかし Pi 4 の資源制約（[§13](./development-environment.md#13-raspberry-pi-4-を継続するかの判断)）に対して重く、RealSense と合わせた導入コストも大きい。加えて本プロジェクトは独自性を目的に含むため、**軽量な自作を選ぶ**。ただし**先行事例として設計の参考にする。** |
| **Grafana + Prometheus でダッシュボード** | 柱2 だけなら合理的な選択。ただし Throw Record（1投擲 = 1エンティティ）はメトリクス時系列と相性が悪く、柱1・柱3 と統合できない。**単一スキーマで束ねる利点を優先する。** |
| クラウドへの常時送信 | 屋内・単一ネットワークで完結するため不要。レイテンシとプライバシーの面でも利点がない。**ローカル完結とする。** |
| 移動体へのカメラ搭載 | [development-environment.md §8](./development-environment.md#8-固定側と移動体側の責務) の責務分離を壊す。エゴモーション補正のため D435i が必要になり、[bom.md §A](./bom.md#a-検出センサー) の選定根拠とも矛盾する。 |

## 8. スコープに関する注意

> ⚠️ **本ドキュメント作成時点で、本体のソフトウェアは一行も存在しない。**
> その状態で Web スタックを追加すると、**基盤づくりだけで力尽きる**危険がある。

したがって以下を守る。

1. **各柱は、それが役立つマイルストーンに間に合う範囲でだけ作る。** 先回りして作り込まない。
2. **Throw Record スキーマの定義を最初に行う。** これだけは先に決めないと3つとも噛み合わない。
   逆に言えば、スキーマさえ決まれば各柱は独立に、後からでも追加できる。
3. 使用言語が Python（Pi）／C++（ESP32）／TypeScript（Web）の3つになる。
   **境界は Throw Record（JSON）1点に限定**し、それ以外で言語をまたがせない。
4. **Web レイヤを Raspberry Pi 上で動かさない。** 開発PC上で動かす（柱2 の制約2）。

### 推奨する着手順序（案・未確定）

| 順 | 対象 | 理由 |
|---|---|---|
| 1 | **Throw Record スキーマ定義** | 全体の前提。ハード不要 |
| 2 | **柱1 シミュレータ** | ハード完成前に NFR-1 の成立性を評価できる。最もリスクを下げる |
| 3 | **柱2 テレメトリ** | M1・M2 の測定要求を満たすため。実機着手と同時に必要になる |
| 4 | **柱3 アーカイブ／ベンチマーク** | 実データが貯まってから価値が出る |
| 5 | **6.1 待機位置の最適化** | 柱3 の蓄積が前提 |
