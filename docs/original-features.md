## 1. 出発点：再現だけでは足りない、が「飾り」を足すのも違う

独自機能として「LED を光らせる」「音を鳴らす」「キャラクター性を持たせる」といった演出は
いつでも足せるが、**プロジェクトの難所（§NFR-1 の時間予算）を1ミリも助けない。**

一方で、既存ドキュメントを読み返すと、**「測る」と書いてあるのに「どう測るか」が
どこにも書かれていない**箇所が大量にある。

| 出典 | 要求されている測定 | 収集手段 |
|---|---|---|
| [development-environment.md §13.1](./development-environment.md#131-実測する項目) | FPS・CPU・レイテンシを**段階別に**分解して計測 | **未定義** |
| [requirements.md M1](./requirements.md#8-段階的開発マイルストーン) | 飛行時間・検出遅れ・予測誤差など 7 項目 | **未定義** |
| [requirements.md M2](./requirements.md#8-段階的開発マイルストーン) | 移動距離・電圧降下・スリップなど 14 項目 | **未定義** |
| [requirements.md NFR-7](./requirements.md#nfr-7-キャッチ成功率-最終的な合否条件) | N 回投擲の成功率 | **未定義** |
| [development-environment.md §6](./development-environment.md#6-record--replay-を将来設計に含める) | Record / Replay（「重要な開発方針」と明記） | **フォーマット未定** |

つまりこのプロジェクトには、**本体とは別に「観測・再現・評価のための基盤」が丸ごと必要**であり、
そこがまだ空白になっている。ここを独自機能の中心に据える。

> **方針**: 独自機能は**演出ではなく道具**とする。
> 「M1〜M4 を実行するために必要だが、元動画には存在しないもの」を作る。
> 結果として、それがそのままデモとしても成立する。

## 2. 全体像：Throw Record を中心に置く

3つの柱をバラバラに作らず、**「1回の投擲＝1つの記録（Throw Record）」という単一スキーマ**で束ねる。

```
   [シミュレータ]      [実機ライブ]        [記録の再生]
        |                   |                   |
        +---------+---------+---------+---------+
                            |
                     Throw Record
              （1投擲の全経過を表す共通スキーマ）
                            |
        +---------+---------+---------+---------+
        |                   |                   |
   ダッシュボード       リプレイ表示        ベンチマーク
```

これは [development-environment.md §7](./development-environment.md#7-realsense-依存部分を将来的に分離する) の
「RealSense 依存部と処理部を疎結合にする」という方針を**一段上のレイヤへ拡張**したものである。
入力元が live / recorded / simulated のどれであっても、下流の表示・評価は同じコードで動く。

**副次的な効果**: [development-environment.md §15](./development-environment.md#15-現時点で確定していること--していないこと) で
「未確定」とされている **Record / Replay のデータ形式**が、この Throw Record の定義によって決まる。

> ⚠️ **v0.2 での注意**: 柱3 を見送り・柱2b を保留したため、**上図の下半分は当面「リプレイ表示」も
> 「ベンチマーク」も存在しない。** したがって **Throw Record を最初から完全な形で設計しない。**
> 柱1（シミュレータ）が必要とする最小形から始め、**「1投擲＝1レコード」という粒度だけを守る。**
> 粒度さえ守れば、柱3 は後から足せる。

### Throw Record に含める想定内容（未確定）

| 区分 | 内容 |
|---|---|
| メタ | 記録ID、日時、ソース種別（live / replay / sim）、レイアウト、対象物の種類 |
| 観測 | 検出された3D位置の時系列（サンプル列） |
| 予測 | 時刻ごとの予測落下地点・予測落下時刻・残差（信頼度） |
| 指令 | 移動体へ送った目標座標の系列 |
| 実挙動 | オドメトリ、各輪の指令値と実速度、バッテリ電圧 |
| 結果 | 実際の落下地点、キャッチ成否（[NFR-7](./requirements.md#nfr-7-キャッチ成功率-最終的な合否条件)）、失敗理由 |
| 計測 | 段階別レイテンシ（[§13.1](./development-environment.md#131-実測する項目)） |

## 3. 柱1: 軌道シミュレータ ★最優先候補

**ブラウザ上で仮想的にゴミを投げ、予測と移動体の追従を再現する。**

- 技術: TypeScript ＋ Canvas / WebGL。配信は Hono（静的配信＋API）。
- 入力: 投擲位置・初速・角度・ばらつき、Depth ノイズ、検出遅れ、制御周期。
- 内部: 放物運動 → ノイズ付与 → 予測アルゴリズム → 3輪オムニの運動モデル（加速度上限・最高速度・減速）。

### なぜこれが最優先か

このプロジェクト最大のリスクは
**「そもそも時間予算内に間に合うのか」（[NFR-1](./requirements.md#nfr-1-短時間移動性能-主評価軸)）が
機体を作り終わるまで分からないこと**である。シミュレータはこれを**ハード完成前に**評価できる。

出力として最も価値があるのは、軌跡のアニメーションではなく**キャッチ可能領域の可視化**である。

```
    必要横移動量 [m]
      ^
  0.8 |  ×  ×  ×  ×          × = 間に合わない
      |  ×  ×  ×  ○          ○ = 間に合う
  0.4 |  ×  ○  ○  ○
      |  ○  ○  ○  ○
  0.0 +--------------------> 持ち時間 [s]
        0.3  0.5  0.7  0.9
```

この図があれば、[requirements.md §7-1](./requirements.md#7-未決事項次に決めること) の
**「投擲レイアウトをどう決めれば成立するか」を机上で設計できる。**
[drivetrain-spec.md §12](./drivetrain-spec.md#12-m2-で性能不足だった場合の調査順序) の改善順序7
「投擲レイアウトと必要横移動量の見直し」も、勘ではなく図の上で検討できる。

さらに [NFR-6](./requirements.md#nfr-6-到達時の静定) の
「停止して待つ / 通過キャッチを許容する」の比較も、**実機を壊さずに**試せる。

### ⚠️ 最大の落とし穴

**シミュレータは前提を入れた分しか返さない。** 楽観的なパラメータを入れれば
「余裕で間に合う」という誤った安心が出力される。これは実機を作った後に発覚すると最も痛い。

対策として、**シミュレータは M1 / M2 の実測値で較正されるまで「参考」扱いとする**ことを運用ルールにする。

| 段階 | シミュレータの位置付け |
|---|---|
| M1・M2 前 | 感度分析の道具。**絶対値を信用しない** |
| M1 実測後 | 検出遅れ・予測誤差の実測値を反映 |
| M2 実測後 | 加速度・最高速度・スリップの実測値を反映 |
| 較正後 | レイアウト設計・改善検討に使える |

### 実装スタックの方針

**⚠️ 最大の技術的リスクは「同じアルゴリズムを2言語で二重実装すること」である。**

本番の予測ロジックは Python（Pi 上）で動く。もしシミュレータ側で予測ロジックを
TypeScript で書き直すと、**シミュレータが検証しているのは TS 実装であって、実際に載る Python 実装ではない。**
両者は必ず少しずつズレていき、しかも**ズレていることに気付けない。**
「シミュレータでは合っていたのに実機で外れる」の典型的な原因になる。

したがって以下を原則とする。

| 層 | 言語 | 根拠 |
|---|---|---|
| 物理モデル（放物運動・ノイズ・移動体の運動モデル） | **Python** | 本番と同じ言語。[development-environment.md §7](./development-environment.md#7-realsense-依存部分を将来的に分離する) の **simulated data 入力**として本番パイプラインへ直接流せる |
| 予測アルゴリズム | **Python のみ** | **本番と同一コードを使う。ブラウザ側に複製しない** |
| パラメータ掃引・キャッチ可能領域の算出 | **Python** | バッチ計算。ブラウザである必要がない |
| 可視化・インタラクティブ操作 | **TypeScript / ブラウザ** | Python が出力した結果を**表示する**。アルゴリズムを持たない |

```
Python                              ブラウザ
  物理モデル                          
  予測（本番と同一コード）      →  JSON  →   軌跡アニメーション
  パラメータ掃引                            キャッチ可能領域の図
                                            レイアウトの操作UI
```

> **原則**: **ブラウザ側に「本番にも存在するアルゴリズム」を置かない。**
> ブラウザが持ってよいのは、描画と、結果を眺めるための軽量な補間だけとする。

### Hono を今は使わない

当初 Hono での配信を想定していたが、**上記の構成では常駐サーバが要らない。**

- Python が JSON を出力 → ブラウザがそれを読んで描画するだけ
- 開発時は静的ファイル配信（`vite` 等）で足り、**HTTP エンドポイントを書く必要がない**

Hono が価値を持つのは「**HTTP API を持つサーバ**」が要るときであり、
柱3 を見送り・柱2b を保留した現時点では**その用途が存在しない。**

> 使いたい技術に合わせて用途を作らない。**2b を作ると判断した時点で改めて検討する**（そこでは適切な選択になる）。

## 4. 柱2: 計測データの収集（ロギングとダッシュボード）

> **判断**: 当初これを一体のものとして書いていたが、**費用対効果がまったく異なる2つが混ざっていた。**
> 分割した上で、片方のみ採用する。

| 区分 | 内容 | 判断 |
|---|---|---|
| **2a 構造化ロギング** | 各処理段階の時刻・計測値を機上で記録し、**後から**解析する | **採用**（M1 / M2 で必要） |
| **2b ライブダッシュボード** | Wi-Fi でリアルタイム送信し、ブラウザで監視する | **保留**（M3 で再判断） |

### 4.1 2a 構造化ロギング — これは避けられない

[development-environment.md §13](./development-environment.md#13-raspberry-pi-4-を継続するかの判断) は
**「実測して Pi 4 を継続するか判断する」**という構造になっている。段階別レイテンシが取れなければ、
この判断そのものが下せない。同様に [M2 の14項目](./requirements.md#8-段階的開発マイルストーン) は、
**取得できなければ M2 が完了しない。**

つまり 2a は独自機能というより**前提条件**である。そして実体は「タイムスタンプ付きの構造化ログを吐き、
後で集計する」だけであり、**Web スタックも通信基盤も要らない。**

| 対象 | 記録方法 |
|---|---|
| Raspberry Pi 4 | 各段階の時刻・FPS・検出結果を構造化ログとしてファイルへ追記 |
| ESP32 | 走行中は**RAM にバッファ**し、走行終了後にまとめて吸い出す |

> **ESP32 側でリアルタイム送信しない理由**: M2 の1試行は 1 秒未満で終わる。
> 200 Hz × 十数項目 × 1秒でも数 KB にすぎず、**RAM に溜めて後で吸い出す方が単純で、しかも取りこぼさない。**
> 走行中に Wi-Fi 送信を挟むと、制御ループに送信処理のジッタが乗る。
> **得られるものが無いのに副作用だけがある。**

### 4.2 2b ライブダッシュボードを今は作らない理由

**M1 / M2 で観測したい現象は、人間がリアルタイムで見るには速すぎる。**

- [NFR-1](./requirements.md#nfr-1-短時間移動性能-主評価軸) の評価対象は **0.4 / 0.6 / 0.9 秒**。
  画面を見ていても何も判断できない。必要なのは**後から拡大して読める記録**である。
- 「急加速時の最低電圧」「発進時スリップ」も同様に、**発生は一瞬で、価値は事後解析にある。**
- ダッシュボードは**見た目に反して、判断材料をほとんど増やさない。**

ライブ表示に意味が出るのは以下であり、いずれも M3 以降の話である。

- ゆっくり変化する量（バッテリ電圧・モータ温度）をセッションを通して監視するとき
- 「固定側が今なにを検出しているか」を、機体の横に立って見ながらデバッグするとき

→ **M3 に着手する時点で改めて判断する。それまでは作らない。**

### 4.3 非常停止をブラウザに持たせない

当初「スマホから緊急停止」を利点として挙げたが、**これは採用しない。**

Wi-Fi に依存する停止手段は、**Wi-Fi が落ちる状況＝まさに暴走しうる状況**で機能しない。
[requirements.md M3](./requirements.md#8-段階的開発マイルストーン) が要求する非常停止は、
**物理スイッチ**で満たす（[bom.md §D-11](./bom.md#d-電源保護ノイズ対策) のメイン電源スイッチで
兼ねられるかを含めて判断する）。

> ブラウザからの停止は「便利機能」であって「安全装置」ではない。**両者を混同しない。**
> [FR-10](./requirements.md#2-機能要件fr)（通信途絶フェイルセーフ）は移動体側で完結して実装する。

### 守るべき制約

将来 2b を作る場合、および 2a を Pi 上で動かす場合に守る。

[development-environment.md §4](./development-environment.md#4-raspberry-pi-4-向けの設計方針) は
「低レイテンシ優先」「不要な処理を減らす」と明記している。**計測の追加はこれに反する負荷**である。

| # | 制約 |
|---|---|
| 1 | 記録は **fire-and-forget**（ローカル追記もしくは UDP）。**完了を待たない** |
| 2 | 集計・可視化の重い処理は **Pi 上で行わない**（記録するだけにする） |
| 3 | 計測は**実行時に無効化できる** |
| 4 | **計測 ON / OFF で end-to-end latency が有意に変化しないこと**を実測で確認する |

制約4 を満たせない場合、計測は**測定対象を歪める**ため、計測器としての価値を失う。

> **判断: 現時点では作らない。**
> 採点対象となる実データが1件も無い段階で採点基盤を作っても、検証できるものが無い。
> **M1 で実投擲データが貯まってから、必要性を再判断する。**
>

>
> 以下は将来再検討するための記録として残す。

**すべての投擲を Throw Record として蓄積し、Web で再生・比較・採点する。**

- ベンチマーク: 蓄積した N 件の記録に対し、複数の予測アルゴリズムを一括実行して採点

### なぜ必要か

[development-environment.md §6](./development-environment.md#6-record--replay-を将来設計に含める) は
Replay を「重要な開発方針」としているが、**Replay できるだけでは「良くなったか」は分からない。**
同一データに対する採点があって初めて、アルゴリズム変更の可否を判断できる。

投擲は**ばらつきが大きく再現性が低い**ため、実機で毎回投げ直して比較する方式は成立しない。
記録に対する自動採点は、この分野では**事実上必須の開発インフラ**である。

## 6. 本体側のオリジナル機能候補（道具ではなく機能）

上記3つは開発基盤であり、「製品としての独自性」は別に検討する余地がある。

### 6.1 投擲傾向の学習による待機位置の最適化（見送り／将来の第一候補）

> **判断: 柱3 を見送ったため、これも自動的に見送る。**
> ただし**将来オリジナル機能を1つ足すならこれを選ぶ**という位置付けは維持する。以下は理由の記録。

蓄積した Throw Record から**落下地点の分布を学習**し、**投擲される前に**最も有利な位置で待機する。

- 元動画は「投げられてから動く」。こちらは「**投げられる前に、動く距離が最小になる場所にいる**」。
- **NFR-1 の必要横移動量そのものを減らす**ため、独自機能でありながら**本体性能の底上げになる。**
- [drivetrain-spec.md §12](./drivetrain-spec.md#12-m2-で性能不足だった場合の調査順序) の改善順序7
  （投擲レイアウトの見直し）を、**手動調整ではなくデータ駆動で行う**位置付け。
- 投擲者ごとに癖が違えば、**人ごとの待機位置**へ発展させられる。

> これは柱3（アーカイブ）が存在して初めて成立する。**基盤と本体機能が噛み合っている**点で、
> 他の候補より筋が良いと考える。

### 6.2 その他の候補（優先度低）

| 候補 | 評価 |
|---|---|
| 連続投擲・複数個キャッチ | 難度が跳ね上がる割に、独自性は「回数」に留まる |
| 予測信頼度の LED 表示 | 安価で分かりやすい。デモ映えする。移動体側で完結するため**柱2b とは独立に実装できる** |
| 効果音・音声 | 実装は容易だが工学的価値はない。最後に検討 |
| ゴミの種類判別（分別） | 別プロジェクト級。**スコープ外とする** |

## 7. 検討したが採用しない案

| 案 | 不採用の理由 |
|---|---|
| **ROS 2 を導入し rviz / rosbag を使う** | 柱2・柱3 は事実上 rosbag + rviz の再実装であり、標準品が存在するのは事実。しかし Pi 4 の資源制約（[§13](./development-environment.md#13-raspberry-pi-4-を継続するかの判断)）に対して重く、RealSense と合わせた導入コストも大きい。**加えて柱3 を見送り・柱2b を保留した結果、ROS 2 が肩代わりできる部分がほぼ残っていない。** 柱2a（構造化ログを吐くだけ）に ROS 2 は不要。ただし**先行事例として設計の参考にする。** |
| **Grafana + Prometheus でダッシュボード** | 柱2b を作る場合には合理的な選択。ただし Throw Record（1投擲 = 1エンティティ）はメトリクス時系列と相性が悪い。**そもそも 2b 自体を保留したため、現時点では検討対象にならない。** 2b を作ると判断した時点で、自作より先にこちらを検討する。 |
| クラウドへの常時送信 | 屋内・単一ネットワークで完結するため不要。レイテンシとプライバシーの面でも利点がない。**ローカル完結とする。** |
| 移動体へのカメラ搭載 | [development-environment.md §8](./development-environment.md#8-固定側と移動体側の責務) の責務分離を壊す。エゴモーション補正のため D435i が必要になり、[bom.md §A](./bom.md#a-検出センサー) の選定根拠とも矛盾する。 |

## 8. スコープに関する注意

> ⚠️ **本ドキュメント作成時点で、本体のソフトウェアは一行も存在しない。**
> その状態で Web スタックを追加すると、**基盤づくりだけで力尽きる**危険がある。

v0.2 で柱3 を見送り・柱2b を保留したため、**当面作るのはシミュレータとロギングの2つだけ**になった。
その上で以下を守る。

1. **それが役立つマイルストーンに間に合う範囲でだけ作る。** 先回りして作り込まない。
2. **Throw Record スキーマは「柱1 で必要な最小形」から始める。**
   柱3 を見送ったため、**最初から完全なスキーマを設計しない。**
   ただし後から柱3 を足せるよう、**1投擲を1レコードとして扱う形だけは崩さない。**
3. 使用言語は Python（本体・シミュレータ）／C++（ESP32）／TypeScript（表示）。
   **TypeScript 側に本番と重複するアルゴリズムを置かない**（→ [§3 実装スタックの方針](#実装スタックの方針)）。
4. **表示レイヤを Raspberry Pi 上で動かさない。** 開発PC上で動かす。

### 着手順序

| 順 | 対象 | 理由 |
|---|---|---|
| 1 | **柱1 シミュレータ**（Python の物理・予測モデル） | ハード不要で着手でき、[NFR-1](./requirements.md#nfr-1-短時間移動性能-主評価軸) の成立性を最も早く評価できる |
| 2 | **柱1 の可視化**（ブラウザ表示・キャッチ可能領域） | 1 の結果を読める形にする。ここが**デモとしても成立する部分** |
| 3 | **柱2a 構造化ロギング** | 実機着手（M1）と同時に必要。Web 不要 |
| — | 柱2b / 柱3 / 6.1 | **作らない。** M3 到達時・実データ蓄積時に再判断 |

> 順序 1 と 2 を分けているのは、**1 だけでも判断材料としては足りる**ため。
> 2 に時間をかけすぎて 1 の結論が出ない、という失敗を避ける。
