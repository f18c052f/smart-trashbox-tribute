# Smart Trashbox Tribute — 共通要件定義 v0.2

元動画: [勝手に入るゴミ箱作った Smart Trashbox](https://www.youtube.com/watch?v=NqDTE6dHpJw)（倉田捻氏 / 文化庁メディア芸術祭受賞 / 制作約1年）

関連: [drivetrain-spec.md](./drivetrain-spec.md)（駆動系詳細） / [bom.md](./bom.md)（部品表） / [development-environment.md](./development-environment.md)（開発環境・実行環境）

> **v0.1 からの方針転換（重要）**
> 旧版は **「最高速度 ≥ 1.5 m/s」を絶対的なハード要件**としていたが、これを**取り下げる**。
> 本プロジェクトの目的は「指定最高速度を達成すること」ではなく、
> **「飛来するゴミの落下地点を予測し、残された時間内にゴミ箱がそこへ移動してキャッチすること」**である。
> したがって性能は**最高速度単独ではなく短時間移動性能で評価**する（→ §3 NFR-1）。
> 旧数値（1.5 m/s、設計最高 1.8 m/s、加速度 2〜3 m/s²、車体質量 3〜4 kg）は
> **参考値・過去の設計目標として残すが、合否条件として扱わない。**

## 0. 前提・スコープ

- **目標忠実度**: 元動画と同等。投げられたゴミを、床を走行するゴミ箱が移動して受け止める。
- **足回り**: 既製キットは購入せず、**部品から自作**（3輪オムニ・確定）。詳細は [drivetrain-spec.md](./drivetrain-spec.md)。
- **手持ち環境**: 3Dプリンタあり。切削加工機（ボール盤・旋盤・フライス）なし。
- したがって**金属切削・精密ギア自作を要する設計は避け**、3Dプリント造形＋既製モジュールの組合せで成立する構成を要件とする。
- ゴミ箱本体は**市販の軽量PP製**を利用し、3Dプリントは駆動ベース・アダプタ・トレイ類に限定する。

### 0.1 使用環境（初期バージョン）

| 項目 | 内容 |
|---|---|
| 場所 | **屋内** |
| 床面 | **平坦な床**（フローリング等を想定） |
| 段差越え | **要求しない** |
| 厚いカーペット走行 | **要求しない** |

> ⚠️ 60mm ホイールを使用するため**最低地上高が小さい**。これは上記使用環境を前提とした割り切りであり、
> 機構設計上の注意事項として扱う（[drivetrain-spec.md §6.3](./drivetrain-spec.md#63-最低地上高)）。

## 1. システム構成（サブシステム分解）

元システムは「知能（固定側）」と「身体（移動体）」が分離し、両者を**目標座標データ**で繋ぐ構造。この骨格は忠実再現でも不変＝**共通要件の中核**。

```
[検出ステーション(固定)] --(予測座標)--> [無線通信] --> [移動体ゴミ箱]
   ゴミを空中で追跡          放物線から             目標地点へ走行して
   → 3D位置を時系列取得      落下地点(x,y)算出        落下時刻までに到達
```

実機への割り当ては以下（詳細は [development-environment.md](./development-environment.md) を正とする）。

```
RealSense D435 → Raspberry Pi 4 Model B → (小さいデータ) → ESP32 → 3輪オムニ移動体
        └──────── 固定側 ────────┘          └──── 移動体側 ────┘
```

| # | サブシステム | 配置 | 役割 |
|---|---|---|---|
| A | 検出 | 固定（壁/天井/三脚） | 飛来するゴミの3D位置を時系列で取得 |
| B | 予測 | 固定側 Raspberry Pi 4 | 放物運動から床の落下座標を算出 |
| C | 通信 | 両側 | 目標座標を移動体へ無線送信 |
| D | 移動体（駆動） | ゴミ箱 | 目標座標へ全方向走行、現在位置把握 |
| E | 電源 | 移動体 | バッテリ駆動・自律給電 |

> **Raspberry Pi は固定側に置く。ゴミ箱本体へ搭載しない。**
> ESP32 へ送るのは予測結果（目標座標・到達時刻）のみで、**画像・Depth フレームは送らない**。

## 2. 機能要件（FR）

- **FR-1 空中物体検出**: 飛来するゴミの3D位置 (x, y, z) を、落下までに**最低3サンプル**取得できること（2点だと放物線頂点通過時に速度を誤る）。
- **FR-2 落下地点予測**: サンプル列に重力加速度を含む放物運動モデルを当てはめ、床面到達座標 (x, y) と到達時刻を推定できること。
- **FR-3 座標系変換**: 検出側座標系 → 移動体座標系（床平面）へ変換できること。
- **FR-4 無線送信**: 予測座標を移動体へ低遅延で送信できること。
- **FR-5 走行制御**: 移動体が目標座標へ、**その場で向き直す時間を待たずに**移動できること（全方向駆動）。
- **FR-6 自己位置把握**: 移動体が自身の現在位置を推定し、目標との差分を詰められること。
- **FR-7 受け口**: 落下ゴミを取りこぼさない開口（漏斗/ワイドリム）を持つこと。
- **FR-8 復帰**: キャッチ後、待機位置へ戻れること（元動画同等の演出）。
- **FR-9 安全停止**: モータロック検出時およびバッテリ低電圧時に、モータ出力を停止できること
  （[drivetrain-spec.md §5 / §9.2](./drivetrain-spec.md#5-モータロック保護ソフトウェア)）。

## 3. 性能要件（NFR）＝ 難所

物理から逆算した**時間予算**が全体を規定する。ここを満たせるかがプロジェクトの成否。

- 人が2〜3m先から山なりに投げる → **総飛行時間 ≈ 0.6〜1.2s**。
- 検出開始〜予測確定に **≈ 0.2s**（3サンプル）を要する。
- → **移動体に残された時間 ≈ 0.4〜0.9s**。
- この間に横方向の狙い誤差（想定 **0.3〜0.8m**）を詰める必要がある。

> 上記の飛行時間・狙い誤差は**設計上の想定値**であり、実測に基づく確定値ではない。
> M1（予測可視化）で実際の投擲を計測し、必要ならこの前提自体を更新する。

### NFR-1 短時間移動性能 ★主評価軸

**最高速度単独では評価しない。** 静止状態から目標座標へ移動指令を与えたとき、
上記の時間予算に対応する **0.4秒 / 0.6秒 / 0.9秒** 経過時点で以下を実測する。

| 経過時間 | 測定項目 |
|---|---|
| 0.4 s | 移動距離 / 速度 / ホイールスリップの有無 / バッテリー電圧降下 / 到達位置誤差 |
| 0.6 s | 同上 |
| 0.9 s | 同上 |

- 旧要件の **1.5 m/s は「参考目標値」**として扱う（合否条件ではない）。
- **最終的な成功条件**:
  **「実際に想定する投擲条件において、落下時刻までにキャッチ可能範囲へ到達できること」**
  （＝ 各時刻の移動可能距離 ≥ その投擲条件で必要な移動量）

**初期MVPでは以下を許容する**（＝これらも**システム設計の一部**として扱う。逃げではない）:

- 投擲開始位置をある程度固定する
- 投擲方向をある程度固定する
- ゴミ箱の待機位置を調整する
- 必要横移動量を小さくする

### NFR-2 加速・安定性

**2〜3 m/s² という数値を必須条件にしない。** 以下を重視する。

- キャッチに必要な**短時間加速**が得られること
- 発進時に**過度な空転（スリップ）が発生しない**こと
- 急加速・急停止時に**転倒しない**こと
- **重量物を底部に配置し低重心**とすること
- **フレーム剛性**を維持すること

**車体重量にも絶対的な上限を設定しない。** ただし設計方針として以下を推奨する:

- 上部構造を軽量化する
- 市販の軽量PP製ゴミ箱を利用する
- バッテリー・モータを最下部に配置する
- 不要な3Dプリント部品を減らす

> **2〜2.5 kg 程度に収まれば望ましいが、これも必須条件ではない。**（旧「3〜4 kg 想定」は参考値）

### NFR-3 予測レイテンシ

検出→座標送信まで **< 250 ms**。（§3 冒頭の時間予算「予測確定 ≈ 0.2s」と整合）

### NFR-4 制御周期

検出・追従ループ **≥ 60 fps 相当**。

### NFR-5 位置精度

最終到達誤差 **< 開口半径**（例: 開口φ200mm なら ±100mm）。

## 4. 制約条件

- **CON-1**: 切削加工不可。金属フレーム・精密ギアの自作前提の設計は不採用。
- **CON-2**: 造形は3Dプリント（FDM想定）。強度・寸法精度はこの範囲。
- **CON-3**: 使用環境は屋内・平坦床（§0.1）。段差・厚手カーペットは対象外。
- **CON-4**: 手持ち部品（[bom.md](./bom.md)）を可能な限り流用する。
  特に Nexus 14145 / 18020 を活かすため、モータは **6mm Dシャフト**互換を維持する。

## 5. サブシステム別 要件と実現方針

### A. 検出
- 要件: 空中の小物体を時系列3D追跡（FR-1）。
- **確定: Intel RealSense D435**。グローバルシャッターで高速移動物体に強い。カメラは固定運用。
- **接続先は Raspberry Pi 4 Model B**（固定側）。解像度・fps の初期評価候補は 640×480 / 30fps だが、
  **必須性能でも達成済み性能でもない**（[development-environment.md §5](./development-environment.md#5-realsense-の初期設定方針)）。

### B. 予測
- 要件: 放物線フィッティング（FR-2）。
- 方針: z(t)=z0+vz·t−½g·t²、x,y は等速。3点以上で最小二乗。床平面 z=0 との交点を解く。
- **実行環境: Raspberry Pi 4 Model B**（Python/OpenCV）。**開発は WSL 側**で行い、Pi へは Git 経由で持ち込む
  （[development-environment.md §2](./development-environment.md#2-環境の役割分担)）。
- 物体検出方式は**未確定**。Pi 4 の性能を考慮し、軽量方式（Depth差分・背景差分・フレーム間差分・ROI・輪郭抽出等）も
  含めて実測後に決める。**AIモデルを最初から必須にしない。**

### C. 通信
- 要件: 低遅延・軽量（FR-4, NFR-3）。
- 送るのは予測結果のみ。**画像・Depth フレームは送らない。**
- 方式は**未確定**。候補として UDP / Wi-Fi / Serial / 固定側 ESP32 を挟む Bridge を残す。
  Bluetoothは接続確立遅延に注意。
  ⚠️ **ESP-NOW を Raspberry Pi から直接使えることを前提にしない**
  （[development-environment.md §9.2](./development-environment.md#92-通信方式候補を残す)）。

### D. 移動体（駆動）★核心
- 要件: 全方向走行（FR-5）＋短時間移動性能（NFR-1/2）＋自己位置（FR-6）。
- **確定: 3輪オムニ・120°配置を部品から自作**。既製の全方向ベースは 0.6 m/s 級かつ改造前提になるため購入しない。
- 詳細仕様（モータ・ドライバ・電源・機構・保護）は **[drivetrain-spec.md](./drivetrain-spec.md) を正**とする。
- 自己位置: ホイールエンコーダ（オドメトリ）必須。エンコーダの counts/rev は **M2 で実測校正**する。
  長時間はドリフトするため、床マーカ/上方カメラでの補正を将来オプション化。

### E. 電源
- 要件: 移動体の自律給電。急加速時のピーク電流に耐えること。
- **確定: 3S LiPo**。モータドライバへ直接供給、ロジックは BP5293-50 で 5V 化。
- 低重心化のため**バッテリは最下部配置**。
- 安全: バッテリ直近に **10A メインヒューズ**、ESP32 による**電圧監視と低電圧保護**（FR-9）。

### 3Dプリンタの活用範囲（加工なしを補う部分）
- 駆動ベース（中央プレート＋モータ取付部3箇所）
- 市販PPゴミ箱の固定アダプタ
- バッテリートレイ・基板トレイ、配線ガイド
- ワイドな受け口漏斗（FR-7）
- センサー固定治具（壁/三脚マウント）

> モータは**付属の金属ブラケット**経由で駆動ベースに固定する。3Dプリント部品でモータ本体を直接クランプしない。

## 6. インターフェース定義（サブシステム間の契約）

- **座標系**: 床平面を基準。原点・軸方向を検出側と移動体側で共有。
- **目標データ**: `{ x_mm, y_mm, t_impact_ms }` を1メッセージで送信。
- **単位**: 距離mm、時刻ms（送信時刻基準の相対）。

> 上記は**現時点の最小形**であり、プロトコルを確定しすぎない方針。
> 必要に応じて timestamp / sequence number / confidence / validity 等の追加を将来検討する
> （[development-environment.md §9](./development-environment.md#9-pi--esp32-の通信内容)）。

## 8. 段階的開発マイルストーン

### M1 予測の可視化
センサーでゴミを追跡し、落下地点をプロット。移動体なしで予測精度を検証。
あわせて**実際の投擲の飛行時間と狙い誤差を実測**し、§3 の時間予算の前提を検証する。

M1 は一括では作らず、**Raspberry Pi 4 上で以下の順に段階検証**する
（[development-environment.md §12](./development-environment.md#12-段階的な検証方針)）。

1. D435 を Pi 4 で安定取得 → 2. 実データ記録 → 3. 検出 → 4. 3D位置取得 → 5. 追跡 → 6. 軌道予測

> 早い段階で**実データを記録**しておくと、以降の検出・追跡・予測の改善を
> WSL 上の Replay で繰り返し検証できる（[development-environment.md §6](./development-environment.md#6-record--replay-を将来設計に含める)）。
> なお**可視化（GUI）は開発用であり、本番処理の必須要件にしない。**

### M2 移動体の短時間応答評価 ★NFR-1 の検証

**単なる最高速度試験ではなく、「実車の短時間応答評価」とする。** 最低限、以下を記録する。

| # | 記録項目 |
|---|---|
| 1 | 静止 → **0.4秒**の移動距離 |
| 2 | 静止 → **0.6秒**の移動距離 |
| 3 | 静止 → **0.9秒**の移動距離 |
| 4 | 最高速度（**参考値**。合否条件ではない） |
| 5 | 発進時ホイールスリップの有無 |
| 6 | バッテリー静止時電圧 |
| 7 | 急加速時の最低電圧 |
| 8 | 前後左右および斜め方向の走行性能 |
| 9 | 目標地点への停止誤差 |
| 10 | 同一指令を10回程度繰り返したときのばらつき |
| 11 | **エンコーダ1回転あたりの実測カウント**（`ENCODER_COUNTS_PER_WHEEL_REV` の校正） |
| 12 | モータドライバ（TB67H450）の発熱 |
| 13 | モータの発熱 |
| 14 | 急停止時の転倒・浮き上がりの有無 |

> M2 の前に、**モータロック保護**と **LiPo低電圧保護**（FR-9）を実装しておくこと。
> 性能が不足していた場合の調査順序は
> [drivetrain-spec.md §12](./drivetrain-spec.md#12-m2-で性能不足だった場合の調査順序) に従う（**すぐに高価なモータへ交換しない**）。

### M3 結合
予測→通信→走行を接続し、静的な短距離キャッチ。まずは投擲位置・方向を固定した MVP 条件で成立させる（NFR-1 の許容事項）。
Pi 4 → ESP32 の通信確立（[development-environment.md §12](./development-environment.md#12-段階的な検証方針) の段階7〜8）がここに対応する。

### M4 高速化・チューニング
時間予算内に収める。必要横移動量の見直し（レイアウト調整）も改善手段に含む。復帰動作(FR-8)を追加。
