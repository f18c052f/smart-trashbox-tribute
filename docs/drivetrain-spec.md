**3輪オムニを選ぶ理由**: 円形ゴミ箱は機体の向き維持が不要なのでメカナムの利点が無効。
オムニはモータ力を無駄なく並進に使えて速度・加速で有利。3モータで軽量・安価・制御単純。3点接地でゴミ落下時の重心移動にも強い。

## 2. 使用環境（初期バージョン）

- **屋内**、**平坦な床**（フローリング等を想定）
- **段差越えは要求しない**
- **厚いカーペット走行は要求しない**

> ⚠️ 60mm ホイールを採用したため**最低地上高が小さい**。これは上記の使用環境を前提とした割り切りであり、
> 機構設計では「フレーム下面・ボルト頭・ブラケット・配線が床に接触しないこと」を必ず確認する（→ §6）。

## 3. モータ仕様（JGB37-520）

商品仕様（出品情報より転記。実測値ではない）:

| 項目 | 値 |
|---|---|
| 電圧 | DC 12V |
| 無負荷回転数 | 530 RPM |
| 減速比 | 約 19:1 |
| 定格回転数 | 約 407 RPM |
| 定格トルク | 約 2.2 kgf·cm |
| 最大トルク | 約 3.1 kgf·cm |
| ストール電流 | 約 2.3 A |
| シャフト | 6mm D カット、**長さ 約15.5mm** |
| 回転方向 | CW / CCW |
| エンコーダ | ホールエンコーダ、電源 3.3V / 5V、基本分解能 11 PPR |
| 付属品 | 金属モータブラケット、取付ネジ |

### 3.1 60mm ホイールでの理論周速

- 60mm ホイール円周 = π × 0.060 = **0.1885 m/回転**
- 無負荷 530 RPM → 530 / 60 × 0.1885 ≈ **1.66 m/s**
- 定格 407 RPM → 407 / 60 × 0.1885 ≈ **1.28 m/s**（参考）

> ⚠️ **これらは無負荷／定格の理論値であり、実車速度を保証するものではない。**
> 実車では車体質量・転がり抵抗・ホイールスリップ・バッテリー電圧降下・ドライバ損失により低下する。
> 実車速度は M2（[requirements.md §8](./requirements.md#8-段階的開発マイルストーン)）で**実測**する。

### 3.2 エンコーダ分解能（固定値をハードコードしないこと）

- 目安: 11 PPR × 減速比 約19 ≈ **209 pulse / 出力軸1回転**
  （メーカー記載「モーターには1周あたり11個のパルスがあります／分解能 ＝ 11 × 減速比」と一致。2026-08-30 確認）
- ただし実際の counts/rev は以下で変わる:
  - A/B相のカウント方法（A相のみ / A・B両相 / 4逓倍）
  - 立上りのみカウントか、立上り＋立下りか
  - 実ギア比（「約19:1」は公称。実際は非整数比のことが多い）
  - ESP32 側のカウント方式（PCNT の設定）

→ **M2a-0（ホイールを浮かせた台上）でホイールを実際に1回転させ、
`ENCODER_COUNTS_PER_WHEEL_REV` を実測・校正する。**
根拠のない固定値をコードに埋め込まない。

## 4. モータドライバ AE-TB67H450

- 秋月電子 AE-TB67H450 ×3。**1モータにつき1台**使用。
- 位置付け: **低価格な試作1号機用**。将来モータを変更する際はドライバも交換できるよう、
  基板トレイ・配線・取付穴は**ドライバ交換を前提**とした構造にする。
- ⚠️ JGB37-520 のストール電流 約2.3A は **AE-TB67H450 の能力に比較的近い**。
  したがって **「モータを長時間ストールさせないこと」を重要な保護要件**とする（→ §5）。
  ドライバの発熱は M2 で実測する（→ §11）。

## 5. モータロック保護（ソフトウェア）

**ハードウェアヒューズだけでモータロックを保護しない。** メインヒューズ（§8）は短絡・配線事故用であり、
1モータのストール（約2.3A）では溶断しない。ESP32 側でソフトウェア保護を実装する。

判定ロジック（例）:

```
if (PWM指令が高い) && (エンコーダ速度 ≈ 0) && (その状態が T ms 継続)
    → 該当モータの出力を停止
```

- 初期値の目安: **T = 100〜200 ms 程度**
- ただし**実機試験で調整できるパラメータ**とし、固定仕様にしない
- 復帰条件（自動復帰 / 手動リセット）は M2a-1 の挙動を見て決める（→ [OQ-15](./open-questions.md#c-電源安全)）

## 6. 機構設計

### 6.1 付属金属ブラケットを利用する（標準案）

JGB37-520 セットには**金属モータブラケットが付属**する。
よって**モータ本体を3Dプリント部品で直接クランプする設計は標準案としない。**

```
JGB37-520
   ↓
付属 金属ブラケット
   ↓
3Dプリント 駆動ベース
```

メリット:
- モータ固定剛性の向上
- モータ位置決めが容易
- FDM部品への応力集中を減らせる
- CAD設計が単純になる
- モータ交換が容易

3Dプリントベース側は、**ブラケット固定穴を長穴（スロット）化**するなどして多少の寸法差を吸収できる設計とする。

> ⚠️ **CADの最終穴寸法は、モータおよびブラケット到着後に現物をノギスで測定して確定する。**
> 現時点で穴ピッチ等を数値で確定させない。

### 6.2 3Dプリント範囲

ゴミ箱本体まで全面3Dプリントする構成は**標準案から外す**（重量・造形時間・剛性のいずれも不利）。

推奨構成:

| 部位 | 方針 |
|---|---|
| ゴミ箱本体 | **市販の軽量PP製ゴミ箱**を利用 |
| 駆動ベース | 3Dプリント（中央プレート＋3つのモータ取付部のモジュラー構造） |
| ゴミ箱固定アダプタ | 3Dプリント |
| バッテリートレイ | 3Dプリント（最下部配置） |
| 基板トレイ | 3Dプリント |
| ワイドリム / 漏斗 | 必要に応じて3Dプリント（FR-7） |
| **整備スタンド** | 3Dプリント。**M2a-0 でホイールを浮かせて回すための台**（→ §10.1） |

- **金属切削加工は要求しない**（CON-1）。

### 6.3 最低地上高

- 60mm ホイール → **車軸中心高さ 約30mm**
- モータ径 37mm（半径 18.5mm）。モータ軸をホイール軸と同軸に配置した場合、
  モータ胴体下面は床から **約 11.5mm**（＝30 − 18.5）。**余裕は小さい。**
- 以下が床に接触しないことを確認する:
  - 付属ブラケット
  - ボルト頭・ナット
  - フレーム（駆動ベース）下面
  - 配線

### 6.4 CAD着手手順

モータ到着後、以下を**仮組みして実寸を測定してから** CAD を完成させる。

1. モータ（JGB37-520）。シャフトは 6mm D・長さ約15.5mm
2. 付属金属ブラケット
3. 6mm ハブ（Nexus 18020 相当品）。**外径・軸方向長さ・使用するボルト円が未確認**
4. 60mm ダブルオムニホイール（外径 Ø60 / 幅 25.6 / **中心穴 Ø12.5** / ボルト円 Ø21・Ø28 は図面で確定済み）

測定項目 → §11「実機で確認する事項」。

> ⚠️ **ホイール／ハブは非純正品である。** 公称寸法をそのまま CAD へ入れず、
> **実効ホイール径・ハブ穴の D 形状・取付穴ピッチを必ず実測する**（→ §11 #4a / #4b / #4c）。
> 実効ホイール径はオドメトリ（FR-6）と `trajectory_sim` の `wheel_diameter_mm` の
> **両方へ効く**ため、機構だけの問題ではない。

## 7. エンコーダ接続

ESP32 の GPIO は 3.3V 系のため、**初期構成ではエンコーダも 3.3V 駆動**する。

| エンコーダ側 | 線色 | 接続先 |
|---|---|---|
| VCC | **青** | **3.3V** |
| GND | **黒** | GND |
| A相 | **黄 or 緑** | ESP32 GPIO |
| B相 | **緑 or 黄** | ESP32 GPIO |

モータ電源は**別系統**である:

| モータ側 | 線色 | 接続先 |
|---|---|---|
| モータ電源＋ | **赤** | ドライバ出力（12V 系。ストール 2.3A） |
| モータ電源− | **白** | ドライバ出力 |

> ⚠️⚠️ **配線色の罠: 「黒＝グランド」と読まないこと。**
> この製品では **黒はエンコーダ側の GND** であり、**モータ電源−は白**である。
> 取り違えて 12V 系をエンコーダ対（青／黒）へ入れると**エンコーダが即座に破壊される。**
> **§10.2 の E-1 より前に、テスターで色と系統の対応を確認する。**

> ⚠️ **黄と緑のどちらが A 相かは仕様に記載がない。** 実測で決める
> （→ §11 #16。**速度PIDの正帰還を防ぐため必須**）。
> 赤と白を入れ替えると回転方向が反転する（メーカー記載）。

- 商品仕様ではエンコーダ電源は **3.3V / 5V 対応**。
- 5V の方が信号安定性に優れる可能性はあるが、**5V の出力信号を ESP32 GPIO へ直接入力しない**。
- 3.3V で問題（カウント抜け・ノイズ）が出た場合のみ、**5V エンコーダ電源 ＋ レベルシフタ**を検討する。

## 8. 電源系統

### 8.1 構成図

```
3S LiPo (11.1V nominal / 12.6V full)
  |
 XT60
  |
 10A Fuse   ← バッテリーにできるだけ近い位置
  |
 Main Power Bus
  |
  +-- Motor Driver 1 (AE-TB67H450) -> Motor 1
  |
  +-- Motor Driver 2 (AE-TB67H450) -> Motor 2
  |
  +-- Motor Driver 3 (AE-TB67H450) -> Motor 3
  |
  +-- BP5293-50 -> 5V -> ESP32 / logic
```

- モータは **3S LiPo からモータドライバへ直接供給**する（降圧を挟まない）。
- ESP32 DevKit 側で必要に応じて 5V → 3.3V へ変換する。

### 8.2 バッテリ

| 項目 | 値 |
|---|---|
| 商品コード | BTLIPO1500mA3S35CXT60*C |
| 商品名 | BTLIPO 1500mA 3S 35C XT60電源コネクター |
| 構成 | 3S LiPo |
| 公称電圧 | 11.1V |
| 満充電電圧 | 12.6V |
| 容量 | 1500 mAh |
| C レート | 35C |
| コネクタ | XT60 |
| 数量 | 1 |

> ⚠️ **1500mAh は容量であって最大出力電流ではない。**
> 35C の公称値からの理論上の放電能力は 1.5Ah × 35 = **52.5A** だが、
> **C値を実使用上の保証最大電流として扱わないこと。**

### 8.3 メインヒューズ

- **10A ヒューズ ×1**（＋ヒューズホルダ）。**バッテリー XT60 直後、できるだけバッテリーに近い位置**へ配置する。

**10A とした理由**:
- JGB37-520 のストール電流 約2.3A × 3 = **約6.9A**、さらに制御回路分の電流が加わる。
- そのため **5A ヒューズでは通常の急加速でも不要動作する可能性がある**。

**位置付け**: 10A は「モータの通常運転電流を制限するため」のものでは**ない**。

- 短絡
- 配線事故
- 電源バスの重大故障

から **LiPo および配線を保護するメイン安全ヒューズ**である。
**モータ個別のロック保護は、エンコーダ＋ソフトウェアで行う**（§5）。

### 8.4 5V DC/DC

- ROHM **BP5293-50** ×1。3S LiPo → 5V 系を生成し、ESP32 / ロジックへ供給。

### 8.5 ノイズ対策部品

| 部品 | 使い方 |
|---|---|
| 0.1µF / 50V X7R セラミックコンデンサ | **各モータ端子の直近に1個ずつ**配置（モータノイズ対策） |
| Rubycon ZLH 1000µF / 35V ×2 | **モータドライバ付近**に配置。必要に応じて2個を分散配置 |

## 9. LiPo 電圧監視

### 9.1 分圧回路

100kΩ / 27kΩ / 0.1µF を使用する。

```
Battery+
  |
 100kΩ
  |
  +------ ESP32 ADC1 (+ 0.1µF → GND)
  |
 27kΩ
  |
 GND
```

- 分圧比 = 27 / (100 + 27) ≈ **0.2126**
  - 12.6V（満充電）→ 約 **2.68V**
  - 11.1V（公称）→ 約 **2.36V**
  - 9.0V（3.0V/セル）→ 約 **1.91V**
- **12.6V 入力時でも ESP32 ADC 電圧が安全範囲（3.3V 未満）に収まる**ことを設計上の条件とする。
- ADC 入力点から GND へ **0.1µF** を追加（ノイズ・サンプリング安定化）。
- **ADC1 系 GPIO を使用**し、Wi-Fi / ESP-NOW 使用時との競合を避ける。
- 実装後は**テスターでバッテリー実電圧を測定し、ADC変換係数をキャリブレーションする**。
  ESP32 の ADC は素の値が非線形かつ個体差があるため、計算値をそのまま信用しない。

> ⚠️ 高い分圧抵抗値（合成 約21kΩ）は ESP32 ADC のサンプリングに影響し得る。
> 0.1µF で緩和する想定だが、読み値が暴れる場合は複数回平均・サンプリング時間の調整で対処する（実機確認事項）。

### 9.2 低電圧保護

ESP32 ソフトウェアに LiPo 監視を実装する。

- **固定閾値を絶対仕様にせず、設定可能なパラメータとする。**
- 3S LiPo のため、**セル電圧が危険な領域まで低下する前**に以下を行う:
  1. **warning**（LED / ログ / 送信）
  2. **motor output stop**
- モータ急加速による**一時的な電圧降下で誤停止しない**よう、以下を使用する:
  - 移動平均
  - 時間判定（一定時間継続して閾値以下）
  - ヒステリシス（復帰閾値を停止閾値より高く）

具体的な閾値は M2 の実測電圧降下データ（§11）を見てから決める（→ [OQ-14](./open-questions.md#c-電源安全)）。

### 9.3 満充電 12.6V 対策

モータの公称電圧は 12V、3S LiPo の満充電は 12.6V。必要なら PWM 上限を設定する。

```
PWM_MAX = min(1.0, 12.0 / measured_battery_voltage)
```

- 例: 実測 12.6V のとき PWM_MAX ≈ 0.952
- **バッテリー電圧を考慮した上限設定を「可能にする」**のが要件であり、
  この式を固定仕様として決め打ちしない。**実機試験結果を優先する。**

## 10. 制御メモ

- **逆運動学（3輪オムニ）**: 目標並進速度 (vx, vy) と回転 ω から各輪速度を算出。
  w1, w2, w3 = 各輪の接線方向単位ベクトルと (vx, vy) の内積 ＋ ω·R。3輪120°配置の標準式。
- **制御ループ**: エンコーダPID（各輪速度制御）→ 上位で目標座標への位置制御。
- **ESP32リソース**: PCNTユニット3つ（エンコーダ）＋ LEDC（3モータ分の PWM / 方向）＋ 目標座標の受信。
  負荷が厳しければ制御を FreeRTOS タスク分離、または駆動用に別MCU（RP2040等）を検討。
  ⚠️ **受信方式は未確定**（→ [OQ-29](./open-questions.md#f-通信)）。固定側は Raspberry Pi 4 のため、
  **ESP-NOW を Pi から直接使える前提にしない**（[development-environment.md §9.2](./development-environment.md#92-通信方式候補を残す)）。
  受信するのは目標座標・到達時刻等の**小さなデータのみ**で、画像・Depth フレームは受信しない。
- **安全系の実装優先度**:
  - **M2a（手動テレオペ＝初通電走行）より前**:
    ①モータロック保護（§5）→ ②LiPo低電圧保護（§9.2）→ ③PWM上限（§9.3）
    → ④**指令ウォッチドッグ**（一定時間 指令が更新されなければ出力停止）
  - **M3（予測との結合）より前**:
    ④の**入力元を受信メッセージへ差し替える**（＝ [FR-10 通信途絶フェイルセーフ](./requirements.md#2-機能要件fr)）
    → ⑤**動作領域制限／ジオフェンス**（[FR-11](./requirements.md#2-機能要件fr)）

  > ⚠️ ①〜③は**移動体が自分の異常を検出する**保護であり、
  > 「外部から誤った指令が届く」「指令が届かなくなる」ことは検出できない。
  > **M2a のテレオペは、外部からの指令で機体が走る最初の段階**であり、この時点ですでに④が要る。
  > ④無しでテレオペを作ると、**コントローラの電池切れ・圏外・BT切断の瞬間に最後の入力で走り続ける。**
  > ⑤が無いと、M3 で誤検出・予測発散がそのまま暴走になる。
  > **M2a/M2b の保護が効いているからといって M3 に進まない。**

  - **④の実装メモ**: 指令の受信ハンドラで最終更新時刻を記録し、**制御ループ側で経過時間を判定する。**
    「指令が来たら動く」だけの実装だと、**送信が止まった瞬間に最後の指令で走り続ける**。
    - **M2a**: 指令元はコントローラ。**デッドマン解放**と**接続断**の両方で停止すること。
    - **M3**: 指令元を固定側からの受信メッセージへ差し替える。**判定ロジックは同一のものを使う。**
    - この差し替えを成立させるため、④は「コントローラ固有の処理」ではなく
      **「最後に有効な指令を受けてからの経過時間」だけを見る形**で実装する。
    - タイムアウト値は未確定（→ [OQ-18](./open-questions.md#d-移動体制御テレオペ)）。**M2a で実測して決め、M3 の初期値の根拠にする。**
  - **④を M2a で先に作る理由**: FR-10 が守るべき状況（固定側の停止・通信断）は、
    M3 で意図的に再現しにくく、しかも**失敗すると機体が暴走する**。
    テレオペなら**コントローラの電源を切るだけ**で同じ経路を発火試験できる。
  - **⑤の実装メモ**: 受信した目標座標を、許容領域へクランプするか破棄する。
    オドメトリ（FR-6）にドリフトがあると領域判定自体がずれる点に注意。

### 10.1 手動テレオペ（M2a）の実装方針

[FR-13](./requirements.md#2-機能要件fr) の実現方針。**開発用の道具であり、完成品の機能ではない。**

#### 10.1.1 接続方式

**第一候補: DualSense（PS5）→ Bluetooth Classic → 移動体 ESP32 に直結。**

| 案 | 評価 |
|---|---|
| **コントローラ → BT → ESP32 直結** | **推奨。** PC も、未確定の Pi→ESP32 通信方式（[development-environment.md §9.2](./development-environment.md#92-通信方式候補を残す)）も切り分けの輪に入らない。**足回り単体を裸で検証できる** |
| コントローラ → PC → USB Serial → ESP32 | 有線のため機体を走らせられない。**M2a-0（台上）だけなら十分** |
| コントローラ → PC → Wi-Fi UDP → ESP32 | **M3 直前に別途行う価値あり**（通信経路そのものの事前検証）。ブリングアップ段階で混ぜると切り分け対象が増える |

- ESP32 DevKit（ESP32-WROOM）は **Bluetooth Classic** を持つため、HID over BT Classic の
  DualSense を扱える見込み。ライブラリは Bluepad32（BTstack ベース）等が候補。
- ⚠️ **実機動作は未検証**（ペアリング手順・再接続挙動・入力レイテンシ・Flash/RAM 消費）→ [OQ-16](./open-questions.md#d-移動体制御テレオペ)。
  動作しない場合は上表の代替案へ落とす。**この判断のために M2a-0 を台上で行う。**

#### 10.1.2 テレオペ用ファームウェアは分離する

> 排他の具体的な実現方法（ビルドフラグ・コンポーネント allowlist 等）は `drivetrain-core` 実装時に確定した
> → [decisions.md D-11](./decisions.md#d-11-テレオペ用と本番用ファームウェアの排他方法を確定した-oq-21-決着)

**BT スタックを M3 の本番ファームウェアへ持ち込まない。**

- 理由: ESP32 の BT Classic と Wi-Fi は **2.4GHz を time-share** するため、両方を同時に使うと
  制御ループにジッタが乗る。M3 では Wi-Fi 系の通信を使う可能性がある（§9.2）。
- したがって **テレオペは専用ビルド**とし、本番ファームと**排他**にする（ビルドフラグ等）。
- ただし**下位層は共有する**。分離するのは最上位の指令生成だけ。

```
[パッド入力 → (vx, vy, ω)]   ← テレオペ専用。捨てても惜しくない層
[目標座標 → (vx, vy, ω)]     ← M3 の本番経路。ここで差し替わる
              |
              v
   逆運動学（3輪120°）          ┐
   速度PID / エンコーダ読み      │ 本番と完全に共有する。
   PWM・方向出力                │ **テレオペで検証した時点で M2b・M3 の分も検証済みになる**
   保護①〜④                    ┘
```

> **重要**: この構造にすると、テレオペで書くコードのうち**捨てになるのは最上段だけ**であり、
> 大半は M2b・M3 でそのまま使う。テレオペは寄り道ではなく本線の一部である。

#### 10.1.3 入力マッピングと運転上の制約

| 項目 | 方針 |
|---|---|
| 左スティック | 並進 (vx, vy) |
| 右スティック X | 回転 ω |
| **デッドマン** | L2 等を**押している間だけ**モータ出力を許可。離す＝即停止（**必須**） |
| 輪単体テスト | D-pad で対象輪を選択（M2a-0 用） |
| **速度スケール上限** | 初期は **30% 程度に絞る**。段階的に上げる |
| デッドゾーン / 入力カーブ | スティック中立付近の不感帯と指数カーブを設ける（値は M2a で調整 → [OQ-17](./open-questions.md#d-移動体制御テレオペ)） |
| 異常通知（任意） | モータロック検出時にコントローラを**振動**させる。安価で分かりやすい |

> ⚠️ **デッドマンも接続断停止も「安全装置」ではなく「運転操作」である。**
> どちらも無線に依存するため、無線が落ちる状況＝まさに暴走しうる状況では機能しない可能性がある。
> [requirements.md M3](./requirements.md#8-段階的開発マイルストーン) が要求する
> **物理的な非常停止手段を、テレオペで代替しない。**
> この線引きは [original-features.md §4.3](./original-features.md#43-非常停止をブラウザに持たせない)
> （Wi-Fi 依存の停止を安全装置にしない）と同じ理屈である。

## 10.2 M2a-0 の前に必ず行う電気系ブリングアップ（MUST）

⚠️ **順序を入れ替えない。1段ごとに未知を1つだけ増やすための順序である。**
⚠️ **E-1 を飛ばして LiPo で初通電しない。**

| 段 | 内容 | 電源 | 合格条件 |
|---|---|---|---|
| **E-0 配線色の確認** | ⚠️ **通電前に**テスターで色と系統の対応を確認する（§7）。**黒＝エンコーダ GND、モータ電源−＝白**。「黒＝グランド」と読まない | 無通電 | 6線の系統がモータ対（赤／白）とエンコーダ対（青／黒／黄／緑）に正しく分かれている。⚠️ **ここを誤ると次段で 12V がエンコーダへ入り破壊される** |
| **E-1 導通・短絡確認** | **電流制限をかけた安定化電源**で配線系へ通電する。**LiPo を挿さない** | 安定化電源 12V ／ 電流制限（初期 0.3A 程度から） | 消費電流が想定内。発熱・異臭が無い。5V 系（BP5293-50 出力）が規定電圧を出す |
| **E-2 モータ単体の回転方向確認** | モータを**ドライバを介さず**安定化電源へ直結し、極性を入れ替えて回転方向とハーネスの対応を確認する | 安定化電源（電流制限） | 3個とも回る。**無負荷電流が3個で揃う**（個体差の外れ値をここで発見する） |
| **E-3 可変抵抗によるドライバ動作確認** | **可変抵抗**でデューティを連続的に変えながら、ドライバ経由でモータを回す。**速度PIDを閉じない開ループ**で行う | 安定化電源（電流制限） | 全域で滑らかに加減速する。ドライバの発熱を確認（#9 の予備確認） |
| **E-4 DualSense（PS5 コントローラ）の疎通確認** | Bluepad32 経由で入力が届くことを確認する。⚠️ **モータを繋がない状態**（ログ出力のみ）で先に行う | USB 給電で可 | ペアリング・再接続・入力レイテンシが実用範囲（→ OQ-16 の判断材料）。**デッドマン解放で入力がゼロになる** |

> ⚠️ **E-3 の注意**: AE-TB67H450 の入力は**デジタル／PWM** であり、可変抵抗のアナログ電圧を
> 直接入れても回らない。可変抵抗は **ESP32 の ADC1（LiPo 電圧監視とは別チャンネル）で読み、
> LEDC の PWM デューティへ写す最小ファーム**と組み合わせる（またはサーボテスタ等の PWM 源を使う）。
> **この最小ファームは PCNT も PID も使わない。** そうすることで E-3 の切り分け対象を
> 「ドライバ＋モータ」だけに保てる。

> **E-1〜E-4 は整備スタンドが無くても実施できる**（モータ単体・机上・モータ非接続）。
> **§11 #15 以降で機体へ載せる時点から整備スタンドが必須**になる。

## 12. M2 で性能不足だった場合の調査順序

性能不足でも、**すぐに高価なモータへ交換しない。** 以下の順に調査する。

1. **ホイールスリップ**（グリップ・荷重配分）
2. **LiPo 電圧降下**（配線抵抗・コネクタ・容量）
3. **PWM / PID 設定**（立ち上がり、飽和、積分項）
4. **車体上部重量**（軽量化）
5. **重心位置**（重量物を最下部へ）
6. **フレーム剛性**
7. **投擲レイアウトと必要横移動量**（待機位置・投擲方向の見直し＝システム設計の一部）
8. 必要に応じて**バッテリー容量**
9. **最後に**モータアップグレード

手持ちの **60mm オムニホイール／6mm ハブ（Nexus 14145 / 18020 相当品）は可能な限り流用する**
（6mm Dシャフト互換を維持する範囲でモータを選ぶ）。
