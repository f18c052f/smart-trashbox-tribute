# 駆動系 詳細仕様 v0.2（3輪オムニ・シャシー自作）

要件: [requirements.md](./requirements.md) / 部品表: [bom.md](./bom.md) / 開発環境: [development-environment.md](./development-environment.md)

> **v0.1 からの方針転換**: 「最高速度 1.5 m/s を満たすこと」を合否条件にしていたが、本プロジェクトの目的は
> **「落下地点を予測し、残された時間内にキャッチ可能範囲へ到達すること」**であって指定速度の達成ではない。
> よって評価軸を **最高速度単独 → 短時間移動性能（0.4 / 0.6 / 0.9 秒で何 m 動けるか）** に変更した。
> 旧数値（1.5 m/s、2〜3 m/s²、3〜4 kg）は**参考値・過去の設計目標**として残すが、合否条件として扱わない。
> 旧構成（100mm ホイール / 330RPM 前提の速度計算 / Pololu #1443 / BTS7960）は標準構成から外し、
> 巻末「[旧案アーカイブ](#旧案アーカイブ比較検討の履歴標準構成ではない)」に経緯として保存する。

## 1. 方式（確定）

| 項目 | 内容 |
|---|---|
| 駆動方式 | **3輪オムニ・120°配置**（確定） |
| ホイール | Nexus **14145** 60mm ダブルオムニ ×3 |
| ハブ | Nexus **18020** 6mm ハブ ×3 |
| モータ | TOPINCN **JGB37-520** 12V / 530RPM / エンコーダ付 ×3 |
| モータドライバ | 秋月電子 **AE-TB67H450** ×3（1モータ1台） |
| バッテリ | 3S LiPo 1500mAh 35C XT60 |
| MCU | ESP32 DevKit（通信と共用） |
| フレーム | 3Dプリント駆動ベース（中央プレート＋モータ取付部3箇所のモジュラー構造） |

**3輪オムニを選ぶ理由**（v0.1から不変）: 円形ゴミ箱は機体の向き維持が不要なのでメカナムの利点が無効。
オムニはモータ力を無駄なく並進に使えて速度・加速で有利。3モータで軽量・安価・制御単純。3点接地でゴミ落下時の重心移動にも強い。

## 2. 使用環境（初期バージョン）

- **屋内**、**平坦な床**（フローリング等を想定）
- **段差越えは要求しない**
- **厚いカーペット走行は要求しない**

> ⚠️ 60mm ホイールを採用したため**最低地上高が小さい**。これは上記の使用環境を前提とした割り切りであり、
> 機構設計では「フレーム下面・ボルト頭・ブラケット・配線が床に接触しないこと」を必ず確認する（→ §6）。

## 3. モータ仕様（JGB37-520）

商品仕様（出品情報より転記。実測値ではない）:

| 項目 | 値 |
|---|---|
| 電圧 | DC 12V |
| 無負荷回転数 | 530 RPM |
| 減速比 | 約 19:1 |
| 定格回転数 | 約 407 RPM |
| 定格トルク | 約 2.2 kgf·cm |
| 最大トルク | 約 3.1 kgf·cm |
| ストール電流 | 約 2.3 A |
| シャフト | 6mm D カット |
| 回転方向 | CW / CCW |
| エンコーダ | ホールエンコーダ、電源 3.3V / 5V、基本分解能 11 PPR |
| 付属品 | 金属モータブラケット、取付ネジ |

### 3.1 60mm ホイールでの理論周速

- 60mm ホイール円周 = π × 0.060 = **0.1885 m/回転**
- 無負荷 530 RPM → 530 / 60 × 0.1885 ≈ **1.66 m/s**
- 定格 407 RPM → 407 / 60 × 0.1885 ≈ **1.28 m/s**（参考）

> ⚠️ **これらは無負荷／定格の理論値であり、実車速度を保証するものではない。**
> 実車では車体質量・転がり抵抗・ホイールスリップ・バッテリー電圧降下・ドライバ損失により低下する。
> 実車速度は M2（[requirements.md §8](./requirements.md#8-段階的開発マイルストーン)）で**実測**する。

### 3.2 エンコーダ分解能（固定値をハードコードしないこと）

- 目安: 11 PPR × 減速比 約19 ≈ **209 pulse / 出力軸1回転**
- ただし実際の counts/rev は以下で変わる:
  - A/B相のカウント方法（A相のみ / A・B両相 / 4逓倍）
  - 立上りのみカウントか、立上り＋立下りか
  - 実ギア比（「約19:1」は公称。実際は非整数比のことが多い）
  - ESP32 側のカウント方式（PCNT の設定）

→ **M2 でホイールを実際に1回転させ、`ENCODER_COUNTS_PER_WHEEL_REV` を実測・校正する。**
根拠のない固定値をコードに埋め込まない。

## 4. モータドライバ AE-TB67H450

- 秋月電子 AE-TB67H450 ×3。**1モータにつき1台**使用。
- 位置付け: **低価格な試作1号機用**。将来モータを変更する際はドライバも交換できるよう、
  基板トレイ・配線・取付穴は**ドライバ交換を前提**とした構造にする。
- ⚠️ JGB37-520 のストール電流 約2.3A は **AE-TB67H450 の能力に比較的近い**。
  したがって **「モータを長時間ストールさせないこと」を重要な保護要件**とする（→ §5）。
  ドライバの発熱は M2 で実測する（→ §11）。

## 5. モータロック保護（ソフトウェア）

**ハードウェアヒューズだけでモータロックを保護しない。** メインヒューズ（§8）は短絡・配線事故用であり、
1モータのストール（約2.3A）では溶断しない。ESP32 側でソフトウェア保護を実装する。

判定ロジック（例）:

```
if (PWM指令が高い) && (エンコーダ速度 ≈ 0) && (その状態が T ms 継続)
    → 該当モータの出力を停止
```

- 初期値の目安: **T = 100〜200 ms 程度**
- ただし**実機試験で調整できるパラメータ**とし、固定仕様にしない
- 復帰条件（自動復帰 / 手動リセット）は M2 の挙動を見て決める（未確定）

## 6. 機構設計

### 6.1 付属金属ブラケットを利用する（標準案）

JGB37-520 セットには**金属モータブラケットが付属**する。
よって**モータ本体を3Dプリント部品で直接クランプする設計は標準案としない。**

```
JGB37-520
   ↓
付属 金属ブラケット
   ↓
3Dプリント 駆動ベース
```

メリット:
- モータ固定剛性の向上
- モータ位置決めが容易
- FDM部品への応力集中を減らせる
- CAD設計が単純になる
- モータ交換が容易

3Dプリントベース側は、**ブラケット固定穴を長穴（スロット）化**するなどして多少の寸法差を吸収できる設計とする。

> ⚠️ **CADの最終穴寸法は、モータおよびブラケット到着後に現物をノギスで測定して確定する。**
> 現時点で穴ピッチ等を数値で確定させない。

### 6.2 3Dプリント範囲

ゴミ箱本体まで全面3Dプリントする構成は**標準案から外す**（重量・造形時間・剛性のいずれも不利）。

推奨構成:

| 部位 | 方針 |
|---|---|
| ゴミ箱本体 | **市販の軽量PP製ゴミ箱**を利用 |
| 駆動ベース | 3Dプリント（中央プレート＋3つのモータ取付部のモジュラー構造） |
| ゴミ箱固定アダプタ | 3Dプリント |
| バッテリートレイ | 3Dプリント（最下部配置） |
| 基板トレイ | 3Dプリント |
| ワイドリム / 漏斗 | 必要に応じて3Dプリント（FR-7） |

- **金属切削加工は要求しない**（CON-1）。

### 6.3 最低地上高

- 60mm ホイール → **車軸中心高さ 約30mm**
- モータ径 37mm（半径 18.5mm）。モータ軸をホイール軸と同軸に配置した場合、
  モータ胴体下面は床から **約 11.5mm**（＝30 − 18.5）。**余裕は小さい。**
- 以下が床に接触しないことを確認する:
  - 付属ブラケット
  - ボルト頭・ナット
  - フレーム（駆動ベース）下面
  - 配線

### 6.4 CAD着手手順

モータ到着後、以下を**仮組みして実寸を測定してから** CAD を完成させる。

1. モータ（JGB37-520）
2. 付属金属ブラケット
3. Nexus 18020 ハブ
4. Nexus 14145 ホイール

測定項目 → §11「実機で確認する事項」。

## 7. エンコーダ接続

ESP32 の GPIO は 3.3V 系のため、**初期構成ではエンコーダも 3.3V 駆動**する。

| エンコーダ側 | 接続先 |
|---|---|
| VCC | **3.3V** |
| GND | GND |
| A相 | ESP32 GPIO |
| B相 | ESP32 GPIO |

- 商品仕様ではエンコーダ電源は **3.3V / 5V 対応**。
- 5V の方が信号安定性に優れる可能性はあるが、**5V の出力信号を ESP32 GPIO へ直接入力しない**。
- 3.3V で問題（カウント抜け・ノイズ）が出た場合のみ、**5V エンコーダ電源 ＋ レベルシフタ**を検討する。

## 8. 電源系統

### 8.1 構成図

```
3S LiPo (11.1V nominal / 12.6V full)
  |
 XT60
  |
 10A Fuse   ← バッテリーにできるだけ近い位置
  |
 Main Power Bus
  |
  +-- Motor Driver 1 (AE-TB67H450) -> Motor 1
  |
  +-- Motor Driver 2 (AE-TB67H450) -> Motor 2
  |
  +-- Motor Driver 3 (AE-TB67H450) -> Motor 3
  |
  +-- BP5293-50 -> 5V -> ESP32 / logic
```

- モータは **3S LiPo からモータドライバへ直接供給**する（降圧を挟まない）。
- ESP32 DevKit 側で必要に応じて 5V → 3.3V へ変換する。

### 8.2 バッテリ

| 項目 | 値 |
|---|---|
| 商品コード | BTLIPO1500mA3S35CXT60*C |
| 商品名 | BTLIPO 1500mA 3S 35C XT60電源コネクター |
| 構成 | 3S LiPo |
| 公称電圧 | 11.1V |
| 満充電電圧 | 12.6V |
| 容量 | 1500 mAh |
| C レート | 35C |
| コネクタ | XT60 |
| 数量 | 1 |

> ⚠️ **1500mAh は容量であって最大出力電流ではない。**
> 35C の公称値からの理論上の放電能力は 1.5Ah × 35 = **52.5A** だが、
> **C値を実使用上の保証最大電流として扱わないこと。**

### 8.3 メインヒューズ

- **10A ヒューズ ×1**（＋ヒューズホルダ）。**バッテリー XT60 直後、できるだけバッテリーに近い位置**へ配置する。

**10A とした理由**:
- JGB37-520 のストール電流 約2.3A × 3 = **約6.9A**、さらに制御回路分の電流が加わる。
- そのため **5A ヒューズでは通常の急加速でも不要動作する可能性がある**。

**位置付け**: 10A は「モータの通常運転電流を制限するため」のものでは**ない**。

- 短絡
- 配線事故
- 電源バスの重大故障

から **LiPo および配線を保護するメイン安全ヒューズ**である。
**モータ個別のロック保護は、エンコーダ＋ソフトウェアで行う**（§5）。

### 8.4 5V DC/DC

- ROHM **BP5293-50** ×1。3S LiPo → 5V 系を生成し、ESP32 / ロジックへ供給。

### 8.5 ノイズ対策部品

| 部品 | 使い方 |
|---|---|
| 0.1µF / 50V X7R セラミックコンデンサ | **各モータ端子の直近に1個ずつ**配置（モータノイズ対策） |
| Rubycon ZLH 1000µF / 35V ×2 | **モータドライバ付近**に配置。必要に応じて2個を分散配置 |

## 9. LiPo 電圧監視

### 9.1 分圧回路

100kΩ / 27kΩ / 0.1µF を使用する。

```
Battery+
  |
 100kΩ
  |
  +------ ESP32 ADC1 (+ 0.1µF → GND)
  |
 27kΩ
  |
 GND
```

- 分圧比 = 27 / (100 + 27) ≈ **0.2126**
  - 12.6V（満充電）→ 約 **2.68V**
  - 11.1V（公称）→ 約 **2.36V**
  - 9.0V（3.0V/セル）→ 約 **1.91V**
- **12.6V 入力時でも ESP32 ADC 電圧が安全範囲（3.3V 未満）に収まる**ことを設計上の条件とする。
- ADC 入力点から GND へ **0.1µF** を追加（ノイズ・サンプリング安定化）。
- **ADC1 系 GPIO を使用**し、Wi-Fi / ESP-NOW 使用時との競合を避ける。
- 実装後は**テスターでバッテリー実電圧を測定し、ADC変換係数をキャリブレーションする**。
  ESP32 の ADC は素の値が非線形かつ個体差があるため、計算値をそのまま信用しない。

> ⚠️ 高い分圧抵抗値（合成 約21kΩ）は ESP32 ADC のサンプリングに影響し得る。
> 0.1µF で緩和する想定だが、読み値が暴れる場合は複数回平均・サンプリング時間の調整で対処する（実機確認事項）。

### 9.2 低電圧保護

ESP32 ソフトウェアに LiPo 監視を実装する。

- **固定閾値を絶対仕様にせず、設定可能なパラメータとする。**
- 3S LiPo のため、**セル電圧が危険な領域まで低下する前**に以下を行う:
  1. **warning**（LED / ログ / 送信）
  2. **motor output stop**
- モータ急加速による**一時的な電圧降下で誤停止しない**よう、以下を使用する:
  - 移動平均
  - 時間判定（一定時間継続して閾値以下）
  - ヒステリシス（復帰閾値を停止閾値より高く）

具体的な閾値は M2 の実測電圧降下データ（§11）を見てから決める。**現時点では未確定。**

### 9.3 満充電 12.6V 対策

モータの公称電圧は 12V、3S LiPo の満充電は 12.6V。必要なら PWM 上限を設定する。

```
PWM_MAX = min(1.0, 12.0 / measured_battery_voltage)
```

- 例: 実測 12.6V のとき PWM_MAX ≈ 0.952
- **バッテリー電圧を考慮した上限設定を「可能にする」**のが要件であり、
  この式を固定仕様として決め打ちしない。**実機試験結果を優先する。**

## 10. 制御メモ

- **逆運動学（3輪オムニ）**: 目標並進速度 (vx, vy) と回転 ω から各輪速度を算出。
  w1, w2, w3 = 各輪の接線方向単位ベクトルと (vx, vy) の内積 ＋ ω·R。3輪120°配置の標準式。
- **制御ループ**: エンコーダPID（各輪速度制御）→ 上位で目標座標への位置制御。
- **ESP32リソース**: PCNTユニット3つ（エンコーダ）＋ LEDC（3モータ分の PWM / 方向）＋ 目標座標の受信。
  負荷が厳しければ制御を FreeRTOS タスク分離、または駆動用に別MCU（RP2040等）を検討。
  ⚠️ **受信方式は未確定**（ESP-NOW / UDP / Serial 等）。固定側は Raspberry Pi 4 のため、
  **ESP-NOW を Pi から直接使える前提にしない**（[development-environment.md §9.2](./development-environment.md#92-通信方式候補を残す)）。
  受信するのは目標座標・到達時刻等の**小さなデータのみ**で、画像・Depth フレームは受信しない。
- **安全系の実装優先度**:
  - **M2（単体走行試験）より前**: ①モータロック保護（§5）→ ②LiPo低電圧保護（§9.2）→ ③PWM上限（§9.3）
  - **M3（予測との結合）より前**: ④**通信途絶フェイルセーフ**（[FR-10](./requirements.md#2-機能要件fr)）
    → ⑤**動作領域制限／ジオフェンス**（[FR-11](./requirements.md#2-機能要件fr)）

  > ⚠️ ①〜③は**移動体が自分の異常を検出する**保護であり、
  > 「固定側から誤った目標座標が届く」「目標座標が届かなくなる」ことは検出できない。
  > M3 では初めて外部からの指令で機体が走るため、④⑤が無いと
  > **通信断や誤検出がそのまま暴走になる**。M2 の保護が効いているからといって M3 に進まない。

  - **④の実装メモ**: 受信ハンドラで最終受信時刻を更新し、制御ループ側で経過時間を判定する。
    「受信が来たら動く」だけの実装だと、**送信が止まった瞬間に最後の指令で走り続ける**。
    タイムアウト値は未確定（§13）。
  - **⑤の実装メモ**: 受信した目標座標を、許容領域へクランプするか破棄する。
    オドメトリ（FR-6）にドリフトがあると領域判定自体がずれる点に注意。

- エンコーダ信号品質不足 → 5V エンコーダ電源 ＋ レベルシフタ
- ドライバ能力不足 → より高電流のドライバへ交換（交換前提の構造にしてある）
- 制御負荷過大 → 駆動制御を別MCU（RP2040等）へ分離
- **最終手段**: モータのアップグレード（→ §12 の改善順序を全て試した後）

---

## 12. M2 で性能不足だった場合の調査順序

性能不足でも、**すぐに高価なモータへ交換しない。** 以下の順に調査する。

1. **ホイールスリップ**（グリップ・荷重配分）
2. **LiPo 電圧降下**（配線抵抗・コネクタ・容量）
3. **PWM / PID 設定**（立ち上がり、飽和、積分項）
4. **車体上部重量**（軽量化）
5. **重心位置**（重量物を最下部へ）
6. **フレーム剛性**
7. **投擲レイアウトと必要横移動量**（待機位置・投擲方向の見直し＝システム設計の一部）
8. 必要に応じて**バッテリー容量**
9. **最後に**モータアップグレード

手持ちの **Nexus 14145 / Nexus 18020 は可能な限り流用する**（6mm Dシャフト互換を維持する範囲でモータを選ぶ）。

## 旧案アーカイブ（比較検討の履歴。**標準構成ではない**）

以下は v0.1 の内容。**いずれも採用せず**、経緯の記録として残す。

### 旧案: 100mm ホイール構成（採用せず）

- ホイール: Nexus **14049** 100mm ダブルオムニ（ベーシック/プラ）＋6mmハブ ×3
- 100mm ホイール円周 = π × 0.1 = 0.314 m/回転
- モータ **330 RPM** × 100mm → 330/60 × 0.314 ≈ **1.73 m/s（無負荷）**
- **不採用の理由**: 実際に採用したのは 60mm の Nexus 14145。上記の速度計算は現構成には適用されない。

### 旧案: Pololu #1443 を標準モータとする案（採用せず）

- Pololu #1443（30:1 37Dx52L, 350RPM, ストール 8 kgf·cm, 64 CPR, ¥15,000〜18,000）
- 350 RPM × 100mm ホイール → 5.83 × 0.314 ≈ **1.83 m/s（無負荷）**
- オドメトリ: 64 CPR × 30:1 = 1920 カウント/出力軸回転
- **不採用の理由**: 高価。まず安価な JGB37-520 で実測し、§12 の順序で改善してから判断する方針に変更。
  将来のアップグレード候補としては引き続き有効（6mm Dシャフトのためホイール・ハブは流用可）。

### 旧案: BTS7960 ドライバ（採用せず）

- BTS7960（43A, 双方向）×3。「43A ≫ ストール電流」で余裕がある構成だった。
- **不採用の理由**: 試作1号機には過剰。安価な AE-TB67H450 を採用。
  ただし TB67H450 は余裕が小さいため、**ソフトウェアによるロック保護（§5）が必須**という条件付き。

### 旧案: 3S LiPo 2200〜3000mAh（採用せず）

- **不採用の理由**: 実際に採用したのは 1500mAh 35C。容量が不足した場合は §12 の手順8で見直す。

### 旧: 設計目標値（**参考値**。合否条件ではない）

| 項目 | 旧目標値 | 現在の扱い |
|---|---|---|
| 最高速度 | ≥ 1.5 m/s（設計最高 ~1.8 m/s） | **参考目標値**。合否条件ではない |
| 加速度 | ~2〜3 m/s² | **参考値**。必須条件ではない（→ [requirements.md NFR-2](./requirements.md#nfr-2-加速安定性)） |
| 車体質量 | ~3〜4 kg | **参考値**。上限を設定しない。設計方針としては 2〜2.5 kg 程度が望ましい |

### 旧: トルク・牽引の試算（100mm ホイール前提。**現構成には未適用**）

- 必要トルク（1輪あたり接地力 ~10N 想定）: 10N × 0.05m（＝100mmホイール半径）= 0.5 N·m ≈ 5 kgf·cm/輪
- 牽引限界: μ≈0.5、mg≈39N（4kg想定）→ 最大牽引 ~20N
- 結論だった「**トルクより牽引が先に限界**＝軽量化とグリップが効く」という定性的知見は現構成でも有効。
- ただし **60mm ホイール（半径0.03m）・JGB37-520（定格2.2 kgf·cm / 最大3.1 kgf·cm）では数値が変わる**ため、
  上記の数値をそのまま現構成に適用しない。**実測（M2）を根拠とする。**
