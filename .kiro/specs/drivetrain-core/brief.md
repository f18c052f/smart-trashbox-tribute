# Brief: drivetrain-core

## Problem

移動体（3輪オムニ）に初めて通電する前に、**書き終えていなければならないコードが仕様として既に確定している。**

`docs/drivetrain-spec.md` §10 と `.kiro/steering/tech.md` 標準2 は、
**M2a（初通電走行）より前に**以下を実装することを要求している。

| 順 | 保護 |
|---|---|
| ① | モータロック保護（エンコーダ速度 ≈ 0 かつ PWM 指令が高い状態が T ms 継続） |
| ② | LiPo 低電圧保護（移動平均・時間判定・ヒステリシス） |
| ③ | PWM 上限（バッテリ電圧を考慮） |
| ④ | 指令ウォッチドッグ（最後に有効な指令を受けてからの経過時間で停止） |

これらは「あとで足す機能」ではない。**④ が無い状態でテレオペを作ると、
コントローラの電池切れ・圏外・BT 切断の瞬間に、機体が最後の入力のまま走り続ける。**

同時に、この層は捨てにならない。`drivetrain-spec.md` §10.1.2 の層構造が示すとおり、
テレオペで検証した時点で **M2b・M3 の分まで検証済みになる**。

## Current State

- `docs/drivetrain-spec.md` に駆動系の設計が詳細に存在する（方式・電源・保護・制御メモ・テレオペ方針）
- **移動体側のコードは1行も存在しない。** リポジトリの `src/` は固定側 Python パッケージ5本のみ
- `src/trajectory_sim/drivetrain.py` に「等方な質点＋加速度上限」の運動モデルが存在するが、
  これは**シミュレータ用の性能モデル**であり、実機の駆動制御ではない。両者は別物である
- `.kiro/steering/structure.md` の Future Code Layout は「実装着手時に改めて決める。
  現時点でディレクトリを作らない」のままで、**実態（`src/` に Python ツリーが存在する）と乖離している**

## Desired Outcome

- 3輪オムニの逆運動学・速度PID・保護①〜④・オドメトリが、**実機を一切使わずホスト上で単体テストできる**
- ESP32 のペリフェラル（PCNT / LEDC / ADC）と Bluetooth が、
  **薄いアダプタ境界の向こう側に隔離されている**
- `teleop-bringup` が着手できる状態、すなわち
  **「実機で潰すべき問題が、配線・符号・実測値だけに絞り込まれている」**状態になる

## Approach

`prediction_core` と同じ作り方を移動体側へ適用する。すなわち **「実機なしで検証できる中核」を先に切り出す。**

- 純ロジックを PlatformIO の `lib/control/` へ置き、`native` 環境（Unity）でホストテストする
- ペリフェラルはポート（インターフェース）として宣言するだけにし、実装は `teleop-bringup` が持つ
- **時刻源を注入する。** ホストに `millis()` / `micros()` は存在しない。
  PID と保護状態機械が現在時刻を自分で取得する設計にすると、この Spec の前提そのものが崩れる

なぜ「テレオペを先に作って動かしながら整える」のではないか:
`requirements.md` M2 が明記するとおり、**組み立て直後に起きるのは性能不足ではなく配線・符号のバグ**であり、
ロジックとハードのどちらが原因かを同時に切り分けるのが最も難しい。**ロジック側を先に確定させる。**

## Scope

- **In**:
  - ファームウェアのプロジェクト骨組み（PlatformIO、3環境: `teleop` / `production` / `native`）と
    ディレクトリ配置の確定（→ OQ-40 のファーム側の決着）
  - 3輪オムニ・120°配置の逆運動学: `(vx, vy, ω)` → 各輪目標速度
  - 順運動学とオドメトリ: 各輪エンコーダカウント → 機体位置・姿勢（FR-6）
  - 各輪の速度PID
  - 保護①〜④の判定ロジックと状態機械（**閾値・タイムアウトはすべてパラメータ**）
  - 時刻源の注入インターフェース
  - 単位系（距離 mm / 時刻 ms）と固定幅整数型の徹底
  - ペリフェラルのポート定義（エンコーダ読み出し / PWM・方向出力 / 電圧読み出し）— **宣言のみ**
  - ホストでの単体テスト一式
- **Out**:
  - ESP32 ペリフェラルの実装コード（PCNT / LEDC / ADC1）→ `teleop-bringup`
  - Bluetooth / Bluepad32 / DualSense → `teleop-bringup`
  - 実機での校正・発火試験 → `teleop-bringup`
  - 定量計測とパラメータの実測 → `m2-motion-validation`
  - 固定側 → 移動体の通信、ジオフェンス（⑤）→ M3（roadmap の Out）

## Boundary Candidates

- **`Arduino.h` / IDF ヘッダを include するか否か** — これがアダプタ境界そのもの。
  境界より下に処理ロジックを置かない
- **指令生成と指令実行の境界** — `(vx, vy, ω)` ＋「その指令が有効になった時刻」。
  テレオペも M3 の本番経路も、この同じ型でここへ入る
- **保護の「判定」と「出力遮断の実行」** — 判定は純ロジック、遮断はアダプタ。
  分離しないと保護をホストでテストできない
- **エンコーダの生カウントと物理量の境界** — `ENCODER_COUNTS_PER_WHEEL_REV` を跨ぐ地点。
  この値は**根拠のない固定値として埋め込まない**（`tech.md` 標準1）

## Out of Boundary

- 実機の性能値（最高速度・加速度）の決定 — 本 Spec は**パラメータの型と検証だけを持ち、値を持たない**
- 保護閾値の具体値（OQ-14 低電圧閾値、OQ-18 ウォッチドッグ timeout、OQ-15 復帰条件）—
  いずれも実測を待って決まる。本 Spec は**設定可能にすることだけ**を担う
- テレオペ固有の入力処理（デッドゾーン、入力カーブ、パッドのボタン割当）

## Upstream / Downstream

- **Upstream**: なし（新規ツリー）。`docs/drivetrain-spec.md` が設計の正
- **Downstream**: `teleop-bringup`（ペリフェラル実装と実機検証）、
  `m2-motion-validation`（定量計測）、および M3 の本番ファームウェア

## Existing Spec Touchpoints

- **Extends**: なし
- **Adjacent**:
  - `trajectory-simulator` — `trajectory_sim.DrivetrainParams`（最高速度・加速度上限・減速度上限・
    制御周期・指令反映遅れ）と**意味論を揃える**。
    `m2-motion-validation` が実測値をここへ戻すため、**単位と定義がずれると翻訳できなくなる**。
    ただし**コードは共有しない**（Python と C++ であり、`tech.md` 標準3 が禁じる二重実装にも当たらない —
    シミュレータの質点モデルと実機の逆運動学は別物である）
  - `prediction-core` — 直接の依存は無いが、**「実行時依存を最小に保ち、実機なしで検証できる中核」
    という作り方の先例**として参照する

## Constraints

技術検証（2026-08-23 実施）で確定・判明した事項。

- **フレームワークは `framework = espidf` + Arduino-as-component をテレオペ／本番の両ビルドで使う。**
  Bluepad32 は `framework = arduino` の `lib_deps` としては導入できず、改造コアとして組み込まれる。
  片方だけ espidf にするとプロジェクトレイアウトが `main/` と `src/` で割れるため、両方を揃える
- **PlatformIO 公式の `platformio/platform-espressif32` は 7.0.1（2024年5月）で凍結**しており、
  Arduino core 2.0.17 / IDF 4.4.7 のまま。Arduino 3.x を使うには **`pioarduino` フォーク**が必要。
  ⚠️ 実質1人規模のプロジェクトのため、**`stable` や `#develop` ではなくリリース zip を pin する**
- **時刻源を注入する。** ホストに `millis()` / `micros()` は無い。
  調査の指摘: *「これがホストテストが実際に機能するかどうかを決める唯一の設計判断」*
- **固定幅整数型を初日から使う**（`int32_t` / `int64_t`）。
  ホストは 64-bit で `long` が 8 バイト、ESP32 は 4 バイト。
  **エンコーダカウンタと PID 積分項のオーバーフロー挙動が、ホストテストで再現されない**
- **`test_build_src` は既定で `no`** のためテストから `src_dir` が見えない。
  純ロジックを `lib/control/` に置き、`native` とファーム両環境からリンクする。
  `test/` は全環境向けにビルドされるので `test_native/` と `test_embedded/` へ分割し `test_filter` で振り分ける
- **チップは classic ESP32 に固定される。** ESP32-S3 / C3 / C6 / H2 は BT Classic を持たず
  DualSense を扱えない。PCNT ユニット数も classic 8 / S3 2 / C3 0。
  **将来 S3 へ乗り換える選択肢は無い**ものとして設計する（`docs/bom.md` #8 は型番未指定 → 明記が要る）
- 単位はプロジェクト規約に従い**距離 mm / 時刻 ms**（`structure.md` Naming Conventions）
- ⚠️ 調査が指摘した「Windows に MSYS2 + MinGW が必要」は**本プロジェクトには該当しない**。
  開発は WSL2 側で行うため gcc は標準で利用できる（`tech.md` Development Environment）

### 新規 OQ 候補

- **BTstack ライセンスの取り扱い** — Bluepad32 本体は Apache-2.0 だが、依存する BTstack は
  「個人的利益のためのみ。商用目的・金銭的利得のためには使用不可」条項付きで**オープンソースではない**。
  趣味プロジェクトとしての使用は問題ないが、**GitHub 公開時にトップレベル LICENSE が
  BT 版ファームまで自由に再利用可能だと誤読させてはいけない。**
  本番ファームは BT を落とすため、encumbrance をテレオペビルドに封じ込めれば本番成果物はクリーンに保てる。
  これは「テレオペFWと本番FWを排他にする」という既存の決定に、
  2.4GHz 共存とは**別の根拠を追加する**
