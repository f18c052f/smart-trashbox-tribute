# Requirements Document

## Project Description (Input)

3輪オムニ移動体の**駆動中核ロジックを、実機に一切通電することなくホスト上で検証できる形で確定させる**。
詳細な背景・スコープ・制約は [brief.md](./brief.md) を正とする。

### 誰の問題か

移動体（3輪オムニ）のファームウェアをこれから初めて書き始める開発者。

- **`teleop-bringup`**: 実機で潰すべき問題を「配線・符号・実測値」だけに絞り込めなければ、
  初通電の場で**ロジックのバグとハードのバグを同時に切り分ける**ことになる。
  `docs/requirements.md` FR-13 が挙げる典型3件（極性逆・エンコーダ A/B 逆・輪番号ずれ）は、
  逆運動学と PID が正しいことを前提にしてはじめて切り分けられる
- **`m2-motion-validation`**: 定量計測は「逆運動学・配線・エンコーダ符号が正しい」ことを暗黙の前提にする。
  この前提を先に固めないと、計測値が性能なのかバグなのか判別できない
- **安全**: `docs/drivetrain-spec.md` §10 と `.kiro/steering/tech.md` 開発標準2 は、
  **M2a（初通電走行）より前に**①モータロック保護 ②LiPo 低電圧保護 ③PWM 上限 ④指令ウォッチドッグ
  を実装することを要求している。**実機に通電する前に書き終えていなければならないコードが、
  既に仕様として確定している**

### 現状

- `docs/drivetrain-spec.md` に駆動系の設計（方式・電源・保護・制御メモ・テレオペ方針）が詳細に存在する
- **移動体側のコードは1行も存在しない。** リポジトリの `src/` は固定側 Python パッケージ5本のみ
- `src/trajectory_sim/drivetrain.py` に「等方な質点＋加速度上限」の運動モデルが存在するが、
  これは**シミュレータ用の性能モデル**であり、実機の駆動制御ではない。両者は別物である
- **④ が無い状態でテレオペを作ると、コントローラの電池切れ・圏外・BT 切断の瞬間に、
  機体が最後の入力のまま走り続ける。** `docs/drivetrain-spec.md` §10 が
  「M2a のテレオペは、外部からの指令で機体が走る最初の段階」であることを根拠に、
  この時点で既に④が要ると明記している
- 保護の具体閾値はいずれも未決である（→ OQ-14 低電圧閾値 / OQ-15 復帰条件 / OQ-18 ウォッチドッグ timeout /
  OQ-22 制御ループ周期）。**実測を待って決まる**
- `.kiro/steering/structure.md` の Future Code Layout は「実装着手時に改めて決める。
  現時点でディレクトリを作らない」のままで、**実態（`src/` に Python ツリーが存在する）と乖離している**
- **ホイール・ハブが未着**のため、機構の現物採寸に依存する作業はクリティカルパスに置けない

### 何が変わるべきか

- 3輪オムニの逆運動学・速度PID・保護①〜④・オドメトリが、**実機を一切使わずホスト上で単体テストできる**
- ESP32 のペリフェラル（エンコーダ読み出し / PWM・方向出力 / 電圧読み出し）と無線が、
  **薄いアダプタ境界の向こう側に隔離されている**
- **時刻源が注入されている。** ホストに `millis()` / `micros()` は存在せず、
  PID と保護状態機械が現在時刻を自分で取得する設計にすると、この Spec の前提そのものが崩れる
- 保護の閾値・タイムアウトが**すべて外から与えられるパラメータ**になっており、
  本 Spec は**値を持たない**
- `teleop-bringup` が着手できる状態、すなわち
  **「実機で潰すべき問題が、配線・符号・実測値だけに絞り込まれている」**状態になる

## 追加入力: 確定済みの方針（A-1〜A-16）

> 本節は Project Description の続きであり、**入力として与えられた確定方針**である。
> 検証可能な形式の要件は下の [`## Requirements`](#requirements) を正とし、
> `A-n` は各要件の**出典参照**として使用する。

### A-1. 「実機なしで検証できる中核」を先に切り出す

`prediction-core` と同じ作り方を移動体側へ適用する。純ロジックを先に確定させ、
ペリフェラルは後段の Spec が実装する。

なぜ「テレオペを先に作って動かしながら整える」のではないか:
`docs/requirements.md` M2 が明記するとおり、**組み立て直後に起きるのは性能不足ではなく配線・符号のバグ**であり、
ロジックとハードのどちらが原因かを同時に切り分けるのが最も難しい。**ロジック側を先に確定させる。**

### A-2. アダプタ境界 ★最重要

**境界は「ペリフェラル／フレームワーク固有のヘッダを include するか否か」そのものである。**
境界より下（アダプタ側）に処理ロジックを置かない。

本 Spec は**ポート（インターフェース）を宣言するだけ**で、実装は `teleop-bringup` が持つ。
必要なポートは以下の3種:

| ポート | 責務 |
|---|---|
| エンコーダ読み出し | 各輪の累積カウントを返す |
| PWM・方向出力 | 各輪の出力指令（大きさと向き）を受け取る |
| 電圧読み出し | バッテリ電圧を返す |

⚠️ **ポートは物理量（累積カウント / バッテリ電圧）を返す契約とする。**
そこへ至る換算（折り返しの桁上げ、分圧比、ADC の非線形補正）は
**本 Spec が純ロジックとして提供し、アダプタはそれを利用する**。
こうしないと、最も壊れやすい算術がアダプタ側に沈んでホストで検証できなくなる。

### A-3. 時刻源を注入する

技術検証の指摘: *「これがホストテストが実際に機能するかどうかを決める唯一の設計判断」*。

- PID と保護状態機械は**現在時刻を自分で取得しない**
- 制御ステップは呼び出し側から駆動され、時刻は引数として渡る

### A-4. 固定幅整数型を初日から使う

ホストは 64-bit で `long` が 8 バイト、ESP32 は 4 バイト。
**エンコーダカウンタと PID 積分項のオーバーフロー挙動が、ホストテストで再現されない。**

### A-5. 単位は 距離 mm / 時刻 ms

`.kiro/steering/structure.md` Naming Conventions の規約に従う。

### A-6. 指令の入力契約

指令は **`(vx, vy, ω)` ＋ その指令が有効になった時刻**である。

テレオペ（パッド入力）も M3 の本番経路（目標座標）も、**この同じ型でここへ入る**。
`docs/drivetrain-spec.md` §10.1.2 の層構造がそのまま境界になる。

指令に加えて、下位層は次の2つの入口を持つ必要がある。
どちらも**上位のマッピング（どのボタンに割り当てるか）は持たない**:

- **出力許可**: 許可されていない間は出力を遮断する。
  テレオペのデッドマン（`docs/drivetrain-spec.md` §10.1.3、「離す＝即停止」は必須）は、
  **この入口へのマッピングとして実現される**
- **輪ごとの目標速度を直接与える入口**: 逆運動学を経由せず1輪だけを回す。
  M2a-0 の輪単体テスト（同 §10.1.3 の D-pad による対象輪選択）が成立するために必要。
  ⚠️ **この入口でも保護①〜④は同一に適用される**

### A-7. 保護①〜④は M2a より前に実装する

これは安全要件であり、**スケジュール都合で順序を入れ替えない**（`.kiro/steering/tech.md` 開発標準2）。

⚠️ ①〜③は**移動体が自分の異常を検出する**保護であり、
「外部から誤った指令が届く」「指令が届かなくなる」ことは検出できない。**だから④が要る。**

### A-8. 保護の「判定」と「出力遮断の実行」を分ける

判定は純ロジック、遮断はアダプタ。**分離しないと保護をホストでテストできない。**

ただし「遮断されるべき状態のとき、出力指令が遮断値になっていること」までは純ロジック側で確定させる。
アダプタは受け取った出力指令をそのまま書き出すだけにする。

### A-9. 閾値・タイムアウトはすべてパラメータ。本 Spec は値を持たない

- OQ-14（LiPo 低電圧保護の閾値）— M2 の実測電圧降下データを見てから決まる
- OQ-15（モータロック保護の復帰条件: 自動 / 手動リセット）— M2a-1 の発火試験の挙動を見て決まる
- OQ-18（指令ウォッチドッグのタイムアウト値）— M2a で実測して決まる
- OQ-22（制御ループ周期。目安 100〜200 Hz）— M2 で決まる

**本 Spec は「設定可能にすること」だけを担う**（`.kiro/steering/tech.md` 開発標準1）。

### A-10. `ENCODER_COUNTS_PER_WHEEL_REV` を根拠のない固定値として埋め込まない

目安は 11 PPR × 減速比 約19 ≈ 209 pulse/出力軸1回転 だが、
A/B 相のカウント方法・逓倍・実ギア比（非整数比のことが多い）・カウント設定で変わる。
**M2a-0 でホイールを実際に1回転させて実測校正する**（`docs/drivetrain-spec.md` §3.2）。

### A-11. エンコーダカウントの累積は本 Spec が持つ

⚠️ **ペリフェラルのハードウェアカウンタは符号付き 16bit（±32767）である。**
桁上げを累積しないと、**「数秒走るとオドメトリが壊れる」形で現れる**。

決定（2026-08-23）:

- **ポート契約は 64bit の累積カウントを返す形にする**（ポートにペリフェラル固有の型を漏らさない）
- **ラップアラウンド検出と桁上げを行う累積器そのものは、本 Spec が純ロジックとして提供する**。
  `teleop-bringup` のアダプタはこれを利用する
- これにより、**最も壊れやすい算術がホストで回帰テストできる**

### A-12. ホスト検証はテスト専用の簡易プラントモデルまで持つ

決定（2026-08-23）:

- drivetrain-core の**テスト側にのみ**簡易な車輪応答モデルを置く
- これにより PID の収束・ロック保護の発火・ウォッチドッグ停止・低電圧ヒステリシスを
  **閉ループで検証できる**
- ⚠️ **プラントモデルの係数は「合否条件ではない仮値」として扱い、本体コードには含めない。**
  ここで得た数値を実機性能の主張に使わない

### A-13. ビルド構成は3つ。テレオペと本番は排他、下位層は共有

```
[パッド入力 → (vx, vy, ω)]   ← テレオペ専用。捨てても惜しくない層（teleop-bringup）
[目標座標 → (vx, vy, ω)]     ← M3 の本番経路。ここで差し替わる
              |
              v
   逆運動学（3輪120°）          ┐
   速度PID / エンコーダ読み      │ 本番と完全に共有する。← 本 Spec の範囲
   PWM・方向出力                │ **テレオペで検証した時点で M2b・M3 の分も検証済みになる**
   保護①〜④                    ┘
```

- 3構成: **テレオペ用 / 本番用 / ホストテスト用**
- **無線スタックを本番用ビルドへ持ち込まない**（2.4GHz の time-share により制御ループにジッタが乗る）
- ⚠️ ホストテスト用構成からは既定でアプリケーション本体のソースが見えないため、
  **純ロジックはライブラリとして分離し、3構成すべてからリンクできる形に置く**

### A-14. チップは classic ESP32 に固定される

ESP32-S3 / C3 / C6 / H2 は BT Classic を持たず DualSense を扱えない。パルスカウンタのユニット数も
classic 8 / S3 2 / C3 0。**将来 S3 へ乗り換える選択肢は無いものとして設計する。**
`docs/bom.md` #8 は型番未指定のため、明記が要る。

### A-15. `DrivetrainParams` と意味論を揃える。コードは共有しない

`trajectory_sim.DrivetrainParams`（最高速度 mm/s・加速度上限 mm/s²・減速度上限 mm/s²・
制御周期 ms・指令反映遅れ ms）と**単位と定義を揃える**。

`m2-motion-validation` が実測値をここへ翻訳して戻すため、**ずれると翻訳できなくなる**
（`.kiro/steering/roadmap.md` Shared seams to watch）。

⚠️ ただし**コードは共有しない**。Python と C++ であり、シミュレータの質点モデルと実機の逆運動学は
別物であるため、`.kiro/steering/tech.md` 開発標準3 が禁じる二重実装には当たらない。

### A-16. 本 Spec で決着させる未決事項

決定（2026-08-23）:

| OQ | 扱い |
|---|---|
| **OQ-40**（リポジトリのディレクトリ構成） | **ファーム側を決着させる。** ⚠️ `.kiro/steering/structure.md` の「現時点でディレクトリを作らない」が実態と合っていないため、**steering の是正まで行う** |
| **OQ-21**（テレオペ用と本番用ファームウェアの排他方法） | **決着させる。** 3構成のビルド骨組みが実質これを決めるため、決定と文書の間にずれを残さない |

## design フェーズで決めるもの（requirements では決めない）

- ポートの具体的なシグネチャ・型・クラス構成

- 出力アービトレーション（複数保護が同時に成立したときの優先順位の表現方法）
- 簡易プラントモデルの具体形（1次遅れ・むだ時間の有無）とテストコード内での配置
- 演算に浮動小数点を使うか固定小数点を使うか、および固定幅整数型の割当（32bit / 64bit の使い分け）
- ライブラリ分割の粒度とディレクトリ名
- ホストテストと組込みテストの振り分け方法の具体
- 累積器がラップアラウンドを検出する具体的な条件式

## Introduction

drivetrain-core は、3輪オムニ移動体の**駆動中核ロジックを、実機を一切使わずホスト上で検証できる形で
確定させる**部品である。

範囲は `docs/drivetrain-spec.md` §10.1.2 の層構造の**下段**にあたる:
逆運動学・速度PID・エンコーダ読み出しの解釈・PWM/方向出力指令の生成・保護①〜④、そしてオドメトリ。
最上段（指令生成）は本 Spec の外にあり、テレオペでは `teleop-bringup` が、M3 では本番経路が担う。

本 Spec の価値は2つある。

**1つめは安全である。** `docs/drivetrain-spec.md` §10 と `.kiro/steering/tech.md` 開発標準2 は、
M2a（初通電走行）より前に保護①〜④を実装することを要求している。
特に④（指令ウォッチドッグ）が無い状態でテレオペを作ると、
**コントローラの電池切れ・圏外・接続断の瞬間に、機体が最後の入力のまま走り続ける。**
この保護は「あとで足す機能」ではなく、**初通電の前提条件**である。

**2つめは切り分け能力である。** 組み立て直後に起きるのは性能不足ではなく配線・符号のバグであり、
ロジックとハードのどちらが原因かを同時に切り分けるのが最も難しい。
ロジック側をホストで確定させておけば、**実機で潰すべき問題が配線・符号・実測値だけに絞り込まれる。**

そしてこの層は捨てにならない。`docs/drivetrain-spec.md` §10.1.2 が明記するとおり、
**テレオペで検証した時点で M2b・M3 の分まで検証済みになる。**

本 Spec は**ハード不要で今すぐ着手でき**、固定側の実機セットアップと完全に並行できる
（`.kiro/steering/roadmap.md` 着手ウェーブ）。

## Boundary Context

- **In scope**:
  - ファームウェアプロジェクトの骨組みと3つのビルド構成（テレオペ用 / 本番用 / ホストテスト用）、
    およびディレクトリ配置の確定
  - 指令の入口4種: 機体速度指令 `(vx, vy, ω)` ＋有効時刻 / 輪ごとの目標速度 /
    **輪ごとの目標出力（速度PID を経由しない開ループ経路。2026-08-24 追加）** / 出力許可
  - 3輪オムニ・120°配置の逆運動学: `(vx, vy, ω)` → 各輪目標速度
  - エンコーダの累積カウントの解釈と、ラップアラウンドを跨ぐ累積器
  - 生の電圧読み値からバッテリ電圧への換算（分圧比・非線形補正）の純ロジック
  - 順運動学とオドメトリ: 各輪カウント → 機体位置・姿勢（FR-6）
  - 各輪の速度PID
  - 保護①〜④の**判定ロジックと状態機械**、および出力指令の遮断値の決定
  - 時刻源の注入インターフェース
  - 単位系（距離 mm / 時刻 ms）と固定幅整数型の徹底
  - ペリフェラルのポート定義（エンコーダ読み出し / PWM・方向出力 / 電圧読み出し）— **宣言のみ**
  - ホストでの単体テスト一式と、テスト専用の簡易プラントモデルによる閉ループ検証
  - OQ-40（ファーム側）・OQ-21 の決着、BTstack ライセンスの新規 OQ 登録、
    および `.kiro/steering/structure.md` の是正
- **Out of scope**:
  - **ESP32 ペリフェラルの実装コード**（パルスカウンタ / PWM / ADC）→ `teleop-bringup`
  - **無線・コントローラ関連の一切**（Bluetooth / Bluepad32 / DualSense）→ `teleop-bringup`
  - **指令生成**（パッド入力 → `(vx, vy, ω)`、目標座標 → `(vx, vy, ω)`）→ `teleop-bringup` / M3
  - デッドゾーン・入力カーブ・パッドのボタン割当 → `teleop-bringup`
  - 実機での校正・発火試験、`ENCODER_COUNTS_PER_WHEEL_REV` の実測値 → `teleop-bringup`
  - 定量計測とパラメータの実測、NFR-1 の評価 → `m2-motion-validation`
  - 実機の性能値（最高速度・加速度）の決定 — 本 Spec は**パラメータの型と検証だけを持ち、値を持たない**
  - 保護閾値の具体値（OQ-14 / OQ-15 / OQ-18 / OQ-22）
  - 目標座標への**位置制御**（上位ループ）→ M3
  - 固定側 → 移動体の通信、⑤ジオフェンス、物理的な非常停止手段 → M3
  - 機構設計・CAD・現物採寸
- **Adjacent expectations**:
  - `teleop-bringup` は本 Spec が宣言したポートを実装し、**そこに判断ロジックを置かない**。
    エンコーダ累積器と電圧換算は本 Spec が提供するものを利用する
  - `teleop-bringup` の**デッドマンは本 Spec の「出力許可」入口へのマッピング**として実現され、
    **輪単体テスト（D-pad による対象輪選択）は「輪ごとの目標速度」入口へのマッピング**として、
    **M2a-1 の開ループ走行は「輪ごとの目標出力」入口へのマッピング**として実現される。
    いずれのマッピングも `teleop-bringup` が持ち、本 Spec は入口だけを持つ。
    ⚠️ **下流が出力ポートへ直接書く経路を作らせない**ことが、開ループ入口を本 Spec に置く理由である
    （保護①〜④は本 Spec の内部構造であり、下流から適用する手段が無い）
  - `m2-motion-validation` は実測値を `trajectory_sim.DrivetrainParams` へ**翻訳して戻す**。
    本 Spec はその翻訳が成立するよう、**単位と定義を揃えた量を外へ出す**にとどまり、
    翻訳そのものは持たない
  - `trajectory-simulator` の**コードは変更しない**。意味論を揃えるだけで、コードは共有しない
  - M3 は保護④の**入力元を差し替えるだけ**にする。FR-10 は新規実装ではないため、
    ④は「指令元固有の処理」を含まない形でなければならない
  - `docs/drivetrain-spec.md` が駆動系の設計の正であり、本 Spec はそれに従う。
    未決事項の唯一の正は `docs/open-questions.md` である

## Requirements

### Requirement 1: ファームウェアプロジェクトの骨組みとビルド構成の分離

**Objective:** As a 移動体ファームウェアをこれから書き始める開発者, I want テレオペ用・本番用・ホストテスト用のビルド構成が最初から分かれ、下位層が3構成すべてで共有されること, so that テレオペで検証したロジックがそのまま本番でも使われることを構造として保証できる

_出典: A-13, A-14, A-16_

#### Acceptance Criteria

1. The drivetrain-core shall テレオペ用・本番用・ホストテスト用の3つのビルド構成を持つ
2. The drivetrain-core shall 駆動中核ロジックを、3つのビルド構成すべてから同一のソースとしてリンクできる形に配置する
3. The drivetrain-core shall テレオペ用ビルドと本番用ビルドを排他とし、同時に成立しないようにする
4. The drivetrain-core shall 無線スタックを本番用ビルドの成果物へ含めない
5. When ホストテスト用構成でビルドした場合, the drivetrain-core shall ESP32 実機・ペリフェラル・無線のいずれも必要とせずにテストを実行できる
6. The drivetrain-core shall 対象マイコンを classic ESP32 に固定し、他系統への乗り換えを前提とした構成を持たない
7. The drivetrain-core shall 依存する外部プラットフォーム定義を、更新によって内容が変化しない形に固定する

### Requirement 2: ペリフェラル境界とポート宣言

**Objective:** As a ホスト上でロジックを検証したい開発者, I want ペリフェラル依存が薄い境界の向こう側へ隔離されていること, so that 実機が無くても駆動ロジック全体をテストできる

_出典: A-2, A-11_

#### Acceptance Criteria

1. The drivetrain-core shall エンコーダ読み出し・PWM/方向出力・電圧読み出しをポートとして宣言し、その実装を持たない
2. The drivetrain-core shall ペリフェラルおよび組込みフレームワークに固有のヘッダを、駆動中核ロジックから参照しない
3. The drivetrain-core shall ポートの契約に、ペリフェラル固有の型・分解能・イベント形式を露出させない
4. If 駆動中核ロジックがペリフェラル固有のヘッダを参照する実装が混入した場合, then the drivetrain-core shall その混入をテストで検出できるようにする
5. The drivetrain-core shall 判断・計算を伴う処理をポートの実装側へ委ねない
6. The drivetrain-core shall 無線・コントローラ・通信に関するポートを持たない

### Requirement 3: 時刻源の注入と制御ステップの駆動

**Objective:** As a ホストテストを実際に機能させたい開発者, I want 現在時刻がロジックの外から与えられること, so that 経過時間に依存する PID と保護をホスト上で決定的に再現できる

_出典: A-3_

#### Acceptance Criteria

1. The drivetrain-core shall 現在時刻を駆動中核ロジックの内部で取得せず、外部から与えられた時刻のみを用いる
2. The drivetrain-core shall 制御ステップを呼び出し側から駆動される形とし、自らループを回さない
3. When 同一の時刻列と同一の入力列を与えた場合, the drivetrain-core shall 同一の出力列を返す
4. If 前回より過去の時刻が与えられた場合, then the drivetrain-core shall 経過時間を零として扱い、内部状態を破壊しない
5. The drivetrain-core shall 制御周期を固定値として前提にせず、実際の経過時間に基づいて計算する
6. The drivetrain-core shall 時刻を伴わない状態更新の入口を持たない

### Requirement 4: 数値表現と単位系

**Objective:** As a ホストと ESP32 の両方で同じ結果を得たい開発者, I want 整数幅と単位が明示的に固定されていること, so that オーバーフロー挙動と単位換算の誤りがホストテストで再現される

_出典: A-4, A-5_

#### Acceptance Criteria

1. The drivetrain-core shall 整数を扱うすべての箇所で、幅が処理系によって変化しない型を用いる
2. The drivetrain-core shall 距離をミリメートル、時刻をミリ秒として外部境界で表現する
3. The drivetrain-core shall 単位換算の係数を計算式へ直接書かず、一箇所に集約する
4. The drivetrain-core shall 累積量の表現幅を処理系に依らず同一とし、ホストと実機でオーバーフロー挙動が一致するようにする
5. The drivetrain-core shall 累積量が表現範囲を超え得る箇所を明示し、その振る舞いをテストで確認できるようにする
6. If 幅が処理系依存となる型が駆動中核ロジックに混入した場合, then the drivetrain-core shall その混入をテストで検出できるようにする

### Requirement 5: 指令の入力契約

**Objective:** As a テレオペと本番経路の両方を同じ下位層へ載せたい開発者, I want 指令の型が指令元によらず一つに定まっていること, so that M3 で指令元を差し替えるだけで済む

_出典: A-6, A-7_

#### Acceptance Criteria

1. The drivetrain-core shall 指令を、並進速度2成分・回転速度1成分・その指令が有効になった時刻の組として受け取る
2. The drivetrain-core shall 指令元の種別によって処理を分岐させない
3. The drivetrain-core shall 指令元に固有の情報（入力機器の状態・通信の詳細）を指令の型に含めない
4. If 有効範囲を外れた指令が与えられた場合, then the drivetrain-core shall その指令を有効範囲へ制限し、制限が行われたことを外部へ提供する
5. The drivetrain-core shall 指令が更新されない間も、直前の有効な指令とその時刻を保持する
6. The drivetrain-core shall 指令を受け取ったこと自体を、出力を許可する条件として扱わない
7. The drivetrain-core shall 指令とは別に、出力を許可するか否かを外部から与えられる入口を持つ
8. The drivetrain-core shall 輪ごとの目標速度を直接与える入口を、逆運動学を経由しない形で提供する
9. While 輪ごとの目標速度が直接与えられている場合, the drivetrain-core shall 保護①〜④を機体速度指令の場合と同一に適用する

11. While 輪ごとの目標出力が直接与えられている場合, the drivetrain-core shall 保護①〜④と出力上限を、機体速度指令の場合と同一に適用する
12. While 輪ごとの目標出力が直接与えられている場合, the drivetrain-core shall 指令の途絶を機体速度指令の場合と同一に判定する
13. If 与えられた目標出力が出力の定義域を外れた場合, then the drivetrain-core shall その値を定義域へ制限し、制限が行われたことを外部へ提供する
14. When 速度PID を経由する経路と経由しない経路が切り替わった場合, the drivetrain-core shall 切り替え前の経路の内部状態を持ち越さない
15. The drivetrain-core shall どちらの経路が有効であるかを、利用側が判別できる形で外部へ提供する

### Requirement 6: 逆運動学（3輪オムニ・120°配置）

**Objective:** As a 全方向走行を実現したい開発者, I want 機体速度指令から各輪の目標速度が算出されること, so that 向き直す時間を待たずに任意方向へ移動できる

_出典: A-1, A-6_

#### Acceptance Criteria

1. The drivetrain-core shall 並進速度2成分と回転速度から、3輪それぞれの目標速度を算出する
2. The drivetrain-core shall 輪の取付角と機体中心から輪までの距離を、外部から与えられるパラメータとして扱う
3. When 回転速度が零で並進速度のみが与えられた場合, the drivetrain-core shall 算出した3輪の目標速度から順運動学で復元した機体速度が、指令された並進速度と一致するようにする
4. When 並進速度が零で回転速度のみが与えられた場合, the drivetrain-core shall 3輪に同一方向・同一大きさの目標速度を与える
5. If いずれかの輪の目標速度が出力可能な範囲を超える場合, then the drivetrain-core shall 指令された運動の方向を保ったまま全輪を縮小する
6. The drivetrain-core shall 輪番号と符号の対応を一箇所で定義し、実装内に重複させない
7. The drivetrain-core shall 目標座標から機体速度指令を求める上位の位置制御を持たない

### Requirement 7: エンコーダカウントの累積と物理量への換算

**Objective:** As a オドメトリを信頼したい開発者, I want ハードウェアカウンタの折り返しを跨いで累積が続くこと, so that 数秒走っただけで自己位置が壊れる事態を防げる

_出典: A-4, A-10, A-11_

#### Acceptance Criteria

1. The drivetrain-core shall ハードウェアカウンタの折り返しを検出して桁上げする累積器を提供する
2. The drivetrain-core shall 累積器を、実機を用いずにホスト上でテストできる形で提供する
3. When 折り返しを含む生カウント列が与えられた場合, the drivetrain-core shall 連続した累積値を返す
4. When 正転と逆転を跨いで折り返しが発生した場合, the drivetrain-core shall 回転方向を取り違えずに累積する
5. The drivetrain-core shall ポートの契約を、折り返しを含まない累積カウントとして定義する
6. The drivetrain-core shall 1輪1回転あたりのカウント数を外部から与えられるパラメータとして扱い、実装内に固定値として埋め込まない
7. The drivetrain-core shall ホイール径を外部から与えられるパラメータとして扱い、カウントから距離への換算を一箇所に集約する

### Requirement 8: 順運動学とオドメトリ

**Objective:** As a 目標との差分を詰めたい開発者, I want 各輪のカウントから機体の位置と姿勢が推定されること, so that 固定側を一切使わずに自己位置と逆運動学の妥当性を検証できる

_出典: A-1, A-5_（`docs/requirements.md` FR-6）

#### Acceptance Criteria

1. The drivetrain-core shall 3輪の累積カウントの変化から、機体の並進速度2成分と回転速度を算出する
2. The drivetrain-core shall 算出した機体速度を時間積分し、機体の位置と姿勢を推定する
3. The drivetrain-core shall 推定位置の原点と姿勢を、外部からの操作で初期化できるようにする
4. When 逆運動学で与えた機体速度どおりに輪が回った場合, the drivetrain-core shall 順運動学で同一の機体速度を復元する
5. The drivetrain-core shall 推定位置を距離ミリメートル、時刻ミリ秒の単位で外部へ提供する
6. The drivetrain-core shall 初期化時点からの経過時間と累積走行距離を、ドリフト量の見積もりに使える形で外部へ提供する
7. The drivetrain-core shall 推定位置を外部の座標系へ合わせる手順を自身の責務に含めない

### Requirement 9: 各輪の速度PID

**Objective:** As a 指令どおりの速度で走らせたい開発者, I want 各輪の速度が目標へ追従すること, so that 逆運動学の結果が実際の機体運動として現れる

_出典: A-1, A-3, A-4, A-9, A-12_

#### Acceptance Criteria

1. The drivetrain-core shall 各輪について、目標速度と計測速度の差に基づく出力指令を算出する
2. The drivetrain-core shall 制御ゲインを外部から与えられるパラメータとして扱い、既定値を必須性能として扱わない
3. The drivetrain-core shall 経過時間を外部から与えられた時刻から求め、内部で時刻を取得しない
4. While 出力指令が上限に張り付いている場合, the drivetrain-core shall 積分項が際限なく増大しないようにする
5. When 出力が遮断されている場合, the drivetrain-core shall 内部状態が遮断解除後の挙動を乱さないように扱う
6. The drivetrain-core shall 積分項を、表現範囲を超え得ることを考慮した型で保持する
7. When テスト用の車輪応答モデルと閉ループで接続した場合, the drivetrain-core shall 目標速度へ収束することを検証できるようにする

### Requirement 10: 保護① モータロック保護

**Objective:** As a モータドライバを焼きたくない開発者, I want 出力を出しているのに輪が回っていない状態が検出されること, so that ヒューズが溶断しないストール電流域でもモータ出力を止められる

_出典: A-7, A-8, A-9_（`docs/drivetrain-spec.md` §5、`docs/requirements.md` FR-9）

#### Acceptance Criteria

1. While 出力指令が閾値以上でありかつ計測速度が閾値以下である状態が継続時間を超えて続いている場合, the drivetrain-core shall 該当する輪の出力を停止する
2. The drivetrain-core shall 出力指令の閾値・速度の閾値・継続時間を、外部から与えられるパラメータとして扱う
3. The drivetrain-core shall 判定を輪ごとに独立して行う
4. If 継続時間に満たない一時的な速度低下が起きた場合, then the drivetrain-core shall 出力を停止しない
5. The drivetrain-core shall 復帰条件を自動復帰と手動リセットのいずれにも設定できるようにする
6. The drivetrain-core shall ロック検出が発生したことを、利用側が判別できる形で外部へ提供する
7. The drivetrain-core shall ハードウェアヒューズによる保護を前提にしない

### Requirement 11: 保護② LiPo 低電圧保護

**Objective:** As a バッテリを痛めたくない開発者, I want セル電圧が危険域へ落ちる前に警告と停止が行われること, so that 急加速時の一時的な電圧降下では誤停止せずにバッテリを保護できる

_出典: A-7, A-8, A-9_（`docs/drivetrain-spec.md` §9.2、`docs/requirements.md` FR-9）

#### Acceptance Criteria

1. When バッテリ電圧が警告閾値を下回った場合, the drivetrain-core shall 警告状態であることを外部へ提供する
2. When バッテリ電圧が停止閾値を一定時間継続して下回った場合, the drivetrain-core shall モータ出力を停止する
3. The drivetrain-core shall 電圧の読み値を移動平均して判定に用いる
4. The drivetrain-core shall 復帰閾値を停止閾値より高く設定できるようにし、両者を独立したパラメータとして扱う
5. If モータの急加速により電圧が一時的に閾値を下回った場合, then the drivetrain-core shall 継続時間の条件を満たさない限り停止しない
6. The drivetrain-core shall 警告閾値・停止閾値・復帰閾値・移動平均の窓・継続時間を外部から与えられるパラメータとして扱い、既定値を絶対仕様として扱わない
7. The drivetrain-core shall 生の読み値からバッテリ電圧への換算（分圧比と非線形補正）を、外部から与えられるパラメータを伴う純ロジックとして提供する
8. If 電圧の読み値が得られない場合, then the drivetrain-core shall その値を移動平均へ取り込まず、読み値が得られない状態が継続時間を超えて続いた場合にモータ出力を停止する

### Requirement 12: 保護③ バッテリ電圧を考慮した PWM 上限

**Objective:** As a 満充電時にモータへ過電圧を掛けたくない開発者, I want 実測電圧に応じて出力上限が下がること, so that 12.6V の満充電でも 12V 定格のモータを想定範囲で駆動できる

_出典: A-7, A-9_（`docs/drivetrain-spec.md` §9.3）

#### Acceptance Criteria

1. The drivetrain-core shall 計測されたバッテリ電圧に応じて、出力指令の上限を決定する
2. The drivetrain-core shall 上限の算出に用いる基準電圧を、外部から与えられるパラメータとして扱う
3. The drivetrain-core shall 上限が最大出力を超えないように制限する
4. When 上限が下がった場合, the drivetrain-core shall すべての輪の出力指令に同一の上限を適用し、指令された運動の方向を保つ
5. The drivetrain-core shall 上限の算出式を固定仕様として決め打ちせず、外部から差し替えまたは無効化できるようにする
6. If 電圧の読み値が得られない場合, then the drivetrain-core shall 上限を無制限とせず、外部から与えられた安全側の既定上限を適用する

### Requirement 13: 保護④ 指令ウォッチドッグ

**Objective:** As a 機体を暴走させたくない開発者, I want 指令が更新されなくなった時点で自律的に停止すること, so that コントローラの電池切れ・圏外・接続断でも最後の入力のまま走り続けない

_出典: A-6, A-7, A-8, A-9_（`docs/drivetrain-spec.md` §10 の④、`docs/requirements.md` FR-10）

#### Acceptance Criteria

1. When 最後に有効な指令を受けてからの経過時間がタイムアウトを超えた場合, the drivetrain-core shall モータ出力を停止する
2. The drivetrain-core shall 判定に「最後に有効な指令を受けてからの経過時間」のみを用い、指令元に固有の情報を用いない
3. The drivetrain-core shall タイムアウト値を外部から与えられるパラメータとして扱う
4. The drivetrain-core shall 経過時間の判定を制御ステップ側で行い、指令の到着時のみに依存させない
5. While 指令が到着しない状態が続いている場合, the drivetrain-core shall 直前の指令を継続して実行しない
6. When タイムアウト後に有効な指令が再び到着した場合, the drivetrain-core shall タイムアウト状態を解除し、出力許可が与えられている場合にのみ出力を再許可する
7. The drivetrain-core shall 指令元を差し替えても判定ロジックが変更を要さない形で実装する
8. The drivetrain-core shall 本保護を、物理的な非常停止手段の代替として位置付けない

### Requirement 14: 保護の統合・出力遮断・復帰

**Objective:** As a 保護が確実に効くことをホストで確かめたい開発者, I want 判定と遮断が分離されつつ、遮断されるべき状態では出力指令が既に遮断値になっていること, so that アダプタの実装品質に依らず保護の成立をテストできる

_出典: A-7, A-8, A-9_

#### Acceptance Criteria

1. While いずれかの保護が成立している場合, the drivetrain-core shall 外部へ渡す出力指令を遮断値とする
2. The drivetrain-core shall 出力の物理的な遮断そのものを自身の責務に含めず、ポートの実装へ渡す値としてのみ表現する
3. When 複数の保護が同時に成立した場合, the drivetrain-core shall いずれか一つでも成立している限り出力を遮断する
4. The drivetrain-core shall 成立中の保護の種別を、利用側が判別できる形で外部へ提供する
5. The drivetrain-core shall 保護ごとに、成立状態を保持し続けるか自動的に解除するかを設定できるようにする
6. When 保持された保護状態を解除する操作が行われた場合, the drivetrain-core shall 解除条件を満たす場合にのみ出力を再許可する
7. The drivetrain-core shall 保護の判定と遮断値の決定を、実機を用いずにホスト上でテストできる形で実装する
8. The drivetrain-core shall 保護①〜④のすべてを本 Spec の範囲として実装し、後続 Spec へ先送りしない
9. While 出力許可が与えられていない場合, the drivetrain-core shall 外部へ渡す出力指令を遮断値とする
10. When 起動後まだ一度も有効な指令を受けていない場合, the drivetrain-core shall 外部へ渡す出力指令を遮断値とする

### Requirement 15: パラメータ化と既定値の扱い

**Objective:** As a 未実測の数値を合否条件にしたくない開発者, I want 閾値・タイムアウト・性能値がすべて外から与えられること, so that 実測が出るまで値を確定させずに実装を進められる

_出典: A-9, A-10, A-15_

#### Acceptance Criteria

1. The drivetrain-core shall 保護の閾値・継続時間・タイムアウト・制御ゲイン・機体寸法・エンコーダ分解能を、外部から与えられるパラメータとして扱う
2. The drivetrain-core shall 実機の性能値（最高速度・加速度）を自身の内部に持たない
3. Where 既定値を持つパラメータがある場合, the drivetrain-core shall それが必須性能でも達成済み性能でもないことを明示する
4. If 不正なパラメータが与えられた場合, then the drivetrain-core shall 制御を開始する前に拒否する
5. The drivetrain-core shall 実効的に適用されているパラメータを、実行開始時に確認できるようにする
6. The drivetrain-core shall 根拠のない固定値を計算式へ直接埋め込まない

### Requirement 16: 実機なしでの検証可能性

**Objective:** As a 実機到着前に着手する開発者, I want 駆動ロジック全体がホスト上でテストできること, so that 実機で潰すべき問題を配線・符号・実測値だけに絞り込める

_出典: A-1, A-2, A-3, A-12, A-13_

#### Acceptance Criteria

1. The drivetrain-core shall 逆運動学・順運動学・オドメトリ・速度PID・累積器・保護①〜④のすべてを、実機を用いずにホスト上でテストできる
2. The drivetrain-core shall テスト専用の車輪応答モデルを備え、閉ループでの挙動を検証できるようにする
3. The drivetrain-core shall 車輪応答モデルを本体のコードに含めず、テスト側にのみ置く
4. The drivetrain-core shall 車輪応答モデルの係数が合否条件でも実測値でもないことを明示する
5. When 同一の入力列と時刻列を繰り返し与えた場合, the drivetrain-core shall 同一の結果を返す
6. The drivetrain-core shall ホスト上で得た結果を実機性能の主張として扱わない旨を明示する
7. The drivetrain-core shall ホスト上で実行するテストと実機上で実行するテストを区別できるようにする
8. The drivetrain-core shall 保護が発火する条件をホスト上で再現し、実際に発火することを検証できるようにする

### Requirement 17: 下流 Spec との接続契約

**Objective:** As a 後続の実機 Spec を滞りなく着手したい開発者, I want 本 Spec が外へ出す量の単位と定義が既存のシミュレータと揃っていること, so that 実測値をシミュレータへ翻訳して戻せる

_出典: A-2, A-11, A-15_

#### Acceptance Criteria

1. The drivetrain-core shall 最高速度・加速度上限・減速度上限・制御周期・指令反映遅れに相当する量を、既存の運動モデルと同一の単位と定義で扱う
2. The drivetrain-core shall 実測値から運動モデルのパラメータへの翻訳そのものを自身の責務に含めない
3. The drivetrain-core shall 既存のシミュレータのコードを変更しない
4. The drivetrain-core shall 既存のシミュレータと駆動制御のロジックを共有しない
5. The drivetrain-core shall 後続 Spec がポートを実装するために必要な契約を、実装を伴わずに提供する
6. The drivetrain-core shall 指令元の差し替えのみで本番経路へ移行できる形で、指令の入口を提供する
7. The drivetrain-core shall 内部状態の外部への読み出しを、制御ステップの実行をブロックしない形で提供する

### Requirement 18: 未決事項の決着とドキュメントの是正

**Objective:** As a 決定と文書がずれた状態を残したくない開発者, I want 本 Spec で決まったことが未決事項一覧と steering へ反映されること, so that 「決まっているのに未確定と書いてある箇所」が生まれない

_出典: A-16_

#### Acceptance Criteria

1. When ファームウェア側のディレクトリ構成が確定した場合, the drivetrain-core shall その決定内容と理由を決定の記録へ移し、未決事項一覧の該当行を削除する
2. When テレオペ用ビルドと本番用ビルドの排他方法が確定した場合, the drivetrain-core shall その決定内容と理由を決定の記録へ移し、未決事項一覧の該当行を削除する
3. The drivetrain-core shall 決着した未決事項について、本文側の参照も同時に外す
4. The drivetrain-core shall 無線ライブラリが依存する非オープンソース部品のライセンス取り扱いを、新規の未決事項として末尾に採番して登録する
5. The drivetrain-core shall 新規の未決事項に「何をすれば決まるか」を記載する
6. When 実装着手によりコードの配置が実態として定まった場合, the drivetrain-core shall プロジェクト構造の steering 文書を実態に合わせて是正する
7. The drivetrain-core shall 未決事項を未決事項一覧以外の場所へ複製しない
8. The drivetrain-core shall 対象マイコンの型番が部品表で未指定である点を、明記が必要な事項として残す
