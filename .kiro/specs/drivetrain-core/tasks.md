# Implementation Plan

> **本 Spec は実機・ESP32 ペリフェラル・無線を一切必要としない。** すべてのタスクはホスト（WSL2）上で完結する。
> ⚠️ **数値パラメータの値を決めるタスクは1つも無い。** 本 Spec は型・不変条件・検証だけを持つ（要件 15）。
> 閾値・ゲイン・寸法・分解能の実測は `teleop-bringup` / `m2-motion-validation` が行う。

## 1. ファームウェアプロジェクトの骨組みと3ビルド構成

- [ ] 1. ファームウェアプロジェクトの骨組みと3ビルド構成

- [x] 1.1 3つのビルド環境を定義し、純ロジックが3構成すべてからリンクされることを実証する
  - `firmware/platformio.ini` に `teleop` / `production` / `native` の3環境を定義する。ファーム2環境は classic ESP32 固定・ESP-IDF・C++17 を明示し、外部プラットフォーム定義は更新で内容が変化しないリリース成果物の URL として固定する
  - 純ロジックのディレクトリに、組込みビルド用のコンポーネント登録ファイルとホストビルド用のライブラリマニフェストを**同居**させる。組込み側のルート設定は、純ロジックのディレクトリを直接指す形にする（テスト専用ライブラリが探索対象へ入らないようにするため）
  - ファーム2環境ではホスト側の依存探索を無効化し、テスト専用ライブラリがファームウェアへ混入する経路を塞ぐ
  - アプリ層のエントリポイントと、そのビルド設定を最小構成で置く。この時点ではポートを結線しない
  - 純ロジック側に公開入口ヘッダと、リンク確認用の最小の実体を1つ置く
  - ホストテストと実機テストのディレクトリを分け、環境ごとに振り分ける設定を入れる
  - ⚠️ **「ホストテストが緑になること」だけを完了と扱わない。** 3構成のうち1つでも通らない骨組みは、以降のすべてのタスクの前提を壊す
  - 観測可能な完了状態: ホストテストが完走し、**かつ**テレオペ用・本番用の両ファームウェアがリンクまで到達することの3点すべてが揃う
  - _Requirements: 1.1, 1.2, 1.5, 1.6, 1.7, 16.7_

- [x] 1.2 テレオペ用ビルドと本番用ビルドを排他にし、本番から無線を排除する
  - アプリ層に、ビルド構成マクロが「ちょうど1つだけ定義されている」ことを検査するヘッダを置く。両方定義／どちらも未定義のときはコンパイル時に失敗させる
  - 各環境のビルドフラグで、対応するビルド構成マクロを1つだけ定義する
  - 本番用ビルドの設定で無線機能を無効化し、無線関連の外部依存を1つも持たせない。テレオペ専用ソースの置き場をビルド対象から除外する設定を入れる
  - **⚠️ ビルド構成マクロを純ロジック側で参照しない。** 純ロジックは3構成すべてで同一のソースであり、構成による分岐を持たない
  - 実機テストのレーンに、実機ツールチェーンでリンクが通ることだけを見る最小のテストを置く
  - 観測可能な完了状態: 両方のビルド構成マクロを同時に定義したビルドがコンパイル時に失敗すること、および本番用ビルドの生成された設定に無線無効化が反映されていることを、実行して確認できる
  - _Requirements: 1.3, 1.4, 16.7_

- [x] 1.3 ビルド構成を静的に検査する仕組みを、以降のタスクより先に用意する
  - 既存の Python テスト資産と同じ流儀で、`tests/` 配下に静的走査のテストを追加する（駆動制御ロジックの複製ではないため二重実装には当たらない）
  - **⚠️ この検査を後回しにしない。** 組込みビルド用のソース列挙とホスト側のソース実体の集合がずれると、**ホストテストだけが緑でファームウェアがリンクできない**状態が生まれる。タスク2以降はソースを追加し続けるため、**この検査が無い期間そのものが危険**である
  - 上記のソース集合の一致と、テスト専用ライブラリが組込みの探索対象に含まれていないことを検出する
  - 3つのビルド環境が存在すること、ホストテスト環境が実機を要さない構成であることを検出する
  - **テレオペ用と本番用のビルド構成マクロが互いに排他であること**を検出する
  - **本番用ビルドが無線関連の外部依存を持たず、無線無効化の設定を持つこと**を検出する
  - **ファーム2環境の対象基板が classic ESP32 に固定され、他系統の環境が定義されていないこと**を検出する
  - **外部プラットフォーム定義が更新で内容の変化しない成果物として固定されており、可変の参照になっていないこと**を検出する
  - ホストテストと実機テストの振り分け設定が存在することを検出する
  - 観測可能な完了状態: 上記すべての違反をわざと作り込んだ場合にテストが赤くなり、現状の構成では緑になることを確認できる
  - _Requirements: 1.3, 1.4, 1.6, 1.7, 16.3, 16.7_

## 2. 基盤層: 単位・型・設定・ポート

- [ ] 2. 基盤層: 単位・型・設定・ポート

- [x] 2.1 単位換算の集約と設定エラーの型を定義する
  - 距離ミリメートル・時刻ミリ秒・電圧ミリボルトの換算係数と円周率を1箇所へ集約する。裸の数値定数を他のどのファイルにも書かない方針をここで確立する
  - 時刻から秒への換算、エンコーダ累積カウント差から距離への換算、角度の正規化を提供する。**カウントから距離への換算を行うのはこの1箇所だけ**にする
  - 設定検証の失敗を、例外を使わずに「原因の種別」「違反したパラメータ」「輪番号やテーブル位置の添字」の3点で返せる型を定義する
  - 観測可能な完了状態: 換算の往復（時刻・距離・角度の正規化）を検証するホストテストが緑になる
  - _Requirements: 4.2, 4.3, 7.7, 15.4, 15.6_

- [x] 2.2 指令・出力・状態・遮断理由のコア型を定義する
  - 時刻と経過時間、機体速度指令と輪ごとの目標速度指令、指令の受理結果、出力デューティ、電圧サンプル、累積カウント、位置姿勢、機体速度、遮断理由のビットマスク、制御ステップの結果を定義する
  - **整数を扱うすべての箇所で幅が処理系によって変化しない型を用いる。** 時刻は32ビットの折り返しを経過時間計算の考慮対象から外せる幅にする
  - 指令の型に、入力機器の状態・通信の詳細といった**指令元に固有の情報を一切含めない**
  - 遮断理由は、機体全体に効くものと輪ごとに効くものを同じビット定義で表現し、利用側が種別を判別できる形にする
  - 観測可能な完了状態: 各型のサイズと整数幅をコンパイル時表明で固定するホストテストが緑になり、ホストと組込みの両方でビルドが通る
  - _Requirements: 4.1, 4.2, 4.4, 5.1, 5.3, 14.4_

- [x] 2.3 (P) 全パラメータ構造体と設定検証を実装する
  - 機体寸法・エンコーダ分解能とホイール径・出力極性・運動上限・制御ゲイン・保護①〜④の閾値と継続時間・電圧換算テーブルを、それぞれ構造体として定義する
  - **⚠️ 数値パラメータに既定値を与えない。** 既定値を持つのは振る舞いを選ぶ真偽値・列挙（有効無効、保持か自動復帰か）のみとし、それが必須性能でも達成済み性能でもないことをコード上で明示する。実機の性能値を構造体の外にも内にも持たない
  - 検証で、有限性・正値性・定義域・順序関係（復帰閾値が停止閾値より高いこと等）・幾何の非退化・電圧テーブルの単調性と点数・移動平均窓の上限・極性が想定の2値であること・積分上限が有限であることを判定する
  - 動的メモリ確保を避けるための容量上限を定数として置く
  - 観測可能な完了状態: ゼロ初期化した設定が拒否されること、順序関係違反・退化した幾何・不正な極性がそれぞれ対応する原因種別で拒否されることを検証するホストテストが緑になる
  - _Requirements: 6.2, 7.6, 7.7, 9.2, 10.2, 11.6, 12.2, 13.3, 15.1, 15.2, 15.3, 15.4, 15.6_
  - _Boundary: DrivetrainConfig_
  - _Depends: 2.2_

- [ ] 2.4 (P) 3つのペリフェラルポートを宣言する
  - エンコーダ読み出し・出力書き出し・電圧読み出しの3つを抽象として宣言し、**実装を1つも持たない**
  - 契約は物理量だけを往復させる。折り返しを含まない累積カウント、正規化されたデューティ、ミリボルトと妥当性フラグを扱い、**ペリフェラル固有の型・分解能・イベント形式を露出させない**
  - **無線・コントローラ・通信に関するポートを持たない**
  - 折り返しの桁上げと電圧換算は核が提供して実装側に利用させる契約であることを、宣言のコメントとして残す（判断・計算を実装側へ委ねないため）
  - 観測可能な完了状態: このヘッダが標準の固定幅整数ヘッダとコア型ヘッダ以外を参照せずにホスト・組込みの両方でコンパイルできる
  - _Requirements: 2.1, 2.3, 2.5, 2.6, 7.5, 17.5_
  - _Boundary: Ports_
  - _Depends: 2.2_

## 3. プリミティブと運動学

- [ ] 3. プリミティブと運動学

- [ ] 3.1 (P) ハードウェアカウンタの折り返しを跨ぐ累積器を実装する
  - 前回の生値との差を法で最短経路へ折り返して積算し、64ビットの累積値を返す。法はパラメータとし、ハードウェア側の折り返し方式が変わっても対応できるようにする
  - **サンプリング間隔中の真の変化量が法の半分未満であること**を事前条件として明記し、想定される最悪の回転速度と制御周期に対する余裕の見積もりをコメントとして残す
  - 観測可能な完了状態: 正転で折り返す列・逆転で折り返す列・正転と逆転を交互に跨ぐ列・累積値の表現範囲上限近傍を初期値にした列の4系統を検証するホストテストが緑になる
  - _Requirements: 4.4, 4.5, 7.1, 7.2, 7.3, 7.4_
  - _Boundary: WrapAccumulator_

- [ ] 3.2 (P) 生の電圧読み値からバッテリ電圧への換算を実装する
  - 校正作業の出力（複数点で実測した「生値と実電圧の対」）をそのまま受け取れる区分線形テーブルとして換算する。点が2つだけのときは分圧比のみの線形換算へ自然に縮退させる
  - テーブル範囲外は両端の区間の傾きで外挿する
  - **分圧比や補正係数を実装内に固定値として持たない**
  - 観測可能な完了状態: テーブル点の上で厳密に一致すること、点間が線形であること、2点構成が分圧比換算と一致すること、範囲外が外挿されることを検証するホストテストが緑になる
  - _Requirements: 11.7, 15.6_
  - _Boundary: VoltageScaler_

- [ ] 3.3 (P) 3輪オムニの逆運動学と順運動学を実装する
  - 各輪の取付角と機体中心からの距離をパラメータとして受け取り、設定時に**逆運動学の行列とその逆行列を1度だけ構築**する。三角関数の評価はこの1回に閉じ、制御ループ内では行列積のみを行う
  - **輪番号と符号の対応をここで定義し、実装内に重複させない**
  - 120度等配置を安全に組み立てる補助を用意し、三角関数の手書きを不要にする
  - 方向を保ったまま複数の値を等比縮小する共通処理を提供する（指令の輪速度にも出力デューティにも使う）
  - **上位の位置制御（目標座標から機体速度指令を求める処理）を持たない**
  - 観測可能な完了状態: 純並進・純回転・複合の各指令で逆運動学と順運動学の往復が許容差内で一致すること、純回転指令で3輪が同一符号・同一大きさになること、等比縮小の後も指令された運動の方向が保たれることを検証するホストテストが緑になる
  - _Requirements: 6.1, 6.2, 6.3, 6.4, 6.5, 6.6, 8.1, 8.4_
  - _Boundary: Kinematics_

## 4. 速度制御とオドメトリ

- [ ] 4. 速度制御とオドメトリ

- [ ] 4.1 (P) 順運動学によるオドメトリを実装する
  - 各輪の周速から機体の並進2成分と回転を求め、**中点法**（機体座標系の変位を姿勢角の中点で回転させる）で世界座標系へ積分する
  - 姿勢角を正規化して保持し、位置は距離ミリメートル・時刻ミリ秒の単位で外へ出す
  - 原点と姿勢を外部からの操作で初期化できるようにし、**初期化時点からの経過時間と累積走行距離**をドリフト見積もりに使える形で提供する
  - **外部座標系への整合を自身の責務に含めない。** 原点は「最後に初期化した時点」以上の意味を持たない
  - 観測可能な完了状態: 直進・その場旋回・一定回転速度の円軌道が1周で閉じること、初期化後に原点へ戻ること、累積走行距離と経過時間が単調増加することを検証するホストテストが緑になる
  - _Requirements: 8.2, 8.3, 8.5, 8.6, 8.7_
  - _Boundary: Odometry_
  - _Depends: 3.3_

- [ ] 4.2 (P) 各輪の速度PIDを2段プロトコルで実装する
  - **上限でクランプしない生の出力を返す算出**と、**実際に適用された値を受け取って積分を調整する確定**の2段に分ける。1段で飽和値を渡す形にすると、3輪まとめての等比縮小と個々のワインドアップ対策が噛み合わない
  - 比例・積分は偏差に、**微分は計測値の変化**に掛ける（目標値変更時のキックを避けるため）
  - 積分は絶対値上限でクランプし、加えて確定の段で「実現されなかった分」を積算し直さないようにする
  - 出力が遮断されている間に呼ぶ経路を用意し、積分をゼロに保ちつつ微分の基準を現在の計測値へ追従させる
  - **経過時間を外部から与えられた時刻から求め、内部で時刻を取得しない**
  - 観測可能な完了状態: 飽和が続く入力で積分が上限を超えないこと、算出値より小さい値で確定し続けても積分が育たないこと、遮断解除の直後の算出が過大な出力を返さないことを検証するホストテストが緑になる
  - _Requirements: 9.1, 9.2, 9.3, 9.4, 9.5, 9.6_
  - _Boundary: VelocityPid_

## 5. 保護①〜④と統合

- [ ] 5. 保護①〜④と統合

- [ ] 5.1 (P) 保護① モータロック検出を実装する
  - 出力指令が閾値以上かつ計測速度が閾値以下である状態の継続が、設定された継続時間を超えたときに発火する状態機械を実装する。**判定は輪ごとに独立**とし、他輪の状態を参照しない
  - 条件が崩れたら継続時間の計測をリセットし、継続時間に満たない一時的な速度低下では発火しないようにする
  - 復帰条件を自動復帰と手動リセットのどちらにも設定できるようにする
  - **⚠️ 判定入力は「出力上限を適用した後・遮断する前」の出力指令である。** 遮断後の値で判定すると発火した瞬間に条件が崩れて自己解除し、上限適用前の生の値で判定すると実際には出ていない指令を根拠に誤発火する
  - ハードウェアヒューズによる保護を前提にしない旨をコメントとして残す（1モータのストールでは溶断しないため、この保護がその領域の唯一の防護である）
  - 観測可能な完了状態: 継続時間を超えた拘束で発火し、満たない拘束では発火せず、輪ごとに独立して判定され、自動復帰と手動リセットの両設定が意図どおり動くことを検証するホストテストが緑になる
  - _Requirements: 10.1, 10.2, 10.3, 10.4, 10.5, 10.6, 10.7_
  - _Boundary: MotorLockDetector_

- [ ] 5.2 (P) 保護② LiPo 低電圧保護を実装する
  - 電圧の読み値を**固定長の移動平均**（動的メモリ確保を行わない）で平滑し、警告閾値を下回った時点で警告状態を、停止閾値未満の継続が継続時間を超えた時点で停止状態を立てる
  - 復帰閾値を停止閾値より高く設定できるヒステリシスを持たせ、急加速による一時的な電圧降下では停止しないようにする
  - **読み値が得られないサンプルを移動平均へ取り込まない。** 欠測が継続時間を超えて続いた場合は、低電圧とは**別の理由**として停止する
  - 判定はすべてミリボルトの整数演算で行い、平均の丸めがプラットフォームに依存しないようにする
  - 観測可能な完了状態: 段階的な電圧低下で警告から停止へ遷移すること、一時的な降下では停止しないこと、復帰閾値まで戻って初めて復帰すること、欠測の継続が低電圧とは別の理由で停止させることを検証するホストテストが緑になる
  - _Requirements: 11.1, 11.2, 11.3, 11.4, 11.5, 11.8_
  - _Boundary: LowVoltageProtector_

- [ ] 5.3 (P) 保護③ バッテリ電圧を考慮した出力上限を実装する
  - 計測されたバッテリ電圧に応じて出力上限を決定する。**状態を持たない純関数**として実装し、遮断理由のビットを持たせない
  - 上限の算出式を固定仕様として決め打ちせず、**外部から差し替えられる形**にし、かつ**無効化もできる**ようにする
  - 上限が設定された最大出力を超えないことを常に保証する
  - **読み値が得られない場合に上限を無制限とせず、外部から与えられた安全側の既定上限を適用する**
  - 観測可能な完了状態: 電圧に応じて上限が下がること、無効化すると常に最大出力を返すこと、差し替えた式の戻り値が定義域へ収まること、欠測時に安全側の既定上限が適用されることを検証するホストテストが緑になる
  - _Requirements: 12.1, 12.2, 12.3, 12.5, 12.6_
  - _Boundary: PwmCeiling_

- [ ] 5.4 (P) 保護④ 指令ウォッチドッグを実装する
  - **最後に有効な指令を受けてからの経過時間だけ**を見て発火する。引数は時刻と「起動後に有効な指令を受けたか」の真偽値のみとし、**指令元に固有の情報を一切参照しない**

## 6. 指令入口と制御ステップの合成

- **タスク 1.1**: `pio test` はディレクトリ名が `test_` で始まるものだけをテストスイートとして認識する（`platformio/test/helpers.py` の `list_test_names` で確認済み）。design.md の File Structure Plan が示す `test/native/units/` `test/native/kinematics/` 等のディレクトリ名は**このままでは `pio test` に一切収集されない**。以降のタスク（2.x〜7.x）で `test/native/` `test/embedded/` 配下にディレクトリを作る際は、design.md の名称の先頭に `test_` を補う（例: `units/` → `test_units/`）。テストが「収集されず0件パスした」形の静かな失敗になり得るため要注意
- **タスク 1.1**: `firmware/CMakeLists.txt` で `EXTRA_COMPONENT_DIRS` を設定する際は `set(...)` ではなく `list(APPEND EXTRA_COMPONENT_DIRS ...)` を使うこと。PlatformIO の espidf ビルダーが `PROJECT_SRC_DIR`（`firmware/src`）を含む `-DEXTRA_COMPONENT_DIRS` を独自に注入しており、`set()` で上書きすると `Couldn't find the main target of the project!` で失敗する
- **タスク 1.1**: `firmware/test/embedded/` 配下の Unity テストは `extern "C" void app_main(void)` を定義する（`native` 側の素の `main()` とは異なる。FreeRTOS の起動コードが `app_main()` を直接呼ぶため）
- **タスク 1.2**: `CONFIG_ESP_WIFI_ENABLED` は classic ESP32 では実プロンプトを持たない Kconfig シンボル（`default y if SOC_WIFI_SUPPORTED` で無条件 `y`）であり、`sdkconfig.defaults*` へどう書いても無効。**本番ビルドから Wi-Fi を実際に除外するのは `firmware/CMakeLists.txt` の `COMPONENTS` allowlist**（`production` 環境限定で `list(APPEND COMPONENTS "src" "drivetrain_control" "__pio_env")`）であり、`sdkconfig.defaults.production` の `CONFIG_BT_ENABLED=n` は Bluetooth には効くが Wi-Fi には効かない別経路。`EXCLUDE_COMPONENTS` は `wpa_supplicant` 等の推移的 `PRIV_REQUIRES` により実際には除外できないことを実測済み（採用せず）
- **タスク 1.2**: `build_src_filter` は `framework = espidf` では PlatformIO のビルドスクリプトが無視する（未サポート）。テレオペ専用ソースの除外は代わりに、ビルドプロファイルの環境変数を `firmware/src/CMakeLists.txt` が読んで `src/teleop/*.cpp` の glob を出し入れする方式（`firmware/scripts/set_build_profile_cmake_env.py`）で実現している
- **タスク 1.2**: `production` の `COMPONENTS` allowlist は現在 `src` / `drivetrain_control` / `__pio_env`（PlatformIO 内部の必須ダミーコンポーネント）の3つのみ。**以降のタスクで `production` 側に実ペリフェラル（`esp_driver_pcnt` 等）を使うコードが増えたら、このリストへ明示的に追加する必要がある**（positive list のため、追加しないと該当コンポーネントがビルドから静かに落ちる）。`teleop` 環境はこの allowlist の対象外（デフォルトのコンポーネント自動探索のまま）
- **タスク 1.3**: `tests/firmware/test_firmware_boundaries.py` を追加。この環境の `uv` venv は既定（`--group dev` のみ）だと `numpy` を要する既存26ファイル（`sensing_foundation`/`flying_object_tracking`/`world_frame_calibration`）の収集に失敗する。**リポジトリ全体のリグレッションは `uv run --all-extras --group dev pytest tests -q` で回す**（`tests/firmware` 単体は `--all-extras` 不要）。これは本 Spec が持ち込んだ問題ではなく既存の環境構成に起因する
- **タスク 1.3**: design.md の FirmwareBoundaryCheck が挙げる残りの項目（禁止 include・禁止トークン・型トークン・依存方向・`test_support` 参照検出）はタスク8の範囲。タスク1.3はビルド構成（`platformio.ini`/`CMakeLists.txt`/`sdkconfig.defaults*`）のみを検査する
- **タスク 2.1**: `pio run -e teleop` の並行実行（フォアグラウンドとバックグラウンドを同時に走らせる等）は同一 `.pio/build/teleop` への同時書き込みでファイル破損を招く（`objdump: file format not recognized` 等の紛らわしいエラーになる）。**PlatformIO のビルドは常に1つずつ・フォアグラウンドで実行する**
