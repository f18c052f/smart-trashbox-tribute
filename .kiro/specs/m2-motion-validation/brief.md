# Brief: m2-motion-validation

## Problem

このプロジェクトの成否は**時間予算のほぼ一点**に集約される。

```
総飛行時間 0.6〜1.2s − システム側オーバーヘッド 0.2〜0.3s = 移動体の持ち時間 0.3〜1.0s
```

したがって性能は**最高速度ではなく短時間移動性能**で評価する
（`.kiro/steering/product.md`）。**0.4 / 0.6 / 0.9 秒で何 m 動けるか**が主評価軸（NFR-1）である。

この数字は現在**一つも実測されていない。** `docs/drivetrain-spec.md` §3.1 の
「無負荷 1.66 m/s」は理論周速であり、車体質量・転がり抵抗・スリップ・電圧降下・
ドライバ損失を含まない。**実車速度を保証しない値**として明記されている。

同時に、この実測値には**もう一つの行き先**がある。`trajectory_sim` のキャッチ可能領域は
現在すべて机上の `DrivetrainParams` で計算されている。**実測値をここへ戻さない限り、
シミュレータは永久に机上のままである。**

## Current State

- `teleop-bringup` により足回りが手動で走り、`ENCODER_COUNTS_PER_WHEEL_REV` が校正済みになっている
- ⚠️ ただし **M2a は定性確認であり、NFR-1 の合否判定に使えない。**
  「手で動かして速そうだった」は判断材料にならない。**ここで満足して M2b を省略しないこと**
- `trajectory_sim` 側の受け口は**既に完成している**:
  `python -m trajectory_sim --config X --output Y --drivetrain Z` で
  `DrivetrainParams` を JSON から注入でき、`configs/trajectory_sim/drivetrain-wheel60.json` が既に存在する。
  **新規実装ではなく、設定ファイルの書き換えで繋がる**

## Desired Outcome

- `requirements.md` M2b の記録項目 14 件がすべて実測・記録されている
- **NFR-1 が評価されている**（達成・未達のいずれであっても、根拠のある数値として）
- 実測値が `DrivetrainParams` へ換算され、`configs/trajectory_sim/` に反映されている。
  **シミュレータのキャッチ可能領域が、机上値ではなく実機由来の値で再計算できる**
- 性能不足だった場合に、`drivetrain-spec.md` §12 の調査順序に載せられる判断材料が揃っている

## Approach

**単なる最高速度試験ではなく「実車の短時間応答評価」として設計する。**

**指令はすべてスクリプト化する。** 人間の入力には再現性が無く、
記録項目10（同一指令を10回繰り返したときのばらつき）が成立しない
（`requirements.md` M2b、`tech.md` Testing「人間の入力で定量評価しない」）。

ログは**走行中 RAM にバッファし、走行後に吸い出す。**
走行中の Wi-Fi 送信は制御ループにジッタを乗せる（`tech.md` 標準5）。

## Scope

- **In**:
  - スクリプト化した指令シーケンスの実行機構（ESP32 側）
  - `requirements.md` M2b の記録項目 14 件の計測と記録
    - 静止 → 0.4 / 0.6 / 0.9 秒の移動距離（**主評価軸**）
    - 最高速度（**参考値。合否条件ではない**）
    - 発進時スリップ / 前後左右斜めの走行性能 / 目標地点への停止誤差
    - 同一指令 10 回程度のばらつき
    - バッテリ静止時電圧 / 急加速時の最低電圧
    - モータおよび TB67H450 の発熱 / 急停止時の転倒・浮き上がり
  - 走行ログの RAM バッファリングと走行後の吸い出し
  - **実測値 → `trajectory_sim.DrivetrainParams` への換算**と `configs/trajectory_sim/` への反映
  - NFR-1 の評価
- **Out**:
  - **NFR-7（キャッチ成功率）の判定** — プロジェクト唯一の最終合否条件だが、これは M4
  - 固定側との結合、通信 → M3（roadmap の Out）
  - 性能不足時の**対策の実施**（§12 の調査順序に従うが、対策そのものは本 Spec の外）
  - 手動操作による評価（→ `teleop-bringup`。**本 Spec は人間の入力を評価に用いない**）

## Boundary Candidates

- **指令シーケンスの実行と、その結果の評価** — 前者は ESP32、後者は WSL 上の解析
- **走行中の記録と、走行後の吸い出し** — 計測が計測対象を歪めない境界（`tech.md` 標準5）
- **実機の実測値と `DrivetrainParams` の間の換算** — 単位と定義を跨ぐ地点。
  ここがずれると、シミュレータの結論が静かに間違う

## Out of Boundary

- ⚠️ **部分指標の達成を完了と呼ばない。** NFR-1 は部分指標であり、
  満たしてもキャッチできるとは限らず、満たさなくてもキャッチできれば成功
  （`product.md` Success Criteria）
- ⚠️ **性能不足でも、すぐに高価なモータへ交換しない。**
  `drivetrain-spec.md` §12 の調査順序（スリップ → 電圧降下 → PWM/PID → 軽量化 → 重心 → 剛性 →
  **投擲レイアウト見直し** → 容量 → 最後にモータ）に従う。
  **手持ちの Nexus 14145 / 18020 は可能な限り流用する**

## Upstream / Downstream

- **Upstream**: `drivetrain-core`（制御ロジック）、`teleop-bringup`（動作する足回りと校正済みエンコーダ）
- **Downstream**: M3（結合。roadmap の Out だが、ここで OQ-22 と保護閾値が確定していることを前提とする）、
  および `trajectory-simulator` の再計算

## Existing Spec Touchpoints

- **Extends**: なし
- **Adjacent**: `trajectory-simulator` — **コードは変更しない。**
  `--drivetrain` の受け口が既に完成しているため、本 Spec の成果物は
  `configs/trajectory_sim/` に置く設定ファイルと、その換算根拠である。
  ⚠️ `DrivetrainParams` は**既定値を持たない**設計（要件4.3: 根拠のない固定値をモデルに埋め込まない）なので、
  全フィールドを明示的に埋める必要がある

## Constraints

- **実機必須。** 部品（特にホイール・ハブ）が揃い、`teleop-bringup` が完了していること
- **計測の再現性**: 指令はすべてスクリプト化する。人間の入力を評価に使わない
- **計測が計測対象を歪めないこと**: ログ送出は走行中に行わない。RAM バッファ ＋ 走行後の吸い出し
- **未実測の値を合否条件にしない**（`tech.md` 標準1）。
  過去に「最高速度 ≥ 1.5 m/s」「加速度 2〜3 m/s²」を要件に置いて根拠不足で撤回した経緯がある
  （`docs/decisions.md` D-1 / D-2）。**同じ失敗を繰り返さない**
- 安全: FR-9（モータロック・低電圧）は `teleop-bringup` で実装・発火試験済みであること
