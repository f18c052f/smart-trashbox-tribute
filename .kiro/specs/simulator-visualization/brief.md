# Brief: simulator-visualization

> **⚠️ この Spec は先送り可。**
> `original-features.md` の着手順序は柱1 を「1. Python の物理・予測モデル」と
> 「2. 可視化」に分けており、その理由を明記している:
> **「1 だけでも判断材料としては足りる。2 に時間をかけすぎて 1 の結論が出ない、という失敗を避ける」**
> `trajectory-simulator` の結論（キャッチ可能領域）が出るまで着手しないこと。

## Problem

`trajectory-simulator` が出力するのは JSON である。
数値のままではレイアウト設計の議論に使いにくく、
特に**キャッチ可能領域の境界**は図で見ないと判断しづらい。

また、このプロジェクトは現時点で**外から見て何も動かない**。
可視化は M1〜M4 の中で**唯一デモとして成立する部分**でもある。

## Current State

- `trajectory-simulator` が未着手（JSON の形も未定）
- 実装手段（Canvas / SVG / WebGL）が未確定（OQ-34）。**2D で足りる可能性が高い**
- コードは一行も存在しない

## Desired Outcome

- **キャッチ可能領域の図**が表示される（本命の出力）
- 軌跡アニメーションで、投擲・予測・移動体の追従が直感的に分かる
- 投擲レイアウトのパラメータを操作して、成立範囲の変化が見える
- 開発PC のブラウザで動く（**Pi 上では動かさない**）

## Approach

**Python が出力した JSON を読んで描画するだけ。** 常駐サーバを立てない。

開発時は静的ファイル配信（`vite` 等）で足り、HTTP エンドポイントを書く必要がない。
**Hono は使わない** — HTTP API を持つ用途（柱2b ライブダッシュボード）が保留されている以上、
使う理由が存在しない。

## Scope

- **In**:
  - `trajectory-simulator` が出力した JSON の読み込み
  - **キャッチ可能領域の可視化**（最優先）
  - 軌跡アニメーション
  - レイアウトパラメータの操作 UI（表示の切り替え程度）
  - 実装手段の決定（→ OQ-34）
- **Out**:
  - **本番にも存在するアルゴリズム。** 予測も物理も持たない
  - HTTP API・常駐サーバ
  - 実機のライブ表示（柱2b。保留 → OQ-38）
  - 実データのリプレイビューア（柱3。見送り → OQ-39）

## Boundary Candidates

- **データ読み込み**（JSON → 表示用モデル）
- **キャッチ可能領域の描画**
- **軌跡アニメーション**
- **操作 UI**

## Out of Boundary

- **予測アルゴリズムの複製。** ここが最大の禁止事項。
  ブラウザが持ってよいのは**描画と、結果を眺めるための軽量な補間だけ**
- 実機との接続
- Throw Record の再定義

## Upstream / Downstream

- **Upstream**: `trajectory-simulator`（JSON を出力する側）
- **Downstream**: なし（表示が終端）。
  ただし将来 柱2b / 柱3 を作る場合、表示レイヤの資産として再利用できる可能性がある

## Existing Spec Touchpoints

- **Extends**: なし
- **Adjacent**: `trajectory-simulator` の出力 JSON の形が唯一の接点。
  **JSON の形を先に固めてから着手する**

## Constraints

- **TypeScript 側に本番と重複するアルゴリズムを置かない**（`tech.md` 開発標準3）。
  これを破ると「シミュレータでは合っていたのに実機で外れる」の典型的な原因になる
- **表示レイヤを Raspberry Pi 上で動かさない。** 開発PC 上で動かす
- **Hono を使わない。** 使いたい技術に合わせて用途を作らない
- **2D で足りる可能性が高い。** WebGL を先に選ばない（→ OQ-34）
- **着手を急がない。** `trajectory-simulator` の結論が出ることが優先
