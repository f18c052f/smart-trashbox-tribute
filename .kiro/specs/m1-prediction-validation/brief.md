# Brief: m1-prediction-validation

## Problem

個々の部品（取得・キャリブレーション・検出・予測）が動いても、
**「予測が実際に当たるのか」「時間予算の想定が正しいのか」は分からない。**

特に `requirements.md §3` の時間予算表は**すべて設計上の想定値**であり、
なかでも**区間1「リリース〜検出開始」は完全に未検証**である。
ここが想定より長ければ移動体の持ち時間が直接削られ、
**プロジェクトの成立性そのものが変わる。**

## Current State

- 時間予算の想定: 総飛行時間 0.6〜1.2s、オーバーヘッド 0.2〜0.3s、持ち時間 0.3〜1.0s
- **いずれも実測されていない**
- M1 の実測項目7件が `requirements.md §8 M1` に定義済み
- OQ-27（Pi 4 で必要性能を達成できるか）は未判断

## Desired Outcome

`requirements.md §8 M1` の7項目が実測され、**時間予算表が実測値で更新されている**。

| # | 実測項目 | 対応 |
|---|---|---|
| 1 | 総飛行時間 | §3 想定 0.6〜1.2s |
| 2 | **リリース〜検出開始までの時間** | §3 区間1（**完全に未検証**） |
| 3 | 検出開始〜予測確定までの時間 | §3 区間2 / NFR-3 |
| 4 | 予測落下地点と実際の落下地点の誤差 | NFR-5 |
| 5 | 落下時刻の予測誤差 | NFR-6 |
| 6 | 狙い誤差（必要横移動量） | §3 想定 0.3〜0.8m |
| 7 | 何サンプル取れたか / 何サンプルで誤差が収束するか | FR-1 の「3」の妥当性 |

あわせて:
- 落下地点の予測が**プロットとして見える**（M1 の名前どおり「予測の可視化」）
- **OQ-27（Pi 4 継続可否）が判断できる**
- 誤差が「系統誤差（座標系ずれ）」か「予測誤差」かを**分離して報告できる**

## Approach

**既存部品を接続し、実投擲データを取って測るだけの Spec にする。** 新しいアルゴリズムを作らない。

```
sensing-foundation ──→ flying-object-tracking ──→ world-frame-calibration
                                                          |
                                                          v
                                                   prediction-core
                                                          |
                                                          v
                                        落下地点プロット / 実測レポート
```

可視化は**開発用**であり、本番処理の必須要件にしない。
また**表示レイヤを Pi 上で動かさない**（記録は Pi、集計と表示は開発PC）。

誤差の切り分けには `world-frame-calibration` の**検証ステップ**を先に実行する。
これにより系統誤差を分離してから予測誤差を評価できる。

## Scope

- **In**:
  - 各 Spec の成果物を接続したエンドツーエンドの実行
  - 実投擲データの取得（空き缶、固定レイアウト）
  - M1 実測7項目の測定と記録
  - **落下地点の可視化**（プロット）
  - 段階別レイテンシの集計（`development-environment.md §13.1`）
  - **時間予算表（`requirements.md §3`）の実測値による更新**
  - **OQ-27（Pi 4 継続可否）の判断**
  - OQ-05（NFR-7 の目標値）の判断材料の提示
- **Out**:
  - 移動体（M2 以降のすべて）
  - 予測アルゴリズムの改良。**まず測る。** 改良が要るなら別 Spec で行う
  - 柱3 投擲アーカイブ／ベンチマーク（→ OQ-39、本 Spec でデータが貯まってから再判断）

## Boundary Candidates

- **接続**（各部品のパイプライン化）
- **実験実行**（投擲レイアウトの固定と試行）
- **計測・集計**（7項目の測定とレポート）
- **可視化**（落下地点プロット）

## Out of Boundary

- **アルゴリズムの最適化。** 本 Spec は測定であって改善ではない。
  `development-environment.md §13.2` の改善順序は、実測して不足が分かってから適用する
- ハードウェアの置き換え判断の**実行**。判断材料を出し「継続 / 変更」を提示するところまで
- 移動体との結合（M3）

## Upstream / Downstream

- **Upstream**: `prediction-core` / `world-frame-calibration` / `flying-object-tracking`
  （間接的に `sensing-foundation`）
- **Downstream**:
  - **M2 / M3**（M1 の実測が時間予算の前提を確定させる）
  - `trajectory-simulator` の**較正**（M1 実測後に検出遅れ・予測誤差を反映する）
  - OQ-39（柱3 を作るかの再判断）

## Existing Spec Touchpoints

- **Extends**: なし
- **Adjacent**: `trajectory-simulator`。本 Spec の実測値が
  シミュレータの較正入力になる。**シミュレータを「参考」から「使える」へ昇格させるのは本 Spec**

## Constraints

- **可視化は開発用。** 本番処理の必須要件にしない。**Pi 上で動かさない**
- **計測 ON / OFF で end-to-end latency が有意に変化しない**ことを確認する。
  満たせない場合、計測は測定対象を歪めるため計測器としての価値を失う
- **実測前に `world-frame-calibration` の検証ステップを通す。**
  通っていない状態の誤差は、系統誤差か予測誤差か分離できない
- 投擲は**ばらつきが大きく再現性が低い。** 単発の結果で判断しない
- 実測結果が想定と食い違った場合、**時間予算表そのものを更新する**
  （数値を守るのではなく、根拠を更新する）
- 対象物は空き缶、投擲位置・方向は固定（初期 MVP で許容されている条件）
