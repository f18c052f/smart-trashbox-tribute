# Implementation Plan

> 本計画は `requirements.md`（要件1〜13 / 受入基準110件）と `design.md` に基づく。
>
> **タスク1〜8 は実機を必要としない。** 継ぎ目・真値・実測算出・帰属・判断・出力は、
> 上流3パッケージの**公開型の形**にしか依存しないため、公開型を模した最小ダブルと
> 合成した軌道だけで完成まで到達できる。

> かつ `sensing-foundation` / `flying-object-tracking` / `world-frame-calibration` の
> **実装が完了するまで着手できない**。この分割は「実機待ちの期間に何も進まない」事態を避けるための意図的なものである。
>
> ⚠️ **本 Spec が触るファイルは `src/m1_validation/**`、`tests/m1_validation/**`、自 Spec ディレクトリ、
> ルート `pyproject.toml` への追記、および `docs/requirements.md §3` だけである。**
> 上流3 Spec が並行して同じ `pyproject.toml` を追記するため、既存行を書き換えず追記のみを行う。
>
> ⚠️ **`docs/requirements.md §3` の更新（タスク9.7）は、M1 実測値が揃っていることをゲートとする。**

## 3. 1投擲の実行と記録

  - **追跡パイプラインは継ぎ目モジュールの生成入口から得る**（本モジュールは検出・追跡パッケージを

  - **検証ゲートを投擲を始める前に評価する**（走らせてから拒否しない）
  - 新しいサンプルが追加されるたびに予測を更新し、予測系列として保持する（予測の再計算は予測コアに委ねる）
  - 記録は予測コアの Throw Record スキーマをそのまま使い、**再定義しない**
  - 本 Spec 固有の情報（レイアウト要約・キャリブレーション要約・追跡の識別情報・由来情報・除外件数・
    検証済みか）を**拡張領域へ退避**し、上流が使う拡張キーを上書きしない
  - ⚠️ **予測コアの記録生成メソッドは拡張領域を引数に取らない**（記録の値オブジェクトは
    frozen かつ slots である）。拡張領域の付与は
    **`dataclasses.replace(record, extra={...})`**、または蓄積済みのサンプル列・予測系列からの
    **公開コンストラクタでの直接構築**のいずれかで行う。
    **`trajectory-simulator` は後者を採っており、両下流が同じ手段を採ること**を意図している。
    **予測コアには一切手を入れない**（迂回であって修正ではない）
  - 予測ごとに予測区間の計測を送出する。送出は完了を待たず、**予測経路の中で集計しない**
  - 入力元の種別を記録に残す
  - 観測可能な完了状態: 合成入力に対して1投擲が通り、記録を読み戻すと予測系列と由来情報が復元される
  - _Requirements: 2.3, 3.1, 3.2, 3.3, 3.4, 3.5, 3.6, 7.4_
  - _Depends: 2.1, 2.3_
  - _Boundary: ThrowRunner_

## 4. 真値と実測7項目

- [ ] 4. 真値と実測7項目

- [x] 4.1 真値の受け取りと導出を実装する
  - 実際の落下地点を外部ファイルから受け取り、**測り方の記述を必須**とする
  - 実際の落下時刻を、観測サンプル列が床面高さを**跨ぐ隣接2点の内挿**として求め、
    跨ぐ区間が無ければ欠測として扱う
  - リリース時刻を、推定軌道を観測開始より前へ**外挿**し、レイアウトのリリース高さに達する時刻として求める
  - 各真値に**求め方の種別と不確かさの目安**を併記する。外挿の不確かさは外挿区間の長さと残差から導く
  - 外部の合図が記録されている場合、外挿値との差を残す
  - 真値の入力を投擲の実行と分離し、**実行後に追記できる**ようにする
  - 記録に存在しない識別子の真値は警告として報告し、黙って捨てない
  - **求め方を書かずに数値だけを出すと誤差の出どころを議論できない**旨を docstring に明記する
  - 観測可能な完了状態: 既知の軌道から生成した記録に対し、内挿による落下時刻と外挿によるリリース時刻が
    解析解と一致し、跨ぐ区間が無い入力では欠測が返る
  - _Requirements: 4.1, 4.2, 4.3, 4.4, 4.5, 4.6, 4.7_
  - _Depends: 1.4, 3.1_
  - _Boundary: TruthDeriver_

- [x] 4.2 (P) 実測項目 1 / 2 / 6 を算出する
  - 総飛行時間を「実際の落下時刻 − リリース時刻」として算出する
  - **リリースから検出開始までの時間**を「最初の有効サンプルの観測時刻 − リリース時刻」として算出する
  - 狙い誤差を「待機位置 → 実際の落下地点の水平距離」として算出する
  - 真値の不確かさを結果へ伝播させ、求め方の種別を結果に含める

## Implementation Notes

> 各タスクで判明した、後続タスクが同じ失敗を繰り返さないための知見を1行ずつ足す。

- タスク4.2（⚠️ **フィーチャレベル検証で design.md を同期すること**）: `FlightResult` の不確かさを design.md の擬似コード（`uncertainty_ms: float | None` の1フィールド）から**項目別の3フィールド**（`total_flight_uncertainty_ms` / `release_to_detect_uncertainty_ms` / `aim_error_uncertainty_mm`）へ分割した。項目1 は2つの真値（内挿＋外挿）に依存し、項目2 は**観測された時刻そのもの**を終点とするため外挿のみに依存する——1フィールドに畳むと**項目1 の過小申告か項目2 の水増しのどちらかになる**。design.md 自身の FlightMetrics Implementation Notes（「項目2 は…求め方（外挿）と不確かさを結果に必ず含め」）と TruthDeriver Risks（「外挿の不確かさが区間1 の実測値をそのまま左右する」）はこの分離を要求しており、逸脱は**擬似コードのスケッチに対してであって設計意図に対してではない**。**ただし design.md の擬似コードは 1 フィールドのまま残っている。** タスク4.6 や 7.1 が擬似コードを見て実装すると食い違う。
- タスク4.2: **項目1 の不確かさは単純和（上界）である。** 二乗和にしないのは、`truth.py` の内挿の不確かさ（`hypot(曲率項, 残差項)`）と外挿の不確かさ（`残差 / 速度 × 増幅`）が**どちらも同じ `_final_residual_mm(record)` を分子に持つ**からである。共通成分を持つ2つの量に二乗和を使うと過小評価になる。**タスク4.1 の不確かさの導出式が変われば、ここも再検討が要る。**
- タスク4.2: **項目6 の不確かさは落下地点の実測不確かさのみで、待機位置の測り方の誤差を含まない**（`ThrowLayout` が不確かさを持たず、待機位置は設計値であるため）。実験計画側で待機位置の測り方を記録する必要がある。
- タスク4.2: `methods`（求め方の種別）は**項目キーではなく真値名キー**（`impact_point_world_mm` / `impact_time_ms` / `release_time_ms`）にした。項目キーにすると、項目1 が依存する2つの求め方（内挿と外挿）が片方に潰れる。
- タスク4.2: 4.1 の教訓（参照解を実装定数から組まない／許容差に実装出力を使わない）を適用済み。合成軌道の段だけでは残差がほぼ 0 になって単純和と二乗和を区別できないため、**代数の段でリテラル（3.0 + 20.0 = 23.0）との厳密一致を併置**している。「解析解と一致」の検査は、解析解が実装に追随しない形と、区別すべき差が実際に現れる入力の**両方**が要る。

- タスク4.1: **参照解を実装の定数から組むと、その定数を変えたとき参照解が一緒に動いて差が消える。** テストが `truth.FLOOR_HEIGHT_MM` を import して「解析解」を組んでいたため、**床面定数を 50.0 にしても 5.0 にしても34件すべて通っていた**（floor=50mm なら内挿値は真の z=0 解から 8.71 ms ずれる＝申告している不確かさの147倍）。タスク2.2 が警告した「0 を既定値にしたフィクスチャ」と同じ形の空振りが、今度は `FLOOR_HEIGHT_MM = 0.0` という**物理的に 0 でなければならない基準量**で再発した（本リポジトリ6件目）。**参照解はテスト局所のリテラルから組み、実装の定数が正しいことは独立した不変条件検査で固定する**（`test_floor_height_is_pinned_to_zero`）。
- タスク4.1: **許容差に実装自身の出力を使う検査は上限側に対して無力である。** `assert abs(error_ms) <= impact.uncertainty_ms` は過小申告しか捕まえず、**不確かさを100倍に膨らませても、線形内挿を中点固定に置き換えても通る**（7件目）。テスト定数だけから組み立てた絶対量を必ず併置すること。許容差 `rel=0.05` の根拠も書く——実装は弦の傾き（区間中点の瞬時速度）で割り、テストは接地点の瞬時速度で割るので差は最大 `g·dt/2` ≒ 1.4%。5% はその3.5倍の余裕であり、`dt²/8 → dt²/6` の式取り違え（+33%）は実際に落ちる。
- タスク4.1: **床面 z = 0 は本 Spec が決め直してはならない値である。** `prediction_core` も落下地点を `z = 0` との交点として定義しており（`src/prediction_core/impact.py`）、内挿による落下時刻と予測の落下時刻が違う平面を指すと、**その差は誤差ではなく定義の食い違いになる**。要件 5.5（落下時刻誤差の系列）が丸ごと偏る。
- タスク4.1（フィーチャレベル検証への申し送り）: **要件4.2 と `SeamConfig.floor_margin_mm = -50.0` が実データで干渉しうる。** 落下時刻の内挿には床面を跨ぐ隣接2点、すなわち床下側のサンプルが1点要る。しかし継ぎ目は `z < -50mm` を `BELOW_FLOOR` として除外し、接地時の鉛直速度は約 5.8 mm/ms なので 60fps でも1フレームで約96mm 落ちる。**サンプルが `(-50, 0]` に入るのは約半分の投擲だけ**で、残りは要件 4.2 どおり正当に欠測になる（要件は欠測を許容しており 4.1 の欠陥ではない）。**実測項目5 が系統的に欠測になりうる**ので、実験計画（タスク9.2）か `floor_margin_mm` の既定値の見直しで扱うこと。
