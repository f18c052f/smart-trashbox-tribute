# Requirements Document

## Project Description (Input)

既に仕様化された4つの部品（`sensing-foundation` / `flying-object-tracking` / `world-frame-calibration` /
実装済みの `prediction-core`）を**実データで一本に繋ぎ、実際に投げて測る**。
詳細な背景・スコープ・制約は [brief.md](./brief.md) を正とする。

### 誰の問題か

部品が個別に動いても、**「予測が実際に当たるのか」「時間予算の想定が正しいのか」は誰も知らない。**

- **プロジェクト全体**: `docs/requirements.md §3` の時間予算表は**すべて設計上の想定値**である。
  なかでも区間1（リリース〜検出開始）は**完全に未検証**であり、
  ここが想定より長ければ移動体の持ち時間が直接削られ、**プロジェクトの成立性そのものが変わる**
- **M2 / M3**: 移動体に残された時間（想定 0.3〜1.0 s）が確定しないと、必要な移動性能が決まらない
- **`trajectory-simulator`**: 検出遅れと予測誤差の実測値が入って初めて「参考」から「使える」へ昇格する
- **OQ-27**: Raspberry Pi 4 を継続するかが未判断のまま、後続のすべてが Pi 4 前提で進んでいる

### 現状

- 上流3 Spec（`sensing-foundation` / `flying-object-tracking` / `world-frame-calibration`）は
  **仕様化済み・未実装**。`prediction-core` のみ実装済みで `main` にマージされている
- 実機（Raspberry Pi 4 / RealSense D435）は**未セットアップ**（OS 未導入）
- `flying-object-tracking` は**意図的に `prediction_core` を import しない**設計であり、
  カメラ座標系の `CameraTrack` までしか作れない。
  **`CameraTrack` を `prediction_core.Sample` にする継ぎ目は、どの Spec も持っていない**
- M1 の実測項目7件は `docs/requirements.md §8 M1` に定義済み。**どれも実測されていない**

### 何が変わるべきか

- 取得 → 検出・追跡（カメラ座標系）→ World 変換 → 予測 → **落下地点のプロット**が、実データで通る
- M1 実測7項目が測られ、**時間予算表が実測値で更新される**
- 予測が外れたとき、**キャリブレーション誤差／検出誤差／予測誤差のどれなのかを切り分けて報告できる**
- **OQ-27（Pi 4 継続可否）が、実測前に固定した判定規則に基づいて判断される**
- OQ-05（NFR-7 の目標成功率と試行回数 N）の**判断材料**が揃う

## 追加入力: 確定済みの方針（A-1〜A-9）

> 本節は Project Description の続きであり、**入力として与えられた確定方針**である。
> 検証可能な形式の要件は下の [`## Requirements`](#requirements) を正とし、
> `A-n` は各要件の**出典参照**として使用する。

### A-1. 本 Spec は測定であって改善ではない

**新しいアルゴリズムを作らない。** 既存部品を接続し、実投擲データを取って測る。

- 予測アルゴリズムの改良は本 Spec の範囲外。**まず測る。** 改良が要るなら別 Spec で行う
- ただし `docs/development-environment.md §13.2` の**設定・ソフト改善（1〜8）は「測定条件の一部」**として扱う。
  ハードウェア判断（OQ-27）の前に適用し、**何を適用して何が変わったかを記録する**（`tech.md` 開発標準4）

### A-2. 継ぎ目（seam）の所有

**`CameraTrack` → `prediction_core.Sample` の変換は本 Spec が唯一の所有者である。**

`flying-object-tracking` が `prediction_core` を import しないのは設計上の意図であり、
「World 変換を検出側に書けなくする」ための構造的保証である
（`flying-object-tracking/design.md` Allowed Dependencies）。
その結果、変換は下流に残される。**本 Spec がそれを引き受ける。**

- 座標変換そのものは `world_frame_calibration` の `WorldTransform` を**呼ぶだけ**とし、再実装しない
- 時刻はカメラ側の `t_capture_ms` を**そのまま引き継ぐ**（再基準化しない）
- 単位は上流・下流ともに mm / ms で一致しており、**単位変換を挟まない**

### A-3. 誤差要因の分離 ★本 Spec の核

`docs/requirements.md §6.2` は「座標系が数 cm ずれていても症状は『予測が悪い』にしか見えない」と警告している。
Spec をキャリブレーション・検出・予測に分けたのは、**この3つを分離可能にするため**である。

**接続することで分離可能性を失ってはならない。**

- 実投擲の前に `world-frame-calibration` の**検証ステップを通す**。
  通っていない状態の誤差は、系統誤差か予測誤差か分離できない
- 誤差を1つの数値に潰さず、**帰属先（キャリブレーション／検出／予測）を付けて報告する**
- 帰属の判定規則は**実測前に固定し、結果とともに記録する**

### A-4. 実測7項目（`docs/requirements.md §8 M1`）

| # | 実測項目 | 対応 |
|---|---|---|
| 1 | 総飛行時間 | §3 想定 0.6〜1.2 s |
| 2 | **リリース〜検出開始までの時間** | §3 区間1（**完全に未検証**） |
| 3 | 検出開始〜予測確定までの時間 | §3 区間2 / NFR-3 |
| 4 | 予測落下地点と実際の落下地点の誤差 | NFR-5 |
| 5 | 落下時刻の予測誤差 | NFR-6 |
| 6 | 狙い誤差（必要横移動量） | §3 想定 0.3〜0.8 m |
| 7 | 何サンプル取れたか / 何サンプルで誤差が収束するか | FR-1 の「3」の妥当性 |

**項目2・4・5 は「実際の値」を必要とする。** 実際のリリース時刻・落下地点・落下時刻の
**求め方そのものを定義し、その不確かさを併記する**ことが本 Spec の要件に含まれる。
求め方を書かずに数値だけ出すと、誤差の出どころを後から議論できない。

### A-5. 逐次予測への読み替え（`prediction-core/requirements.md` D-1）

`prediction-core` は**3点で初回予測 → 駆動開始 → 以降更新**という逐次予測を実装している。
一方 `docs/requirements.md §3` の時間予算表は「予測が1回確定 → 送信 → 駆動開始」という**単発予測モデル**のままである。

- 区間2 は「検出開始〜**初回予測**」と読み替える必要がある
- **この読み替えと、実測値による表の更新は本 Spec が行う**（roadmap の ⚠️ が本 Spec を名指ししている）
- **実測値が揃う前に表を書き換えない。** 数値を守るのではなく、根拠を更新する

### A-6. OQ-27（Pi 4 継続可否）★

- **ハードウェアを判断する前に、設定・ソフトウェアで詰める**（`development-environment.md §13.2`）
- **判定規則を実測前に固定する**。上流 Spec（`sensing-foundation` / `flying-object-tracking`）が
  同じ規律（判定基準を実測前に確定し、結果とともに記録する）を採っており、それに揃える
- 判定は**絶対値の目標を置かず**、同一測定内で得た量どうしの相対比較とばらつきで定義する
  （`tech.md` 開発標準1「未実測の数値を合否条件にしない」）
- 判断は**単発の投擲では行わない**。投擲はばらつきが大きく再現性が低い

### A-7. OQ-05（NFR-7 の目標成功率と試行回数 N）

**決着させない。判断材料を出すところまで。**
OQ-05 は「M1・M2 実測後」に決めると `open-questions.md` が定めており、
M1 単独では移動体性能が入らないため成功率を決められない。

出せる材料:
- 予測誤差の分布から見た「NFR-5 の窓（例: ±67.5 mm）に予測が入る割合」＝**予測側から見た成功率の上限**
- 誤差のばらつきから逆算した、**所望の信頼区間幅を得るために必要な試行回数 N**

### A-8. 可視化は開発用

- **本番処理の必須要件にしない。** 落ちても本番経路が止まらない
- **Pi 上で動かさない**（`structure.md` / `original-features.md` 制約2）。記録は Pi、集計と表示は開発PC
- 表示レイヤに**アルゴリズムを持たせない**（`tech.md` 開発標準3）

### A-9. 実験条件の固定

- 対象物は**空き缶（φ65 mm 程度の剛体）**に固定（OQ-02 の M1 仮値。決定済み）
- 投擲位置・投擲方向・ゴミ箱待機位置を**固定する**（NFR-1 が初期 MVP として許容している条件）
- この固定内容は **OQ-01（投擲レイアウトの定義）の仮値**であり、本 Spec の実測で確定に近づける

## Introduction

`m1-prediction-validation` は、既に仕様化・実装された部品を**実データで一本に繋ぎ、実際に投げて測る** Spec である。

本 Spec が持つ固有の責務は3つある。
第一に、**`CameraTrack`（カメラ座標系）→ `prediction_core.Sample`（World 座標系）という継ぎ目**である。
上流の `flying-object-tracking` はこの変換を持てない設計になっており、この継ぎ目は本 Spec にしか存在しない。
第二に、**誤差の帰属**である。接続によって「予測が悪い」という一つの症状に潰れてしまうことを防ぎ、
キャリブレーション・検出・予測のどこに原因があるかを切り分けて報告する。
第三に、**判断**である。M1 完了判定、時間予算表の更新、OQ-27（Pi 4 継続可否）の決着、OQ-05 の材料提示。

本 Spec は**新しいアルゴリズムを作らない**。接続・実験・計測・集計・可視化・判断だけを行う。
判定規則はすべて**実測前に固定し、結果と同じ場所に記録する**。

## Boundary Context

- **In scope**:
  - カメラ座標系の点列を World 座標系の予測入力へ変換する継ぎ目（本 Spec 固有）
  - 取得 → 検出・追跡 → World 変換 → 逐次予測を1投擲として実行する経路
  - キャリブレーション検証の**先行実施の強制**と、未検証状態での実測の拒否
  - 実際の落下地点・落下時刻・リリース時刻の**求め方の定義**と記録
  - M1 実測7項目の算出と、ばらつきを伴う集計
  - 誤差の帰属（キャリブレーション／検出／予測）と、その判定規則
  - 段階別レイテンシ（`development-environment.md §13.1`）の集計と、計測の非侵襲性の確認
  - 落下地点の可視化（開発用・開発PC 上）
  - OQ-27 の判定規則の固定と適用、および結論の記録
  - OQ-05 の判断材料の提示（**決着させない**）
  - `docs/requirements.md §3`（時間予算表とそこから導出される値）の実測値による更新
- **Out of scope**:
  - フレーム取得・記録・再生・構造化ロギング基盤（→ `sensing-foundation`）
  - 検出方式・追跡・カメラ座標系での3D位置算出（→ `flying-object-tracking`）
  - 床平面推定・World frame の確立・変換の実装（→ `world-frame-calibration`）
  - 予測アルゴリズム・Throw Record スキーマ（→ `prediction-core`。実装済み・変更しない）
  - 予測アルゴリズムの改良・置き換え（測って不足が分かってから別 Spec で）
  - 移動体に関するすべて（M2 / M3 / M4）、ESP32 への送信、テレオペ
  - 投擲アーカイブ／ベンチマーク（→ OQ-39。本 Spec でデータが貯まってから再判断）
  - ハードウェアの**置き換えの実行**。「継続／変更」の判断材料と結論の提示までを持つ
  - ブラウザ可視化（→ `simulator-visualization`）
- **Adjacent expectations**:
  - `sensing-foundation` が live / recorded / simulated の入力層と、NDJSON の構造化ログ・
    セッション記録・Throw Record の保存を提供する。本 Spec は**予約 stage と衝突しない自分の stage を足す**
  - `flying-object-tracking` が**カメラ座標系のまま**点列を渡す。World 値を混ぜない
  - `world-frame-calibration` が変換と**独立検証レポート**を提供する。
    本 Spec は検証レポートを誤差帰属の材料として使い、**検証の合否判定そのものは上流の定義に従う**
  - `prediction-core` は入力を `(t, x, y, z)` の列だけに限定する。
    **RealSense 固有の型をこの入口へ漏らさない**
  - `trajectory-simulator` は本 Spec の実測値を較正入力として受け取る（下流）。
    本 Spec は同 Spec に依存しない

## Requirements

### Requirement 1: 継ぎ目 ― カメラ座標系の点列を予測入力へ変換する

**Objective:** As a M1 の実施者, I want カメラ座標系の追跡結果を World 座標系の予測入力へ、単一の明示された経路だけで変換できること, so that 上流が意図的に持たなかった変換の責任所在が一箇所に定まり、座標系の取り違えが構造的に起きなくなる

_出典: A-2_

#### Acceptance Criteria

1. When カメラ座標系の点列とキャリブレーション結果が与えられた場合, the M1検証ハーネス shall 各点を World 座標系へ変換し、時刻付き3次元位置サンプルの列を生成する。
2. The M1検証ハーネス shall 座標変換を `world-frame-calibration` が提供する変換に委ね、変換式を独自に実装しない。
3. The M1検証ハーネス shall 各点の観測時刻を上流が与えた値のまま引き継ぎ、時刻の基準を変更しない。
4. If 点列の座標系がカメラ座標系でない場合, then the M1検証ハーネス shall サンプルを生成せずに、座標系不一致として識別可能な理由で失敗する。
5. If 点列の受け渡し形式版またはキャリブレーション結果の形式版が既知のものでない場合, then the M1検証ハーネス shall 内容を推測して読まずに、未知形式として失敗する。
6. If キャリブレーション結果が記録されたストリーム設定または内部パラメータと、実行時のそれらが一致しない場合, then the M1検証ハーネス shall 設定不一致として失敗する。
7. When 個々の点が欠測・床面下・観測品質下限未満のいずれかに該当する場合, the M1検証ハーネス shall その点をサンプルから除外し、除外理由ごとの件数を残す。
8. The M1検証ハーネス shall 生成した各サンプルに、その元となった観測点の品質情報（有効画素数・奥行きのばらつき・競合候補数・フレーム欠落の有無）を対応付けて保持する。
9. The M1検証ハーネス shall 予測入力へカメラ固有の型・カメラパラメータ・画素座標を持ち込まない。
10. When 同一の内部パラメータ・画素座標・生の奥行き値が与えられた場合, the M1検証ハーネス shall 追跡側の逆投影経路とキャリブレーション側の逆投影経路が完全に同一の結果を返すことを検証し、一致しない場合は失敗として報告する。

### Requirement 2: キャリブレーション検証の先行と、未検証状態の拒否

**Objective:** As a M1 の実施者, I want 座標系の検証を通していない状態では実測が進まないこと, so that 得られた誤差が系統誤差か予測誤差か分離できない状態のデータを作らずに済む

_出典: A-3_

#### Acceptance Criteria

1. While キャリブレーション結果が検証を通過していない状態, the M1検証ハーネス shall 既定でサンプル生成と実測の実行を拒否する。
2. Where 未検証のまま実行することが明示的に許可された場合, the M1検証ハーネス shall 実行を許可したうえで、生成物すべてに未検証である旨の印を付け、レポートに「誤差の帰属ができない」旨を明示する。
3. The M1検証ハーネス shall 使用したキャリブレーション結果の識別子・検証状態・検証時刻を、投擲ごとの記録に残す。
4. When 実測の集計を行う場合, the M1検証ハーネス shall 検証レポートの平均オフセット・ばらつき・距離帯別誤差を、誤差帰属の材料として取り込む。
5. If 実測期間中にキャリブレーション結果が入れ替わった場合, the M1検証ハーネス shall 投擲を識別子ごとに分けて集計し、混在したまま平均しない。

### Requirement 3: 1投擲の実行と記録

**Objective:** As a M1 の実施者, I want 1回の投擲を取得から予測まで通して実行し、後から再現できる形で記録できること, so that 実機を毎回動かさずに集計・改善・再検証を繰り返せる

_出典: A-1, A-2_

#### Acceptance Criteria

1. When 入力元と設定が与えられた場合, the M1検証ハーネス shall 取得・検出・追跡・座標変換・逐次予測を通して1投擲を実行する。
2. The M1検証ハーネス shall 新しいサンプルが追加されるたびに予測を更新し、予測系列として保持する。
3. The M1検証ハーネス shall 1投擲を1レコードとして記録し、記録形式は `prediction-core` が定めた Throw Record スキーマに従う。
4. The M1検証ハーネス shall Throw Record のスキーマを再定義せず、本 Spec 固有の情報は拡張用の領域へ退避する。
5. The M1検証ハーネス shall 記録に、セッション記録・キャリブレーション結果・追跡結果への対応付けを残し、生データへ辿れるようにする。
6. The M1検証ハーネス shall 入力元の種別（実機 / 記録再生 / 合成）を記録に残す。
7. When 同一の記録済み入力に対して再実行した場合, the M1検証ハーネス shall 同一の予測系列と同一の実測値を返す。
8. If 投擲中に追跡が成立しなかった場合, the M1検証ハーネス shall その試行を失敗として理由付きで記録し、成功した試行の集計から除外する。

### Requirement 4: 実際の値（真値）の定義と記録

**Objective:** As a M1 の実施者, I want 実際の落下地点・落下時刻・リリース時刻の求め方が定義され、その不確かさが併記されること, so that 予測誤差の数値が「何と比べた誤差なのか」を後から議論できる

_出典: A-4_

#### Acceptance Criteria

1. The M1検証ハーネス shall 実際の落下地点を、World 座標系で表した実測値として投擲ごとに受け取り、測り方の記述を必須とする。
2. The M1検証ハーネス shall 実際の落下時刻を、観測点列が床面高さを跨ぐ区間の内挿として求め、跨ぐ区間が存在しない場合は欠測として扱う。
3. The M1検証ハーネス shall リリース時刻を、推定軌道を観測開始より前へ外挿し、投擲レイアウトが定めるリリース高さに達する時刻として求める。
4. The M1検証ハーネス shall 各真値について、求め方の種別（実測 / 内挿 / 外挿）とその不確かさの目安を併記する。
5. Where リリース時刻を独立に示す外部の合図が記録されている場合, the M1検証ハーネス shall 外挿による推定値と突き合わせ、その差をレポートに残す。
6. If 真値が欠測している場合, the M1検証ハーネス shall その真値を必要とする実測項目のみを欠測とし、他の項目の集計を止めない。
7. The M1検証ハーネス shall 真値の入力を投擲の実行とは分離して受け付け、実行後に追記できるようにする。

### Requirement 5: M1 実測7項目の算出

**Objective:** As a プロジェクトの意思決定者, I want `docs/requirements.md §8 M1` の7項目が実測され、ばらつきとともに提示されること, so that 時間予算の想定が正しいかを事実に基づいて判断できる

_出典: A-4, A-9_

#### Acceptance Criteria

1. The M1検証ハーネス shall 総飛行時間を、リリース時刻から実際の落下時刻までとして投擲ごとに算出する。
2. The M1検証ハーネス shall リリースから検出開始までの時間を、リリース時刻から最初の有効サンプルの観測時刻までとして算出する。
3. The M1検証ハーネス shall 検出開始から初回予測が成立するまでの時間を算出し、**単発予測ではなく初回予測を基準とする**ことを結果に明示する。
4. The M1検証ハーネス shall 予測落下地点と実際の落下地点の水平距離の誤差を、予測が更新されるたびの系列として算出する。
5. The M1検証ハーネス shall 予測落下時刻と実際の落下時刻の差を、予測が更新されるたびの系列として算出する。
6. The M1検証ハーネス shall 狙い誤差を、投擲レイアウトが定める待機位置から実際の落下地点までの水平距離として算出する。
7. The M1検証ハーネス shall 1投擲で得られた有効サンプル数と、誤差が収束したとみなせる最小サンプル数を算出する。
8. The M1検証ハーネス shall 収束の判定規則を実測前に固定し、算出結果と同じ場所にその規則を記録する。
9. When 複数投擲を集計する場合, the M1検証ハーネス shall 各項目について代表値とばらつき、および試行数を併記する。
10. If 集計対象の試行数が設定された下限に満たない場合, the M1検証ハーネス shall 結果を暫定として印を付け、判断に用いてよい状態としない。
11. The M1検証ハーネス shall 実測値を、対応する `docs/requirements.md` の想定値と並べて提示する。

### Requirement 6: 誤差要因の分離（帰属）★

**Objective:** As a M1 の実施者, I want 予測が外れたときに原因をキャリブレーション・検出・予測へ切り分けられること, so that 「予測が悪い」という一つの症状に潰れて原因究明に時間を奪われる事態を避けられる

_出典: A-3_

#### Acceptance Criteria

1. The M1検証ハーネス shall 誤差の帰属判定規則を実測前に固定し、判定結果と同じ場所にその規則を記録する。
2. The M1検証ハーネス shall 落下地点の誤差を、投擲群に共通する偏り成分と、投擲ごとのばらつき成分に分解する。
3. When 共通の偏り成分が存在する場合, the M1検証ハーネス shall その向きが World 座標系に固定されているか、カメラ視線方向に沿っているかを判別し、判別結果を帰属の根拠として提示する。
4. When 共通の偏り成分がキャリブレーション検証レポートの平均オフセットと整合する場合, the M1検証ハーネス shall 当該成分をキャリブレーション由来として報告する。
5. When 共通の偏り成分がカメラ視線方向に沿い、キャリブレーション検証では偏りが認められない場合, the M1検証ハーネス shall 当該成分を検出由来（対象物表面の観測に伴う系統的な偏り）の候補として報告する。
6. When ばらつき成分が観測品質から導いた予測のばらつきの範囲に収まる場合, the M1検証ハーネス shall 当該成分を観測ノイズ由来として報告する。
7. When ばらつき成分が観測由来の範囲を超え、かつフィットの残差が大きい場合, the M1検証ハーネス shall 当該成分をモデル由来（予測）として報告する。
8. The M1検証ハーネス shall 観測品質に基づく予測のばらつきを、観測サンプルを再抽出して予測をやり直す方法で見積もる。
9. The M1検証ハーネス shall 帰属の結果を、単一の合計誤差ではなく成分ごとの内訳として提示する。
10. If 帰属を決めきれない場合, the M1検証ハーネス shall 「判別不能」を正常な結果として報告し、無理に一つの原因へ割り当てない。
11. The M1検証ハーネス shall 距離帯ごとの誤差を提示し、遠方でのみ誤差が大きい場合を奥行き計測の距離特性として読み分けられるようにする。

### Requirement 7: 段階別レイテンシの集計と、計測の非侵襲性

**Objective:** As a プロジェクトの意思決定者, I want 各段階の所要時間が分解されて集計され、かつ計測自体が測定対象を歪めないこと, so that どこが律速かを根拠に判断でき、その根拠自体が信用できる

_出典: A-6_

#### Acceptance Criteria

1. The M1検証ハーネス shall `development-environment.md §13.1` の項目（取得 fps・実処理 fps・CPU 使用率・メモリ使用量・取りこぼし・段階別レイテンシ・end-to-end レイテンシ）を集計する。
2. The M1検証ハーネス shall end-to-end レイテンシを、観測時刻からその観測に基づく予測が得られるまでとして定義し、定義を結果に明示する。
3. The M1検証ハーネス shall 上流 Spec が記録した段階を、集計側の改修なしに読み取れるようにする。
4. The M1検証ハーネス shall 自身が担当する予測区間の計測点を追加し、上流が予約した段階名と衝突させない。
5. The M1検証ハーネス shall 計測の有効・無効を実行時に切り替えられるようにする。
6. When 計測の有無を比べる場合, the M1検証ハーネス shall 同一入力・同一設定・同一時間で条件を交互に入れ替えて実行する。
7. The M1検証ハーネス shall 「有意に変化しない」の判定基準を、上流 Spec が用いている基準と同じ形（無効条件自身のばらつきに対する相対量）で定義する。
8. If 計測の有無で有意な差が認められた場合, the M1検証ハーネス shall 当該条件で得た計測結果を無条件に有効なものとして扱わない旨を結果に明示する。
9. The M1検証ハーネス shall 集計処理を実機上で常時実行することを前提としない。

### Requirement 8: 落下地点の可視化

**Objective:** As a M1 の実施者, I want 予測落下地点と実際の落下地点が図として見えること, so that 数値表では気付けない偏りや外れ値を目で捉えられる

3. The M1検証ハーネス shall 位置精度の許容窓を図中に描き、許容窓の値が暫定目標値である旨を図に明示する。

### Requirement 9: OQ-27（Raspberry Pi 4 継続可否）の判断 ★

**Objective:** As a プロジェクトの意思決定者, I want Pi 4 を継続するかどうかが、実測前に固定した規則と証跡に基づいて判断されること, so that 「なんとなく遅いから買い替える」という判断を避けられる

_出典: A-6_

#### Acceptance Criteria

1. The M1検証ハーネス shall OQ-27 の判定規則を実測前に固定し、判定結果と同じ場所にその規則を記録する。
2. The M1検証ハーネス shall 判定を絶対値の目標ではなく、同一測定内で得た量どうしの相対比較とばらつきによって定義する。
3. While `development-environment.md §13.2` の改善項目に未適用のものが残っている状態, the M1検証ハーネス shall 「Pi 4 では不足」という判定を出さない。
4. The M1検証ハーネス shall 適用した改善項目とその前後の計測値を記録する。
5. The M1検証ハーネス shall 段階別レイテンシの内訳から律速段階を特定し、判定の根拠として提示する。

10. If 実機以外の入力しか得られていない場合, the M1検証ハーネス shall 結果を実機の結論として扱わない旨を明示する。
11. The M1検証ハーネス shall ハードウェアの置き換えを実行せず、判断材料と結論の提示までにとどめる。

### Requirement 11: 時間予算表の更新

**Objective:** As a プロジェクトの意思決定者, I want `docs/requirements.md §3` の時間予算表が実測値と逐次予測の前提で更新されること, so that 後続のマイルストーンが想定値ではなく実測値の上で計画される

## 用語

| 用語 | 定義 |
|---|---|
| **継ぎ目（seam）** | カメラ座標系の点列を World 座標系の予測入力へ変換する接点。本 Spec が唯一の所有者 |
| **真値** | 実際の落下地点・落下時刻・リリース時刻。求め方と不確かさを必ず併記する |
| **帰属（attribution）** | 観測された誤差を、キャリブレーション・検出・予測のどれに由来するかへ割り当てること |
| **共通の偏り成分** | 投擲群に共通して現れる誤差ベクトル。系統誤差の候補 |
| **ばらつき成分** | 共通の偏りを除いた投擲ごとの残り。観測ノイズまたはモデル由来 |
| **初回予測** | 最小サンプル数に達した時点で最初に得られる有効な予測。時間予算の区間2 の終端 |
