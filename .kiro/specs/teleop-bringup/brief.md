# Brief: teleop-bringup

## Problem

組み立てた足回りに初めて通電するとき、実際に起きるのは性能不足ではなく
**配線・回転方向・エンコーダ符号のバグ**である（`docs/requirements.md` M2）。

そして**それを自動計測スクリプトでデバッグするのが、最も切り分けの難しい状況**になる。
計測スクリプトは「逆運動学が正しい」「モータの回転方向とホイール割当が合っている」
「エンコーダの符号が合っている」ことを暗黙の前提にしているが、
**その前提を確認する段階がこれまで存在しなかった。**

もう一つ、この段階にしかできないことがある。**FR-10（通信途絶フェイルセーフ）の発火試験**である。
FR-10 が守るべき状況（固定側が落ちる・Wi-Fi が切れる）は M3 で意図的に再現しにくく、
しかも**失敗すると機体が暴走する**。テレオペなら**コントローラの電源ボタンを押すだけ**で
同じ経路を発火させられる。`requirements.md` はこれを **「M2a の隠れた主目的」** と呼んでいる。

## Current State

- `drivetrain-core` が純ロジック（逆運動学・速度PID・保護①〜④・オドメトリ）とペリフェラルのポート定義を提供する
- **ペリフェラルの実装は存在しない。** ESP32 上で実際にエンコーダを数え、PWM を出し、電圧を読むコードが要る
- 部品状況（2026-08-30 更新）: **駆動系の部品はすべて手元にある。**
  ⚠️ ただし**ホイール／ハブは Nexus 純正品ではなく 14145 / 18020 相当品**であり、
  実効ホイール径・ハブ穴の D 形状は現物採寸で確定させる（`chassis-mechanism` が担当）
- **整備スタンド（ホイールを浮かせる台）が未製作。** M2a-0 は接地させずに行うため、
  接地走行より先にこれが要る（`docs/bom.md` §E）。
  ⚠️ **製作は `chassis-mechanism` の所有へ移した**（2026-08-30）。本 Spec は**使う側**である
- ⚠️ **電気系ブリングアップ（`drivetrain-spec.md` §10.2 の E-1〜E-4）が未実施。**
  安定化電源での導通確認・可変抵抗によるドライバ開ループ確認・DualSense の疎通確認は
  **M2a-0 より前に必ず行う MUST 手順**であり、本 Spec がこれを持つ
- ⚠️ **ピンアサインが存在しない**（2026-09-07 discovery で確認）。
  `drivetrain-spec.md` は §7 / §9.1 を通して一貫して「ESP32 GPIO」「ADC1 系 GPIO」としか書いておらず、
  **GPIO 番号は全ブランチを通して1件も無い。** `firmware/` にもピン定数は存在しない
  （`drivetrain-core` はポート宣言のみを持つ設計であり、これは**正しい状態**である）。
  **ペリフェラルアダプタを書き始める直前の前提がここで欠けている**
- ⚠️ **結線が単一の正を持たない。** 内容自体は §7（線色と系統）・§8（電源系統とヒューズ）・
  §9.1（LiPo 分圧）に**散在している**が、統合された結線表が無い。
  E-0（通電前の線色確認）が参照すべき対象が存在しないことを意味する
- `docs/drivetrain-spec.md` §10.1 にテレオペの実装方針があるが、
  **第一候補（DualSense → BT Classic → ESP32 直結）は実機未検証**（OQ-16）

## Desired Outcome

- 人が DualSense で機体を手動走行させられる
- **M2a-0 / M2a-1 / M2a-2 の3段が、危険度の低い順に完了している**
- **安全機能4種すべての発火試験が済んでいる** — デッドマン解放 / コントローラ電源断 /
  ホイール拘束 / バッテリ消耗
- `ENCODER_COUNTS_PER_WHEEL_REV` が**実測校正されている**（未校正のまま M2b へ進むと、
  移動距離の実測値そのものが信用できない）
- `m2-motion-validation` が「計測だけ」に集中できる状態になる

## Approach

`drivetrain-spec.md` §10.1.1 の第一候補（**DualSense → BT Classic → 移動体 ESP32 に直結**）を採る。

PC も、未確定の Pi → ESP32 通信方式（OQ-29）も切り分けの輪に入らないため、
**足回り単体を裸で検証できる**のが理由である。動作しない場合は PC 経由（Serial / UDP）へ落とす。

実施は**危険度の低い順**に3段（`requirements.md` M2a）。**いきなり接地走行させない。**

| 段 | 状態 | 確認すること |
|---|---|---|
| M2a-0 | 台に乗せ**ホイールを浮かせる**。1輪ずつ回す | 回転方向とハーネス対応 / エンコーダ A/B の符号 / `ENCODER_COUNTS_PER_WHEEL_REV` の実測校正 |
| M2a-1 | 接地。**オープンループ**（PWM 直接指令） | 逆運動学の符号 / 発進時スリップ / 発熱 / 急加速時の電圧降下 / 重心・転倒しやすさ |
| M2a-2 | 接地。**速度PID を経由** | PID ゲインのラフ合わせ / オドメトリのドリフト |

M2a-2 では**手動で正方形を走らせて出発点との誤差を測る。**
これで FR-6 オドメトリのドリフトと逆運動学の妥当性を、**固定側を一切使わずに**検証できる。

## Scope

- **In**:
  - **結線図とピンアサインの確定**（**ハード不要。本 Spec の最初の段**。2026-09-07 discovery で本 Spec の所有と決定）
    - ESP32 の GPIO 割当を**単一の正**として確定する: PCNT ×3（A/B 相 = 6本）/ LEDC（PWM・方向）/
      ADC1（LiPo 電圧監視。⚠️ **E-3 の可変抵抗は別チャンネル**）
    - ⚠️ **機械検査できる不変条件として固定する。** 実機に焼くまで気づかない種類の誤りだからである:
      同一 GPIO の二重割当が無いこと / **ADC1 限定**（ADC2 は Wi-Fi 動作中に使えない）/
      **GPIO34〜39 へ出力を割り当てない**（入力専用・内部プルアップ無し）/
      ストラッピングピンと Flash 用ピンの回避 / PCNT ユニット数・LEDC チャネル数の上限
    - §7 / §8 / §9.1 に散在する結線を統合し、**E-0（通電前の線色確認）が参照できる単一の結線表**にする。
      ⚠️ **黒＝エンコーダ GND / モータ電源−＝白**という §7 の罠を表の側で明示する
    - ⚠️ **A 相／B 相が黄か緑かは仕様に記載が無く実測で決まる**（§11 #16）。
      **結線表は「実測で確定する欄」を持った形にする** — 未確定を確定として書かない
  - ESP32 ペリフェラルアダプタの実装: PCNT ×3（エンコーダ）/ LEDC（PWM・方向）/ ADC1（LiPo 電圧監視）
  - Bluepad32 の統合、DualSense のペアリング・再接続・リンクキー消去手段
  - 入力マッピング（左スティック→並進、右スティックX→回転、**デッドマン必須**、D-pad で輪単体選択）
  - デッドゾーン・入力カーブ・速度スケール上限（初期 30% 程度から段階的に上げる）
  - `teleop` ビルド環境と本番ビルドの排他（ビルドフラグ）
  - M2a-0 / M2a-1 / M2a-2 の実施と記録
  - `ENCODER_COUNTS_PER_WHEEL_REV` の実測校正
  - 安全機能4種の発火試験
  - テレオペ走行のログ（**走行1回 = 1レコード**として Throw Record とは別扱いにする見込み）
  - **【MUST】電気系ブリングアップ E-1〜E-4**（`drivetrain-spec.md` §10.2）。
    ⚠️ **M2a-0 より前に、この順序で必ず実施する。順序を入れ替えない**:
    - **E-1** 電流制限つき**安定化電源**での導通・短絡確認。⚠️ **LiPo を挿さない**
    - **E-2** モータを**ドライバを介さず**安定化電源へ直結し、回転方向とハーネス対応を確認。
      3個の**無負荷電流が揃うこと**（個体差の外れ値をここで発見する）
    - **E-3** **可変抵抗**でデューティを変えながらドライバ経由で回す**開ループ**確認。
      ⚠️ AE-TB67H450 の入力は PWM のため、可変抵抗は **ADC1 で読んで LEDC デューティへ写す
      最小ファーム**と組み合わせる（PCNT も PID も使わない）
    - **E-4** **DualSense（PS5 コントローラ）の疎通確認**。⚠️ **モータ非接続**（ログ出力のみ）で先に行う。
      OQ-16 の判断材料をここで得る
- **Out**:
  - 逆運動学・速度PID・保護①〜④の**ロジック本体** → `drivetrain-core`
  - 定量計測と NFR-1 の評価 → `m2-motion-validation`
  - 固定側 → 移動体の通信、ジオフェンス、物理的な非常停止手段 → M3（roadmap の Out）

## Boundary Candidates

- **ペリフェラルアダプタと純ロジックの境界** — `drivetrain-core` が定義したポートを実装する側。
  ここに判断ロジックを持ち込むと、ホストテストの範囲が痩せる
- **パッド入力 → `(vx, vy, ω)` の変換** — `drivetrain-spec.md` §10.1.2 が
  **「捨てても惜しくない層」**と呼ぶ最上段。M3 で「目標座標 → `(vx, vy, ω)`」に差し替わる
- **ウォッチドッグの入力元** — ④ は「コントローラ固有の処理」ではなく
  **「最後に有効な指令を受けてからの経過時間」だけを見る形**で実装する。
  M3 ではこの入力元を受信メッセージへ差し替えるだけにする（FR-10 は新規実装ではない）
- **台上（M2a-0）と接地（M2a-1 以降）** — 検証の危険度が変わる境目
- **ピンアサイン（論理）と配線経路（物理）** — 前者は本 Spec、後者は `chassis-mechanism`。
  ⚠️ **同じ「配線」という語が2つの別物を指している**ため、要件を書く際に必ず言い分ける
- **ハード不要の段と実機必須の段** — 結線表・ピンアサイン・ペリフェラルアダプタは**機体が無くても完了できる**。
  E-0〜E-4 は机上（整備スタンド不要）、M2a-0 以降は整備スタンドと機体が要る。
  ⚠️ **`sensing-foundation` / `world-frame-calibration` / `flying-object-tracking` /
  `m1-prediction-validation` の4 Spec が採っている「ハード不要セクション → 実機セクション」の
  並べ方をそのまま踏襲する。** `chassis-mechanism` の完了を待つのは**後段だけ**である

## Out of Boundary

- 定量的な性能評価。⚠️ **M2a は定性確認であり、NFR-1 の合否判定に使わない。**
  「手で動かして速そうだった」は判断材料にならない（`requirements.md` M2a）
- **物理的な非常停止手段**（OQ-13）。⚠️ **デッドマンも接続断停止も「安全装置」ではなく「運転操作」である。**
  どちらも無線に依存するため、無線が落ちる状況＝まさに暴走しうる状況では機能しない可能性がある。
  **テレオペで非常停止を代替しない**
- ゴミ箱本体・固定アダプタの設計（機構トラック側 → `catch-mechanism` / `chassis-mechanism`）
- **整備スタンドの設計・製作**（→ `chassis-mechanism`）。本 Spec は使う側であって作る側ではない
- **OQ-11（メイン電源スイッチの要否・取付位置）/ OQ-12（電源分岐端子の要否・方式）の決着**
  → `chassis-mechanism` の **Requirement 8「電源系の機構的決着」が唯一の決着先**である
  （両 OQ とも決着期限が「機構設計時」「配線設計時」と定められている）。
  ⚠️ **本 Spec はこれらを決めない。** 決まった結果を結線表へ**取り込む側**である
- **配線の物理経路**（どこを通すか）→ `chassis-mechanism`。
  同 Spec が既に**モータ／エンコーダ／電源の3系統を壁で隔てた通路**として実装しており、
  本数の正は `chassis_mechanism.shapes.CABLE_ROUTE_NAMES` が持つ。
  ⚠️ 本 Spec が決めるのは**どの線がどの系統に属するか**であって、**どこを通すか**ではない

## Upstream / Downstream

- **Upstream**: `drivetrain-core`（ポート定義と純ロジック一式）
- **Downstream**: `m2-motion-validation`（校正済みエンコーダと動作する足回りを前提とする）、
  M3 の本番ファームウェア（下位層とウォッチドッグをそのまま引き継ぐ）

## Existing Spec Touchpoints

- **Extends**: なし
- **Adjacent**: `drivetrain-core` — ポート定義を跨ぐ。**アダプタ側にロジックを漏らさない**

## Constraints

- **後段は実機必須。ただし部品はすべて揃っている**（2026-08-30 更新。⚠️ 旧記述の
  「部品が揃っていない」「AE-TB67H450 の手元有無は未確認」は**いずれも解消済み**）。
  **制約は部品ではなく機体（整備スタンド）へ移った:**
  - **機体も部品も要らない**: **結線表とピンアサインの確定**（本 Spec の最初の段）。
    ⚠️ **ここが今すぐ着手できる範囲であり、`chassis-mechanism` の進捗に一切依存しない**
  - ESP32 単体で先行できる: **Bluepad32 / DualSense の導通とペアリング挙動（OQ-16）**。
    これは最大の未検証項目であり、**モータもホイールも要らずに単体で潰せる**
  - 机上のモータ・ドライバで進む: **E-1〜E-4**（安定化電源・可変抵抗・モータ非接続）。
    ⚠️ **整備スタンドは要らない**
  - **整備スタンド待ち**（→ `chassis-mechanism`）: M2a-0 の台上確認以降すべて。
    ⚠️ **これが現在のクリティカルパスである**
- **DualSense は BR/EDR（BT Classic）のみで BLE 非対応** → classic ESP32 必須（S3/C3/C6/H2 不可）
- **ペアリングの罠**: 新しい DualSense ファームの「マルチペア」モードでは無言で失敗する既知問題がある。
  レガシー手順（Create/Share + PS 長押し → ライトバー2回点滅）を使う。
  PS5/PC と最後にペアした場合は自動再接続しない
- **リンクキーの残留**が再接続失敗の頻出原因。
  **「Bluetooth キーを消去する」操作（ボタン組合せかシリアルコマンド）をファームに用意する**
- **電波が弱い**（DevKit のベタパターンアンテナ）。数 m 程度を想定し、
  リンク断での停止を前提に置く（④ が必要な理由がもう一つ増える）
- **パーティションテーブルの自前指定が要る。** Arduino core + BTstack BR/EDR HID host で約 1.0〜1.4 MB。
  4MB の既定スキーム（1.31 MB × 2 OTA）では**ぎりぎりか溢れる**。
  テレオペビルドは `huge_app`（3MB、OTA 無し）を `board_build.partitions` で指定する
- **PCNT は自前アダプタを `driver/pulse_cnt.h`（IDF 5.x の新 API）で書く。**
  `ESP32Encoder` ライブラリは非推奨の legacy API 上にあり、方向反転時のパルス落ちも報告されている。
  自前化はアダプタ隔離の方針とも一致する
- ⚠️ **PCNT のハードウェアカウンタは符号付き 16bit（±32767）。**
  watch point ＋ 64bit ソフトウェアアキュムレータで桁上げを累積しないと、
  **「数秒走るとオドメトリが壊れる」形で現れる**
- **グリッチフィルタの上限は 1023 APB クロック（80MHz で約 12.8 µs）**、ユニット単位設定。
  これは硬い天井であり、それ以上のフィルタリングを前提にしない
- **ADC1 を使う**（ADC2 は Wi-Fi 動作中に使用不可。本番 Wi-Fi ビルドで効いてくる）。
  ESP32 の生 ADC は両端で非線形なので、**カーブフィッティング補正を入れる**
  — LiPo カットオフ閾値の精度に直結する
- GPIO 34〜39 は入力専用で**内部プルアップが無い**。オープンコレクタ出力のエンコーダには外部プルアップが要る
