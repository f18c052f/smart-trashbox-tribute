#### 環境構築の初期手順

`~/.platformio` をフォルダごと削除 → VSCode の PlatformIO 拡張を導入 →
`firmware/` で `pio run -e bench`。初回はツールチェーン約1GB と Bluepad32 / BTstack の
取得が走り、20分程度かかる。

⚠️ **ツールチェーンの導入が途中で失敗すると、`tool-cmake` などが中身の無い殻のまま
`.piopm`（導入済みの印）だけ残り、PlatformIO が二度と取り直さない。**
`~/.espressif` が作られていなければ導入は完了していない。
この状態になったら `~/.platformio` を消してやり直すのが早い。

#### ⚠️ `fetch_bluepad32.py` の Windows 対応が必須

本リポジトリは `core.autocrlf=true` の環境にある。素のままだと必ず次で止まる。

| 症状 | 原因 | 対応 |
|---|---|---|
| `error: corrupt patch at line 20` | クローン時に BTstack のパッチが CRLF 化する | `git clone` に `-c core.autocrlf=false -c core.eol=lf` |
| `PermissionError: [WinError 5]` | git のパックファイルが読み取り専用で `shutil.rmtree` が消せない | 読み取り専用ビットを落として再試行する `onerror` ハンドラ |

いずれも修正済み（`f0f7c2f`）で、Bluepad32 の取得とパッチ適用まで通ることは確認済みである。

#### ⚠️ VSCode 拡張は `firmware/` をルートにして開く

PlatformIO の VSCode 拡張は、**ワークスペースのルートに `platformio.ini` があること**を
前提にする。本リポジトリでは `firmware/platformio.ini` にあるため、
**リポジトリのルートを開いたままでは拡張が働かない。**

→ `firmware/` を別ウィンドウでルートとして開き直す
（またはマルチルートワークスペースへ `firmware/` を足す）。

⚠️ `platformio.ini` をリポジトリのルートへ移すことでは解決しない。
固定側（Python）と移動体側（ファームウェア）を分ける `structure.md` の構成が崩れる。

#### ⚠️ platform と PlatformIO Core が要求する SCons の版が食い違う

**これが最後まで残ったブロッカーである。**

本プロジェクトは pioarduino の platform-espressif32 を **55.03.311 に固定**して使う
（要件 1.7）。この platform とコアが、**同じ `tool-scons` というパッケージ名に対して
別の版を要求する**。

| 要求元 | 要求する版 | 出典 |
|---|---|---|
| platform 55.03.311 | **4.40801.0**（SCons 4.8.1） | `platforms/espressif32/platform.json` の `tool-scons` |
| Core **6.2.0** | 4.41101.0（scons-local 4.11.1） | Core の `platformio/dependencies.py` |
| Core **6.1.19** | **4.40801.0**（scons-local 4.8.1） | 同上（wheel を展開して確認） |

同じディレクトリ（`packages/tool-scons`）を奪い合うため、毎回こうなる。

```
Tool Manager: tool-scons@4.40801.0 has been installed!     <- platform が要求
Tool Manager: tool-scons@4.41101.0 has been installed!     <- Core 6.2.0 が要求
Tool Manager: tool-scons@4.41101.0 has been installed!
...
*** [.pio/build/bench/firmware.elf] ModuleNotFoundError : No module named 'SCons.Tool.FortranCommon'
```

⚠️ **ビルド後に `packages/tool-scons` ごと消えている**（実測）。
不完全な状態でリンク段に使われるため、上記のエラーになる。

⚠️ **ESP-IDF 側のコンパイルは全部通る。落ちるのは最後のリンク段だけ**である。
そのため「あと少し」に見えるが、原因は環境の版不一致であってコードではない。

**対処（本筋）**: ⚠️ **VSCode 拡張を pioarduino 版にする。**

```

code --uninstall-extension ms-vscode.cpptools-extension-pack

code --install-extension Jason2866.esp-decoder
```

「拡張パック」**であって cpptools 本体ではない。パックを消すと本体まで
一緒に消えるため、本体だけ入れ直す（PlatformIO が生成する
`c_cpp_properties.json` はこれ向けである）。

**対処（応急）**: Core を platform に合わせて **6.1.19** へ下げる。

```

```

⚠️ こちらは拡張の管理外で手当てする形なので、**拡張が Core を入れ直すと元に戻る**。
恒久的には上の「本筋」で直すこと。

**2026-09-21 に決着した状態**（ここへ収束すれば正しい）:

### 1.1 なぜ E-3 と E-5 で LED を使うのか

**モータを繋がずに、そこまでの鎖をすべて確かめるため**である。

E-3 の時点で未知なのは「ファームとドライバの論理が正しいか」だけであり、
モータの実負荷は**その次の段（E-4）で初めて入れる**。LED を挟むことで、
この2つが同時に未知になることを避けられる。

とくに **案B が効いているかどうかは LED で完全に判定できる**。
効いていなければ「指令ゼロで全点灯」になるだけで、**何も壊れない**。
モータでこれをやると、いきなり全速逆転する。

## 2. 共通の前提

### 2.1 着手前に揃っているべきもの

- [ ] 回路図どおりに配線した1輪ぶんの回路
- [ ] 安定化電源（電流制限＝CC が使えること）
- [ ] テスター
- [ ] **LED 治具**（→ §2.4）。E-5 で3輪ぶん使うなら3組
- [ ] `[env:bench]` と `[env:teleop]` がビルドできる環境（→ §0.2）
- [ ] 案B を反映した `motor_ledc.{hpp,cpp}`
- [ ] 部品: RRS（0.22Ω/1W以上）、C7〜C9 / C10〜C12（0.1µF）、JP1（2ピンヘッダ＋ジャンパ）

### 2.2 どの段でも守ること

⚠️ **電源を入れる前に、必ず次を確認する。**

1. **ESP32 をリセットしてから VM を入れる。** IN1/IN2 が振られている状態で主電源を入れると、
   入れた瞬間に出力が出る（アプリケーションノート 1.2 / 3章）。
   IC 内部に 100kΩ プルダウンがあるため、ESP32 がリセット中なら自動的に L に落ちる。
2. **USB を挿すなら JP1 を外す。** BP5293-50 の 5V と PC の USB 5V が並列になるのを防ぐ。
   ⚠️ 切るのは 5V の1本だけで、**GND は常に繋いだまま**にする。
3. **電流制限を先に設定してから出力を入れる。**

### 2.3 異常を感じたら

**発熱・異臭・異音・想定外の電流** のいずれかがあれば、**ただちに電源を切る**。
原因が分かるまで次へ進まない。log へ「中止」として残す。

### 2.4 LED 治具

**逆向き並列の2色 LED ＋ 直列抵抗 1kΩ**（1/4W）を1組とし、
ドライバの `OUT1` − `OUT2` 間へ繋ぐ。モータの代わりである。

```
 OUT1 ──┬──[ LED赤 ▶ ]──┬──[ 1kΩ ]── OUT2
        └──[ ◀ LED緑 ]──┘
```

- 電流 ≒ (12V − 2V) / 1kΩ = **約 10mA**。抵抗の消費は 0.1W なので 1/4W で足りる
- LED は互いを順方向電圧（約2V）でクランプするため、**逆耐圧の心配は要らない**
- 20kHz の PWM なので、明るさは滑らかに見える（ちらつかない）

#### 案Bのときの見え方

| 指令 | IN1 | IN2 | OUT1 | OUT2 | LED |
|---|---|---|---|---|---|
| ゼロ | L | L | Hi-Z | Hi-Z | **両方消灯** |
| 前進 | PWM | L | PWM | L | 赤が明るさ可変 |
| 後進 | L | PWM | L | PWM | 緑が明るさ可変 |
| ブレーキ | H | H | L | L | 両方消灯 |

⚠️ **ゼロとブレーキは LED では区別できない。** ただし案Bはブレーキを出さないので、
この段では問題にならない。

🔶 赤と緑のどちらが「前進」かは、この段では決めない。
`OUT1`/`OUT2` と 赤/白 の対応が E-2 で決まってから紐づける。

### 2.5 切り分けの順番（うまくいかないとき）

⚠️ **LED が想定と違ったら、鎖の上流へ1つずつ戻る。**

| # | 測る場所 | 見方 |
|---|---|---|
| 1 | LED | 上表と一致するか |
| 2 | ドライバの `IN1` / `IN2` を**テスターの DC 電圧**で | ⚠️ **PWM の平均が読める。** `3.3V × デューティ` になる（デューティ0 なら 0V、50% なら約 1.65V） |
| 3 | ESP32 の GPIO19 / GPIO23 を同様に | ここが正しくて IN1/IN2 が違えば**配線**の問題 |
| 4 | `VM`（TP1 / TP6） | 電源が来ているか |

2 と 3 が一致し、かつ上表どおりなら **ファームは正しい**。
LED だけがおかしければ、治具か `OUT1`/`OUT2` の配線である。

## 3. E-0 — 無通電で線の色と系統を確かめる（タスク 8.2）

> ⚠️ **通電しない。** ここを誤ると次段で電源電圧がエンコーダへ入り、**エンコーダが即座に壊れる**。

### 3.1 なぜこの段が要るか

このモータは **黒＝エンコーダの GND、白＝モータ電源の−** である。
「黒＝共通グランド」と読んで 12V 系をエンコーダ対（青・黒）へ入れると、
エンコーダに電源電圧がそのまま掛かる。**一般的な配線の直感に反する**ため、
思い込みではなく計測器で確かめる。

### 3.2 手順

1. すべての電源を切り、バッテリを外す。
2. モータ6線のうち、**赤と白**の間の抵抗を測る。数Ω（モータ巻線）であること。
3. **青と黒**の間の抵抗を測る。赤白とは**導通していない**こと（別系統）。
4. 赤（または白）と、青・黒・黄・緑それぞれの間を測る。**すべて開放**であること。
5. 結果を [`bringup-log.md`](./bringup-log.md) の E-0 欄へ記録する。
6. [`wiring.md`](./wiring.md) §1 の表と突き合わせる。

### 3.3 合格条件

- [ ] 赤−白 が数Ωで導通する（モータ巻線）
- [ ] 青−黒 が赤白と**別系統**である
- [ ] モータ対とエンコーダ対の間に導通が**無い**
- [ ] [`wiring.md`](./wiring.md) §1 の記載と食い違いが無い

### 3.4 不合格だったら

ハーネスの色の割当がメーカー記載と違う可能性がある。**次へ進まない**。
実測した対応を [`wiring.md`](./wiring.md) へ反映してから、回路図の側も直す。

## 4. E-1 — 電流を制限できる電源で導通と短絡を確かめる（タスク 8.3）

> ⚠️ **バッテリを挿さない。** LiPo は短絡時に数十A を流せるため、配線ミスがあれば発煙する。

### 4.1 準備

- モータ・エンコーダ・ESP32 を**すべて外した**状態から始める。
- 安定化電源を **12.0V / 電流制限 0.2A** に設定する。

### 4.2 手順

各段で電流・発熱・異臭を確認しながら、**1つずつ**繋いでいく。

| # | 繋ぐもの | 電流制限 | 見るもの |
|---|---|---|---|
| 1 | 電源のみ（ドライバ・DC/DC 未接続） | 0.2A | 電流がほぼ 0 であること |
| 2 | ＋ BP5293-50（U4） | 0.2A | **TP2**（5V 出力）＝ 5.0V ±5% |
| 3 | ＋ ESP32（JP1 を挿す） | 0.5A | **TP3**（3V3 ピン）＝ 3.3V ±5%。消費電流が数十〜百数十 mA |
| 4 | ＋ 分圧回路（R1/R2/C6） | 0.5A | ⚠️ **TP4 が 3.3V 未満**（12.0V なら約 2.55V） |
| 5 | ＋ ドライバ U1（出力は未接続） | 0.5A | **TP1 / TP6** が入力電圧と同じ（差 0.2V 未満）。**TP7** が SGND 基準で約 0V |
| 6 | エンコーダ用コネクタ | 0.5A | ⚠️ **TP5（青−黒）＝ 3.3V。12V が出ていたら直ちに中止** |

⚠️ **TP4 と TP5 は、その先を繋ぐ前に測る。**
TP4 が 3.3V を超えていれば GPIO32 が壊れる。TP5 に 12V が出ていればエンコーダが壊れる。

測定点の一覧は [`schematic-draft.md`](./schematic-draft.md) §5.2 を参照。

### 4.3 合格条件

- [ ] 各段で電流制限に張り付かない（＝短絡していない）
- [ ] 発熱・異臭が無い
- [ ] TP1〜TP7 がすべて期待値の範囲内
- [ ] **TP4 < 3.3V**、**TP5 = 3.3V**

### 4.4 記録する項目

各段の消費電流、TP1〜TP7 の実測値、発熱・異臭の観察（要件 10.4）。

### 4.5 不合格だったら

電流制限に張り付いたら**その段で繋いだものが原因**である。切り分けは1つ戻すだけでよい。
これがこの段を1つずつ進める理由である。

## 5. E-2 — ドライバを介さずモータ単体を回す（タスク 8.4）

### 5.1 目的

回転方向とハーネス（赤/白）の対応を確定し、3個の無負荷電流のばらつきから
**個体差の外れ値をこの段で見つける**。ドライバもファームも絡まないので、
切り分けが最も簡単な段である。

### 5.2 手順

1. モータを回路から外し、**安定化電源へ直結**する（12.0V / 電流制限 2.5A）。
2. 赤を＋、白を−に繋ぎ、回転方向を記録する。**これを「正転」と定義する**。
3. 無負荷電流を記録する。
4. 赤と白を入れ替え、逆に回ることを確認する。
5. 3個すべてについて 2〜4 を行う。

### 5.3 合格条件

- [ ] 3個とも回る
- [ ] 赤白の入れ替えで回転方向が反転する
- [ ] 3個の無負荷電流に大きな外れ値が無い

### 5.4 記録する項目

各モータの回転方向と赤白の対応、無負荷電流3個（要件 10.5）。
⚠️ ここで決めた「正転」の定義が、以降すべての段の基準になる。

## 6. E-3 — LED で開ループ確認（タスク 8.5 前半）＝ **step 1 前半**

> ⚠️ **モータを繋がない。** LED 治具（§2.4）をドライバの `OUT1` − `OUT2` へ繋ぐ。

### 6.1 この段で確かめること／確かめないこと

| | |
|---|---|
| 確かめる | **案B が効いていること**。可変抵抗が出力の大きさへ写ること。ESP32 からドライバまでの鎖 |
| 確かめない | 実負荷での電流・発熱・滑らかさ（→ E-4）。回転方向の反転（BenchApp は正転しか出さない）。エンコーダ、無線、速度制御 |

⚠️ **エンコーダは繋がない。** BenchApp は計数器を一切初期化しない。
切り分けの対象を「ファームとドライバ」だけに保つのが、この段の設計意図である。

### 6.2 準備

- [ ] 案B を反映した `motor_ledc.{hpp,cpp}` でビルドすること
- [ ] **LED 治具**を `OUT1` − `OUT2` へ繋ぐ。**モータは繋がない**
- [ ] 可変抵抗 10kΩ を **上端→3V3 / 下端→GND / ワイパ→GPIO33** の3本すべて結線する
      （2本だけだと中途半端な電圧になる）
- [ ] JP1 を**外す**（USB で書き込むため）
- [ ] 安定化電源 12.0V / 電流制限 **0.5A**（LED しか繋がないので低くてよい）

### 6.3 手順

1. `pio run -e bench -t upload` で書き込む。
2. ⚠️ **可変抵抗を絞りきった（0%）状態にする。**
3. **ESP32 をリセットしてから** 主電源を入れる。
4. ⚠️ **この時点で LED が両方とも消灯していること**を確認する。
   点灯していたら直ちに電源を切る（→ §6.5）。
5. 可変抵抗をゆっくり上げる。**片方の LED だけ**がだんだん明るくなること。
6. 100% まで上げ、また 0% まで戻す。消灯に戻ること。
7. 🔶 余裕があれば、ドライバの `IN1` / `IN2` をテスターの DC 電圧で測り、
   `3.3V × デューティ` になっていることを確かめる（§2.5 の #2）。

### 6.4 合格条件

- [ ] **絞りきりで LED が両方とも消灯している**（案Bが効いている決定的な証拠）
- [ ] 上げると**片方だけ**が点灯する（両方同時に点かない）
- [ ] 明るさが連続的に変化する（段付き・ちらつきが無い）
- [ ] 0% に戻すと消灯する

### 6.5 ⚠️ 絞りきりで LED が点灯したら

**案Bが効いていない。** 直ちに電源を切る。次のいずれかである。

1. 案Bを反映していないファームが書き込まれている
2. IN1 と IN2 の配線が入れ替わっている
3. ビルドが古い（`pio run -e bench -t clean` してから書き直す）

⚠️ **この症状は「前進・指令ゼロで全速逆転」であり、案B以前の状態そのものである。**
**LED でこれを踏めたのは幸運である。** モータを繋いでいたら全速で逆転していた。
原因が分かるまで**モータを繋がない**。

### 6.6 記録する項目

絞りきりでの消灯、点灯する側の色、明るさの連続性、IN1/IN2 の DC 電圧（測ったなら）。

## 7. E-4 — モータで開ループ確認（タスク 8.5 後半）＝ **step 1 後半**

> E-3 に合格してから行う。**新しく入る未知は実負荷だけ**である。

### 7.1 準備

- [ ] **E-3 に合格していること**
- [ ] LED 治具を外し、モータを**1個だけ**繋ぐ
      （BenchApp は3輪へ同じデューティを出すが、繋がっていない輪は無負荷）
- [ ] 車輪を浮かせる
- [ ] 安定化電源 12.0V / 電流制限 **2.0A**

### 7.2 手順

1. ⚠️ **可変抵抗を絞りきった（0%）状態にする。**
2. **ESP32 をリセットしてから** 主電源を入れる。
3. **この時点でモータが動かないこと**を確認する。
4. 可変抵抗をゆっくり上げ、0% → 100% → 0% と往復させる。
5. 滑らかさ（引っかかり・段付き・うなりの有無）を観察する。
6. 数分回したあと、ドライバの発熱を触って確認する。
7. 消費電流の範囲を記録する。

### 7.3 合格条件

- [ ] 絞りきりでモータが止まっている
- [ ] 全域で滑らかに加減速する
- [ ] ドライバが触れないほど熱くならない
- [ ] 電流制限に張り付かない

### 7.4 記録する項目

全域の滑らかさ、ドライバの発熱、消費電流の範囲（要件 10.6）。

### 7.5 不合格だったら

E-3 に合格しているので、**ファームとドライバの論理は正しい**。
原因は実負荷側（モータ、配線、電流制限、電源容量）にある。切り分けの範囲がそのぶん狭い。

## 8. E-5 — LED でコントローラの疎通を確かめる（タスク 8.6）＝ **step 2 前半**

> ⚠️ **モータを接続しない状態で行う**（要件 10.7）。
> ペアリング・再接続・デッドマンの挙動が未検証のままモータが繋がっていると暴れる。
> **LED 治具に戻す。**

### 8.1 準備

- [ ] **モータを外し、LED 治具を `OUT1` − `OUT2` へ繋ぐ**
- [ ] 3輪ぶん見たいなら、3台のドライバそれぞれに治具を繋ぐ
- [ ] 可変抵抗は外してよい（この段では使わない）
- [ ] `pio run -e teleop -t upload` で書き込む（bench ではない）
- [ ] 安定化電源 12.0V / 電流制限 0.5A

### 8.2 操作の割当

| 操作 | 割当 |
|---|---|
| デッドマン（出力許可） | **L1（左肩ボタン）** |
| 輪単体の選択 | 十字キー **← = 輪0 / ↓ = 輪1 / → = 輪2** |
| 選択中の輪の速度 | 左スティック 上下 |
| 機体走行（十字キーを押していないとき） | 左スティック＝並進、右スティック横＝回転 |

### 8.3 手順

1. DualSense をペアリングする。
2. **L1 を離した状態で LED が消灯している**ことを確認する。
3. L1 を押しながら左スティックを倒し、**LED が点く**ことを確認する。
4. スティックを前後に倒し、**点く LED の色が変わる**ことを確認する（前進／後進）。
5. **L1 を離した瞬間に消灯する**ことを確認する。
6. 3輪ぶん治具を繋いでいるなら、十字キーで輪を切り替え、
   **選んだ輪の LED だけが点く**ことを確認する。
7. コントローラの電源を切り、**接続断で消灯する**ことを確認する。
8. 再接続できることを確認する。
9. 入力の遅れ（スティックを倒してから LED が変わるまで）を主観で記録する。

⚠️ **速度指令は速度PID を通る。** エンコーダが未接続なので、測定速度がゼロのまま
指令だけが残り、**デューティが上がり切る**可能性がある。LED なので害は無いが、
「スティックをわずかに倒しただけで全点灯する」なら、それは PID が飽和している。
E-6 でエンコーダを繋げば解消するはずであり、この段では**異常ではない**。

### 8.4 合格条件

- [ ] ペアリングできる
- [ ] **L1 を離すと消灯する**
- [ ] L1 を押しながらスティックを倒すと点灯する
- [ ] 倒す向きで色が変わる
- [ ] **接続断で消灯する**
- [ ] 再接続できる
- [ ] （3輪ぶん繋いだなら）十字キーで選んだ輪だけが点く

### 8.5 不合格だったら

⚠️ **接続方式そのものの成立可否の判断材料になる（OQ-16）。**
BT Classic 直結が使えないと判明したら、PC 経由（Serial / UDP）へ退避する。
その判断材料を log へ残す。

LED が点かない場合の切り分けは §2.5 の順に行う。**E-3 に合格している**ので、
ESP32 からドライバまでの鎖は既に確かめてある。疑うのは無線と入力マッピングである。

## 9. E-6 — コントローラで輪単体を回し、エンコーダを校正する（タスク 9.1 / M2a-0）＝ **step 2 後半**

> ⚠️⚠️ **この段から性質が変わる。** コントローラ経由の指令は**速度指令**であり、
> **速度PID を通る**。エンコーダが繋がって正しく数えていないと、測定速度がゼロのまま
> 指令だけが残り、**PID がデューティを上げ切る**。

### 9.1 準備

- [ ] **E-5 に合格していること**
- [ ] E-1 の #6 で **TP5（青−黒）= 3.3V** を確認済みであること（12V が出ていたらエンコーダが死ぬ）
- [ ] エンコーダ4線を結線する。⚠️ **黒は ESP32 の GND ピンへ**（動力側の GND バスにぶら下げない）
- [ ] モータは**1個だけ**繋ぐ
- [ ] 車輪を浮かせる

🔶 **LED 治具を並列に残しておくと切り分けが楽になる。** モータと並列に繋いでも
10mA しか食わないので影響は無く、デューティが目で見える。

### 9.2 手順

1. **まずデッドマンを押さずに**電源を入れ、モータが動かないことを確認する。
2. 十字キー ← で輪0 を選び、L1 を押しながら左スティックをごくわずかに倒す。
3. **回り始めたら直ちにスティックを戻す。** 暴走しないことをここで確認する。
4. 問題なければ、ゆっくり出力を上げる。
5. 車輪を**手で決まった回数**（例: 10回転）回し、計数値を読む。
6. 分解能（パルス／出力軸1回転）を算出する。目安は 11 PPR × 減速比 約19 ≒ **209**。
7. 黄／緑のどちらが A相 かを、回転方向と計数の符号から確定する。

### 9.3 合格条件

- [ ] デッドマンを押さない状態でモータが動かない
- [ ] 指令に対して暴走しない（PID が発散しない）
- [ ] 計数値が回転に比例する
- [ ] 算出した分解能が 209 前後である
- [ ] A相/B相 と線色の対応が確定する

### 9.4 ⚠️ 暴走したら

**エンコーダが数えていない。** 直ちに L1 を離す（それで止まる）。次のいずれかである。

1. エンコーダの配線違い（黄緑の入れ替え、電源逆）
2. PCNT の設定ミス
3. プルアップ不足（→ [`schematic-draft.md`](./schematic-draft.md) §7.3 の予備位置を実装する）

⚠️ E-5 で「わずかに倒しただけで全点灯」だったのが、エンコーダを繋いで解消するなら
**PID が正しく閉じた証拠**である。解消しないならエンコーダ側を疑う。

### 9.5 記録する項目

分解能の実測値、A相/B相 と線色の対応、暴走の有無（要件 11.x、OQ の決着材料）。

## 10. E-7 — モータ3個を机上で回す ＝ **step 3**

> 🔶 **机上で車輪を浮かせて回すだけ**であり、整備スタンドは不要。
> 接地走行（逆運動学の符号確認）は本手順書の範囲外。

### 10.1 準備

- [ ] 3輪とも車輪を浮かせる

### 10.3 合格条件

- [ ] 十字キーで選んだ輪だけが回る

### 10.4 記録する項目

3輪の挙動の差、合計消費電流、発熱。
