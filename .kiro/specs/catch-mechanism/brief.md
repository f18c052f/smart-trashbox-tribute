# Brief: catch-mechanism

## Problem

**捕球機構の開口寸法は、まだどこにも存在しない。にもかかわらず、その値は既に稼働中のコードに
「暫定値」として埋め込まれ、プロジェクト唯一の最終判定（NFR-7）の手前にある合否条件を決めている。**

`src/trajectory_sim/params.py` の `CatchCriteria.position_tolerance_mm = 67.5` は、docstring 自身が
次のように書いている:

> 導出根拠: キャッチ機構の**開口半径**から、対象物寸法の半分を引く考え方による。……
> **開口寸法自体がまだ確定していないため、この 67.5mm は暫定値**であり、実測（M1/M2）により
> 見直す前提の仮値である。

つまり `開口半径 − 対象物半径` → `position_tolerance_mm` → シミュレータのキャッチ可能領域 →
**NFR-1 の必要駆動性能** という伝播経路が既に存在し、その起点だけが空席になっている。

さらに機構の造形手段（Bambu Lab A1 mini）と CAD 手段（FreeCAD）が新たに確定したが、
**このリポジトリには CAD 資産が一切なく、寸法パラメータの置き場所も、造形制約の記録先も無い。**
機構設計を始める前に、この土台が要る。

## Current State

- 仕様の断片は `docs/` に散在するが、**所有者となる Spec が無い**。
  `FR-7`（受け口・漏斗）/ `FR-12`（キャッチ保持）/ `NFR-5`（位置精度＝開口半径 − ゴミ寸法/2）/
  `bom.md §E`（機構3Dプリンタ活用）/ `drivetrain-spec.md §6.2`（3Dプリント範囲）
- `teleop-bringup/brief.md` は「ゴミ箱本体・固定アダプタの設計（**機構トラック側**）」を
  Out of Boundary として明示しており、**宛先の無い参照が既に存在する**
- `trajectory_sim` は `position_tolerance_mm = 67.5`（φ200mm 開口 − φ65mm 空き缶の仮定）で
  既にキャッチ可能領域を計算している。**根拠となる実物は存在しない**
- `docs/decisions.md` D-9 により、`trajectory_sim` は `bounce_out`（跳ね返り）を
  **明示的にモデル外**としている。したがって FR-12 の判断はシミュレータからは出せない
- ゴミ箱本体は未購入（OQ-08 未決）。ただし**百均で調達可能であり、ハード待ちではない**。
  2026-08-30 の実売調査により、**要求（φ200 以上・300g 以下・PP・フタなし）は 110円 で成立する**ことを確認済み。
  選定基準と第一候補は `.kiro/steering/roadmap.md`「ゴミ箱の選定基準」を正とする
- ⚠️ **実売調査で当初の推奨2件を訂正した**（brief 作成時の推測が実態と合っていなかった）:
  **(1) 開口径は φ215〜225 が実質の上限**であり、当初想定した φ240〜260 は 100均には存在しない。
  **(2) テーパーは全品にある**（ネスティング前提）ため「強いテーパー不可」は要件として成立せず、
  「緩いものを選ぶ」へ緩和した
- 足回り部品（60mm オムニホイール / 6mm ハブ / JGB37-520 / 電子部品）は**すべて手元にある**。
  ⚠️ ホイール／ハブは **Nexus 14145 / 18020 相当品であり純正ではない**（→ `chassis-mechanism`）

## Desired Outcome

- **開口径が実物で確定し、`position_tolerance_mm` が「暫定値」でなくなる。**
  `trajectory_sim` の設定ファイルへ実物由来の値が反映され、キャッチ可能領域が机上値から実測由来へ置き換わる
- **OQ-08（市販PPゴミ箱の具体機種）が決着する。** 選定基準が根拠付きで文書化され、実物が選定・採寸されている
- **寸法パラメータの単一の正が存在し、現物採寸値を後から流し込める。**
  git で差分が読め、ヘッドレスで再生成・検証できる
- **A1 mini の造形制約（180mm 分割必須・PETG 上限・継手はボルト＋インサート）が
  設計の初期前提として明文化され、以降の機構設計がそれを前提に始められる**
- 受け口の深さ・底の扱い（くりぬきの可否）について、FR-12 の観点から根拠のある判断が下されている

## Approach

**ハイブリッド CAD**: 形状定義を `build123d`（Python / OCCT カーネル）で持ち、
STEP を経由して FreeCAD で組立確認・干渉チェック・図面化する。

**なぜ FreeCAD 単一にしないか**（2026-08-30 の技術検証で判明）:

- FreeCAD には完全な Python API があり、スクリプトだけでモデルを組める。**しかし争点は
  「Python か否か」ではなく「モデルの正がどこにあるか」である。** FreeCAD の Python API は
  `.FCStd`（バイナリ zip）というドキュメントを操作する形であり、成果物はそのバイナリになる
- ⚠️ **トポロジカルネーミング問題（TNP）はスクリプトで書いても回避されない。**
  FreeCAD は面/エッジを `Face6` / `Edge12` のような生成名で参照するため、再計算で番号が
  振り直されると別の面に付く。これはカーネルが面に振る名前の問題であり、GUI 操作の問題ではない
- ⚠️ **本プロジェクトの中核ワークフロー（現物採寸値の後入れ）を直撃する未修正バグが実在する**:
  - [#26084](https://github.com/FreeCAD/FreeCAD/issues/26084) **Spreadsheet のセル値を変えるだけで
    SubShapeBinder の参照面が別の面へ飛ぶ**。1.1.0rc1 で再現・**open**。
    Spreadsheet 集中管理は FreeCAD でパラメータ運用する際の定石であり、**その定石そのものがバグ経路**
  - [#17041](https://github.com/FreeCAD/FreeCAD/issues/17041) recompute 後に face/edge ID が変わる。
    Confirmed・**open**（ラベルは "Toponaming fixed in **V2**"）
  - [#31040](https://github.com/FreeCAD/FreeCAD/issues/31040) その **V2 アルゴリズム本体が
    2026-06 起票で未完了**。`toponaming` を含む open issue は 26 件
  - FreeCAD 1.0 で TNP 緩和が本体統合されたが、**公式ブログ自身が「適用は Sketcher と
    PartDesign のみで完全解決ではない」と明記**している
- ⚠️ **git 差分は非圧縮保存でも本質的に解決しない。** 形状の実体は `.FCStd` 内の `*.brp`（BREP）にあり、
  寸法を 1mm 変えると BREP のエントリ番号が総入れ替えになる。テキスト化要求
  （[#5585](https://github.com/FreeCAD/FreeCAD/issues/5585) /
  [#9432](https://github.com/FreeCAD/FreeCAD/issues/9432)）はいずれも未実装。
  `.gitattributes` の `textconv` 回避策は**マシンごとに再設定が必要でリポジトリに同梱できない**

**build123d を選ぶ理由**: `.py` そのものがモデルであり、別のバイナリ文書が存在しない。
参照解決を幾何セレクタとして明示的に書くため TNP の影響が限定的で、git 差分・CI・
パラメータ後入れの3要件が同時に素直に解決する。**カーネルは FreeCAD と同じ OCCT** なので
STEP 経由の連携に情報欠落が無く、FreeCAD 側の利点（Assembly WB・干渉チェック・TechDraw 図面）は残る。
これは `prediction-core` / `drivetrain-core` が採った「実機なしで検証できる中核を持つ」作り方の踏襲でもある。

**FreeCAD 側に残す責務**: 組立確認、干渉チェック、図面化、目視レビュー。**形状の正は持たない。**

⚠️ **「最終微調整は結局 FreeCAD になるのでは」という疑問への回答**（本 Spec が構造で答えるべき点）:

そのとおりになったら**二重管理が始まり、build123d 側が黙って腐る。** これは
`tech.md` 開発標準3（二重実装の禁止）に該当する事故であり、規律ではなく**構造で防ぐ**:

- **`.FCStd` を git 管理しない**（`.gitignore` に入れる）。**成果物の正は `.py` と、
  そこから生成した STEP / STL / 3MF のみ。** FreeCAD ファイルは「見る・測る」ための
  再生成可能なスクラッチとして扱う。⚠️ **正になり得ないので、正になりようがない**
- **CI で `.py` から再生成した STEP の体積とバウンディングボックスを、
  コミット済みの値とつき合わせる。** FreeCAD で手を入れた形状は `.py` から再生成できないため、
  **この検査が落ちることで二重管理が可視化される**
- 「微調整」の中身を分解すると、FreeCAD で手を動かす必要はほぼ無い:
  - クリアランス・フィレット半径・穴径・部品の相対位置 → **すべてパラメータ**。`.py` に書く
  - 見て気付いた干渉 → FreeCAD で**測って**、数値を `.py` へ戻す。**FreeCAD は測定器であって編集器ではない**
  - サポート・シーム・肉厚・造形向き → **スライサ（Bambu Studio）の領域**であり、そもそも CAD ではない
- 残る正当な例外は「有機的な形状を手で詰めたい」場合だが、
  本プロジェクトの部品（板・ブラケット・トレイ・スタンド）には該当しない

**造形前提の確定**: A1 mini（180×180×180mm・エンクロージャ無し・ベッド上限 80℃）から、
「**φ180 を超える部品は分割必須**」「**ASA/ABS/PC/CF・GF は公式に not recommended → PETG が実質の上限材料**」
「**継手は貫通ボルト＋金属ヒートインサートで樹脂を圧縮荷重に限定し、ダボは位置決め専用**」
（FDM の層間強度が弱く、樹脂だけで荷重を渡す継手は層間剥離モードで落ちるため）を
**設計の初期前提として固定してから**形状設計に入る。後から気付くと全面やり直しになる種類の制約である。

**受け口の確定順序**: 選定基準の確定 → 購入・採寸 → 開口径の確定 → `position_tolerance_mm` の更新。
**「百均で適当に買う」を許さない**ことが本 Spec の要点である。開口径はプロジェクトの合否条件の入力だからである。

## Scope

- **In**:
  - **CAD 基盤**: build123d / FreeCAD のツールチェーン確立、寸法パラメータの単一の正の設置、
    現物採寸値の流し込み経路、ヘッドレスでの STEP/STL 生成と妥当性検証（体積・バウンディングボックスの
    アサーション）、`.gitignore` / `.gitattributes` の整備、A1 mini 制約の明文化
  - **受け口（FR-7）**: ゴミ箱の選定基準の確定と根拠、実物の選定・採寸、開口径の確定、
    ワイドリム／漏斗の要否判断と設計
  - **`position_tolerance_mm` の確定と `trajectory_sim` への還元**（設定ファイル経由）。OQ-08 の決着
  - **保持（FR-12）の机上判断**: 受け口の深さと底の扱い（くりぬきの可否）について、
    「浅い＝衝突エネルギー小・脱出しやすい／深い＝衝突エネルギー大・脱出しにくい」の
    トレードオフを整理し、方針を決める
  - ⚠️ **テーパーの釣り合いの判断**: 実売品はほぼ全品が円錐台である。
    **テーパーは漏斗として FR-7 には有利だが、跳ね返った缶を開口へ向けて上外へ弾くため
    FR-12 には不利**という、**同じ形状が2要件へ逆向きに効く**関係がある。
    ⚠️ `decisions.md` D-9 により `trajectory_sim` は `bounce_out` をモデル外としているため、
    **この釣り合いはシミュレータからは出せず、本 Spec が机上で決めるしかない**
- **Out**:
  - **駆動ベース・ゴミ箱固定アダプタ・バッテリ／基板トレイ・整備スタンド**（→ `chassis-mechanism`）
  - **緩衝ライナーの材質選定と購入**（OQ-10。`bom.md §E` の既定方針どおり
    **先回りして購入せず M3 で実投擲後に判断**する。本 Spec は「後から貼れる形にしておく」までを持つ）
  - `trajectory_sim` のコード変更。**本 Spec は設定ファイルの値を確定させるだけで、
    キャッチ判定ロジックには触れない**（`bounce_out` は D-9 でモデル外と決着済み）
  - NFR-7 の目標値と試行回数 N（OQ-05。M1/M2 実測後）

## Boundary Candidates

- **CAD 基盤（寸法の単一の正・造形制約・ヘッドレス検証）** — `chassis-mechanism` も消費する
- **受け口の寸法決定（開口径・深さ・重量）** — `trajectory_sim` が消費する
- **受け口の造形物（ワイドリム／漏斗）** — 本 Spec 内で閉じる

## Out of Boundary

- 機体の構造部材（荷重を受ける部分）はすべて `chassis-mechanism` が持つ
- ⚠️ **キャッチ成否の判定ロジックを持たない。** シミュレータ側の判定は `trajectory_sim` の所有であり、
  本 Spec はその**入力パラメータの値だけ**を確定させる。`tech.md` 開発標準3（二重実装の禁止）
- ⚠️ **開口径を「決めた」ことをもって NFR-5 を達成したと呼ばない。** NFR-5 は位置精度の要件であり、
  本 Spec が決めるのはその**許容幅の分母**にすぎない

## Upstream / Downstream

- **Upstream**:
  - `docs/requirements.md` FR-7 / FR-12 / NFR-5、`docs/bom.md §E`、`docs/drivetrain-spec.md §6.2`
  - `docs/decisions.md` D-9（`trajectory_sim` が `bounce_out` をモデル外とした決着）
- **Downstream**:
  - `trajectory-simulator` — `position_tolerance_mm` の実物由来の値を受け取る
  - `chassis-mechanism` — CAD 基盤と、ゴミ箱の底寸法（固定アダプタの設計入力）を受け取る
  - `m1-prediction-validation` — NFR-5 の評価に確定した許容誤差を使う

## Existing Spec Touchpoints

- **Extends**: なし（新規トラックの1本目）
- **Adjacent**:
  - `trajectory-simulator` — **設定ファイルの値のみ**を更新し、`src/trajectory_sim/` のコードには触れない
  - `teleop-bringup` — 同 brief が本トラックへ委譲した「ゴミ箱本体・固定アダプタ」のうち、
    ゴミ箱本体側を本 Spec が引き取る（固定アダプタは `chassis-mechanism`）

## Constraints

- **造形機は Bambu Lab A1 mini に確定**。180×180×180mm、エンクロージャ無し、ベッド上限 80℃。
  ⚠️ **ASA / ABS / PC / PA / CF・GF 強化材は公式スペックが not recommended と明記** →
  **PETG が実質の上限材料**であり、後から材料でリカバリできない
- **CAD は build123d（形状の正）＋ FreeCAD（組立確認・図面）のハイブリッド**。
  ⚠️ **FreeCAD を形状の正にしない**（TNP #26084 / #17041 / #31040、および `.FCStd` の git 差分不能）
- **金属切削加工は行わない**（CON-1）
- ゴミ箱本体は市販の軽量PP製を利用する（`drivetrain-spec.md §11 Confirmed`）。
  ゴミ箱本体まで全面3Dプリントする構成は**標準案から外れている**
- 対象物は**空き缶（φ65mm 程度の剛体）に固定**（M1 の実験条件）。
  最終スコープとして他の対象物を含めるかは OQ-02 として未決
- `tech.md` 開発標準1: **未実測の値を合否条件にしない。** 転倒限界等の概算は判断材料であって合否ではない
- 実行時サードパーティ依存ゼロの原則は `prediction_core` / `trajectory_sim` のツリーに対するもの。
  ⚠️ **本 Spec が導入する build123d をそれらの依存に混入させない**
  （`tests/prediction_core/test_boundaries.py` / `test_trajectory_sim_boundaries.py` が静的に回帰検証している）
