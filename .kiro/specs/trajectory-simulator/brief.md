# Brief: trajectory-simulator

## Problem

このプロジェクト最大のリスクは、
**「そもそも時間予算内に間に合うのか」（NFR-1）が機体を作り終わるまで分からないこと**である。

移動体の製作には部品調達・CAD・3Dプリント・配線・ファームウェアが必要で、
そこまで進んでから「間に合わない」と分かると手戻りが最も大きい。

## Current State

- 時間予算（総飛行時間 0.6〜1.2s − オーバーヘッド 0.2〜0.3s = 持ち時間 0.3〜1.0s）は
  **すべて設計上の想定値**であり、実測に基づかない
- 投擲レイアウト（OQ-01）も未定。**必要横移動量が決まらないと成立性が判断できない**
- コードは一行も存在しない

## Desired Outcome

- 投擲条件と移動体性能をパラメータとして与えると、
  **「間に合う / 間に合わない」の境界（キャッチ可能領域）が図として出る**
- `requirements.md §7` の「投擲レイアウトをどう決めれば成立するか」を**机上で設計できる**
- NFR-6 の「停止して待つ / 通過キャッチを許容する」の比較が、**実機を壊さずに**試せる
- `drivetrain-spec.md §12` の改善順序7「投擲レイアウトと必要横移動量の見直し」を、
  勘ではなく図の上で検討できる

期待する出力イメージ（軌跡アニメーションではなく**これ**が本命）:

```
    必要横移動量 [m]
      ^
  0.8 |  ×  ×  ×  ×          × = 間に合わない
      |  ×  ×  ×  ○          ○ = 間に合う
  0.4 |  ×  ○  ○  ○
      |  ○  ○  ○  ○
  0.0 +--------------------> 持ち時間 [s]
        0.3  0.5  0.7  0.9
```

## Approach

**Python でバッチ計算し、結果を JSON として出力する。** 常駐サーバもブラウザも要らない。

構成:
1. 投擲物理（放物運動）→ 2. Depth ノイズ付与・検出遅れの模擬 →
3. **`prediction-core` を呼ぶ**（本番と同一コード） → 4. 3輪オムニの運動モデル
   （加速度上限・最高速度・減速）→ 5. パラメータ掃引 → キャッチ可能領域

`prediction-core` を別 Spec として先に切ってあるため、**ここで予測を再実装しない。**

## Scope

- **In**:
  - 投擲物理モデル（初速・角度・ばらつき）
  - Depth ノイズ・検出遅れ・制御周期の模擬
  - 3輪オムニ移動体の運動モデル（加速度上限・最高速度・減速）
  - パラメータ掃引とキャッチ可能領域の算出
  - 結果の JSON 出力
  - OQ-01（投擲レイアウト）の**机上検討**
- **Out**:
  - 予測アルゴリズム（→ `prediction-core` を呼ぶだけ）
  - ブラウザ表示（→ `simulator-visualization`）
  - HTTP API・常駐サーバ（**用途が存在しない**）

## Boundary Candidates

- **投擲物理**（真の軌道の生成）
- **観測モデル**（ノイズ・遅延の付与＝センサーの模擬）
- **移動体運動モデル**（目標座標 → 到達時刻）
- **掃引と評価**（成否判定とキャッチ可能領域の算出）

## Out of Boundary

- **空気抵抗・スリップの精密モデル化。** 最初は最小限とし、
  M1・M2 の実測で不足が分かってから足す（→ OQ-33）
- 移動体の制御アルゴリズム（PID）そのもの。運動モデルは**性能上限の近似**でよい
- 実機の較正値の取り込み。M1 / M2 実測後に別途反映する

## Upstream / Downstream

- **Upstream**: `prediction-core`（予測アルゴリズムを呼ぶ）
- **Downstream**:
  - `simulator-visualization`（JSON を表示する）
  - OQ-01 の決定（投擲レイアウト）
  - 将来 M2b / M3 の実測値による較正

## Existing Spec Touchpoints

- **Extends**: なし
- **Adjacent**: `sensing-foundation` の入力層抽象に対し、
  本 Spec の出力が **simulated data** として繋がることを想定する
  （`development-environment.md §7`）。ただし今回は接続まで作り込まない

## Constraints

- **⚠️ 最大の落とし穴: シミュレータは前提を入れた分しか返さない。**
  楽観的なパラメータを入れれば「余裕で間に合う」という誤った安心が出力される。
  **M1 / M2 の実測値で較正されるまで「参考」扱いとする**ことを運用ルールとして明記する

  | 段階 | 位置付け |
  |---|---|
  | M1・M2 前 | 感度分析の道具。**絶対値を信用しない** |
  | M1 実測後 | 検出遅れ・予測誤差の実測値を反映 |
  | M2 実測後 | 加速度・最高速度・スリップの実測値を反映 |
  | 較正後 | レイアウト設計・改善検討に使える |

- **Python のみ。** ブラウザ側にアルゴリズムを置かない
- **Hono を使わない。** JSON を出力してブラウザが読むだけなら常駐サーバは不要
- 対象物は**空き缶**（φ65mm 程度の剛体）を仮値とする
