# Implementation Plan

> 本計画は `requirements.md`（要件1〜11 / 受入基準79件）と `design.md` に基づく。
> **実行時のサードパーティ依存はゼロ**（上流 `tests/prediction_core/test_packaging.py` が `dependencies == []` を固定しているため、
> 依存を足すと上流のテストが落ちる）。すべてのタスクはハードウェア非接続で完了・検証できる。
> 予測は `prediction_core` の公開 API 経由でのみ呼ぶ。**予測の数式をこのパッケージに書かない。**

## 1. 基盤: パッケージ骨組みと共有型

- [x] 1. 基盤: パッケージ骨組みと共有型

- [x] 1.1 パッケージを追加し、テスト実行基盤を用意する
  - 既存の `pyproject.toml` の wheel 対象へ新パッケージを追加する。**`[project] dependencies` は空のまま変更しない**
  - `src/` レイアウトで新パッケージの入口ファイルと、テストツリーの共通フィクスチャの器を作る
  - 共通フィクスチャは「検証を通る最小構成のパラメータ一式」を返す器とし、中身は 1.4 完了後に埋める
  - Python 3.11 で動く構文に限定する（PEP 695 のジェネリクス構文を使わない）
  - 観測可能な完了状態: ハードウェア非接続の環境で `python -m pytest` が成功終了し、新パッケージが import でき、上流 `tests/prediction_core/` の全テストが引き続き通る
  - _Requirements: 8.5, 11.3_

- [x] 1.2 (P) 単位換算モジュールを実装する
  - mm/s と mm/ms、mm/s² と mm/ms²、度とラジアンの相互換算を定義する
  - 換算係数をこのモジュールにのみ置き、他モジュールが `1000` / `1e6` / `π/180` を直接書かない方針を成立させる
  - 観測可能な完了状態: 換算の往復が定義どおりであることを検証するテストが通る
  - _Requirements: 2.6, 7.7_
  - _Boundary: Units_

- [x] 1.3 (P) 例外階層を定義する
  - 基底例外と、パラメータ不正・掃引定義不正・出力不正の3系統を定義する
  - 「シナリオの成否・評価対象外は値で返し、呼び出し方の誤りだけを例外にする」という区分をこの階層で表現する
  - 観測可能な完了状態: 各例外が基底例外としても `ValueError` としても捕捉できることを固定するテストが通る
  - _Requirements: 11.5_
  - _Boundary: Errors_

- [x] 1.4 パラメータ型と構築時検証を実装する
  - 投擲・ばらつき・観測・機体・キャッチ判定・レイアウト・較正段階・出所を、不変（frozen かつ slots）なデータクラスとして定義する
  - **機体性能（最高速度・加速度上限・減速度上限・制御周期・指令遅延）に既定値を与えない。** 省略した構築は失敗させる
  - キャッチ判定の許容誤差の既定値には導出根拠を docstring に併記する（開口半径から対象物寸法の半分を引く考え方、および残留速度の許容根拠）
  - 較正段階の既定値を「未較正」とし、対象物の代表寸法の既定値を空き缶の仮値とする
  - 予測パラメータは上流の設定型をそのまま保持し、独自の予測設定型を作らない
  - 非負であるべき量・比率の範囲・速度と加速度の正値性を構築時に検証し、違反フィールド名と値を含むメッセージで拒否する
  - 観測可能な完了状態: 機体性能を省略した構築、負の周期・遅延・標準偏差、範囲外の欠測率が拒否され、既定値が仕様どおりであることをテストで固定する
  - _Requirements: 1.4, 2.6, 4.1, 4.3, 5.1, 5.4, 7.7, 9.2, 10.1_
  - _Depends: 1.2, 1.3_
  - _Boundary: Params_

- [x] 1.5 ホイール径からの性能導出とパラメータパス表を実装する
  - ホイール径・モータ回転数・速度効率から最高速度を導出する構築手段を用意し、導出に使った値をパラメータへ残す
  - パラメータ木を走査して掃引が指定できるパスの表を生成し、単位をフィールド名の接尾辞から導く。手書きの表を二重管理しない
  - パス指定によるパラメータ置換を実装し、未知のパスを掃引定義エラーとして拒否する
  - パラメータ出所（実測 / 想定）のキーがパス表と一致することを検証する
  - 観測可能な完了状態: 60mm と 48mm のホイール径から異なる最高速度が導出され、未知のパス指定が拒否されることをテストで固定する
  - _Requirements: 4.2, 6.1, 9.4_
  - _Depends: 1.4_
  - _Boundary: Params_

- [x] 1.6 結果型とモデル除外要因の一覧を定義する
  - シナリオ結果・格子点結果・掃引結果を不変データクラスとして定義する
  - 評価対象外の理由（床面と交わらない / サンプルが無い / 有効な予測が無い）と格子点の状態（成立 / 不成立 / 評価対象外）を列挙型で定義する
  - **モデル除外要因の一覧を定数として定義する。** 投擲物理・観測・移動体・キャッチの各段について、初期モデルに含めなかった要因を列挙する（これが OQ-33 の決着内容そのものである）
  - 「成否が未定なら理由が必ず埋まる」という不変条件を構築時に検査する
  - 直列化をここに持たせない（構造と表現を分ける）
  - 観測可能な完了状態: 中途半端な結果（成否が未定なのに理由が空）の構築が拒否され、除外要因一覧が4段すべてを持つことをテストで固定する
  - _Requirements: 1.5, 2.8, 4.6, 5.7, 6.5, 6.7, 9.7_
  - _Depends: 1.4_
  - _Boundary: Results_

## 2. コア: 物理・運動・観測・予測接続

- [x] 2. コア: 物理・運動・観測・予測接続

- [x] 2.1 (P) 投擲物理モデルを実装する
  - リリース位置・初速・仰角・方位角・重力加速度から真の軌道を生成し、任意時刻の真の位置を算出できるようにする
  - 投擲条件のばらつきを、引数として受け取った乱数器から**固定の順序・固定の回数**で引いて適用する。ばらつきがゼロの項目では乱数を消費しない
  - 真の落下地点・落下時刻を二次方程式の未来側の根として解析的に求める。数値探索を行わない
  - 未来側の根が存在しない場合は例外ではなく「無し」を返す
  - 内部は mm/ms・mm/ms² で保持し、外部パラメータとの換算は単位モジュールを経由する
  - 観測可能な完了状態: 既知の初速と仰角に対する落下地点・落下時刻が解析解と丸め誤差の範囲で一致し、縮退した入力で「無し」が返ることをテストで固定する
  - _Requirements: 1.1, 1.2, 1.3, 1.6, 1.7_
  - _Depends: 1.4_
  - _Boundary: ThrowPhysics_

- [x] 2.2 (P) 到達可否の閉形式判定を実装する
  - 静止状態からの到達可能距離を、加速区間と最高速度飽和区間に分けて閉形式で算出する
  - 目標点で停止するために必要な最短所要時間を、三角形プロファイルと台形プロファイルの場合分けで算出する
  - 停止方針と通過方針それぞれについて、与えられた持ち時間で必要移動量に到達できるかを判定する
  - 機体性能値を自前で持たず、すべてパラメータから受け取る
  - 観測可能な完了状態: 三角形と台形の境界で到達可能距離が連続であること、加速度と減速度が等しいとき停止方針の所要時間が加速のみの2倍になることをテストで固定する
  - _Requirements: 5.2, 6.2_
  - _Depends: 1.4_
  - _Boundary: DrivetrainModel_

- [x] 2.3 時間最適追従の数値積分を実装する
  - 並進のみの質点として、目標方向への最大加速と最高速度の飽和を固定刻みで積分する
  - 停止方針では残距離が制動距離以下になった時点で最大減速へ切り替える。通過方針では行き過ぎを抑える制御を足さない
  - 目標の切り替えは制御周期の境界でのみ行い、指令反映遅れを経た更新だけを有効にする
  - 任意の終了時刻における位置と速度を返す。目標更新が1件も無い場合は始点に静止したままとする
  - 観測可能な完了状態: 単一目標を時刻0に与えた条件で、積分結果の到達距離が 2.2 の閉形式と積分刻み以内の誤差で一致することをテストで固定する
  - _Requirements: 4.4, 4.5, 4.7_
  - _Depends: 2.2_
  - _Boundary: DrivetrainModel_

- [x] 2.4 観測モデルを実装する
  - 検出開始遅れ以降、標本化周期ごとに真の軌道を標本化し、真の落下時刻を超えない範囲に限る
  - 軸ごとの標準偏差に、観測原点からの距離の2乗に比例する項を加えた実効標準偏差でノイズを付与する
  - 欠測率に従ってサンプルを脱落させる。乱数の消費順序を「欠測判定 → x → y → z」で固定し、標準偏差ゼロの軸では消費しない
  - 生成物は距離 mm・時刻 ms の時刻付き3次元位置の列とし、上流の型をパラメータモジュール経由で構築する
  - 観測可能な完了状態: 誤差要因をすべてゼロにしたとき生成サンプルが真の位置と厳密に一致し、標本化時刻が「検出開始遅れ + k × 周期」に一致することをテストで固定する
  - _Requirements: 2.1, 2.2, 2.3, 2.4, 2.5, 2.7_
  - _Depends: 2.1_
  - _Boundary: ObservationModel_

- [x] 2.5 (P) prediction-core への接続層を実装する
  - 上流の逐次追跡器にサンプルを1点ずつ追加し、返る結果を走査して有効な予測のみを目標更新へ変換する
  - 目標更新の反映時刻を「予測の基準観測時刻 + サンプル遅延 + 予測遅延」として算出する
  - 無効と判定された予測は理由を保持し、成功として扱わない。有効な予測が1件も無い場合はその旨を呼び出し側へ返す
  - Throw Record を simulated 由来として構築し、掃引の格子点番号・試行番号は上流が用意した拡張欄の**名前空間キー `"sim"` の1キーに収める**（`sim_extra_version` / `cell_index` / `trial_index`）。拡張欄のトップレベルへ項目を直接置かず、他 Spec の名前空間と衝突させない。**スキーマを再定義しない**
  - **フィッティング・床面交点・残差の計算をこの層に書かない**（上流の公開 API から得るのみ）
  - 観測可能な完了状態: 誤差ゼロのサンプル列に対する最終予測が真の落下地点と丸め誤差の範囲で一致し、最小サンプル数未満のみの入力で有効な予測が0件になり、構築された記録の拡張欄のトップレベルが `"sim"` の1キーのみで版フィールドを含むことをテストで固定する
  - _Requirements: 3.1, 3.3, 3.4, 3.5, 3.7, 3.9, 7.4_
  - _Depends: 1.4, 1.6_
  - _Boundary: PredictionLink_

## 3. 評価と掃引

- [x] 3. 評価と掃引

- [x] 3.1 シナリオ評価器を実装する
  - 全経路の評価（物理 → 観測 → 予測 → 運動 → 判定）と、運動モデルのみの到達可否評価の2つを実装し、**同じ結果型を返す**
  - 評価対象外を3種類の理由で区別し、不成立と混ぜない
  - 必要移動量を待機位置と真の落下地点の水平距離として、持ち時間を真の落下時刻と最初の指令反映時刻の差として算出する
  - 真の落下時刻における位置誤差と残留速度を算出し、停止方針では残留速度も判定に用いる。通過方針では記録するが判定に使わない
  - 代表シナリオ以外では Throw Record を保持しないようにする
  - 観測可能な完了状態: 誤差要因をすべてゼロにした条件で、全経路評価の成否が到達可否評価の結果と一致し、評価対象外の3経路がそれぞれ正しい理由で返ることをテストで固定する
  - _Requirements: 5.3, 5.5, 6.2, 6.3, 10.2_
  - _Depends: 2.3, 2.4, 2.5_
  - _Boundary: ScenarioEvaluator_

- [x] 3.2 掃引エンジンを実装する
  - 掃引仕様（種別・軸・試行回数・種・成立割合の閾値）を定義し、**評価を1件も行う前に**軸名・値・閾値の妥当性を一括検証する
  - 到達可否掃引の軸名を持ち時間と必要移動量に限定し、全経路掃引の軸名をパラメータパス表に載っているものに限定する
  - 試行回数が2以上のときは成立割合の閾値を必須とし、無ければ掃引定義エラーとする
  - 各試行の乱数の種を、基準種・格子点番号・試行番号から暗号学的ハッシュで導出する。プロセスごとに変わる組み込みハッシュを使わない
  - 格子点ごとに成立数・評価件数・成立割合・指標の平均を集計し、**評価対象外を分母から除く**。全試行が対象外の格子点は評価対象外とする
  - 観測可能な完了状態: 未知の軸名・空の軸・重複軸名・閾値未指定が拒否され、評価順序を反転しても各格子点の結果が変わらないことをテストで固定する
  - _Requirements: 6.1, 6.4, 6.6, 6.7, 8.1, 8.3_
  - _Depends: 3.1, 1.5_
  - _Boundary: SweepEngine_

## 4. 出力とエントリポイント

- [ ] 4. 出力とエントリポイント

- [x] 4.1 掃引結果の出力構造を組み立てる
  - 本 Spec 独自の出力形式の版を含める。**Throw Record のスキーマ版とは別のキー名**で表す
  - 較正段階を必須項目として出力し、未較正のときは「感度分析用であり絶対値を信用しない」旨の注意書きを必ず含める
  - パラメータ一式・パラメータ出所・モデル除外要因の一覧・軸の名前と単位と値の並びを出力に含める
  - 成立割合には、判定に用いた閾値を必ず併記する
  - 観測可能な完了状態: 出力辞書に較正段階・注意書き・除外要因・出所・軸の単位がすべて存在し、未較正が既定であることをテストで固定する
  - _Requirements: 7.1, 7.2, 7.3, 7.6, 7.7, 9.1, 9.3, 9.4, 9.6, 9.7_
  - _Depends: 3.2, 1.6_
  - _Boundary: ResultSerializer_

- [x] 4.2 出力の書き出しと断定的判定の排除を実装する
  - 代表シナリオが保持されている場合、上流が提供する変換で Throw Record をそのまま埋め込む
  - 非有限値や未知の列挙値を検出した場合は書き出さずに出力エラーとし、**部分的なファイルを残さない**
  - 出力キーの許可リストを設け、合否・達成・NFR-7 に相当する断定的な項目が含まれないことを保証する
  - 直列化は非 ASCII をそのまま出力し、キー順を固定し、非有限値を禁止する設定で行う
  - 観測可能な完了状態: 同一の掃引結果を2回書き出したファイルがバイト単位で一致し、断定的キーの混入がテストで検出されることを固定する
  - _Requirements: 7.4, 7.5, 8.2, 9.5, 10.5, 5.8_
  - _Depends: 4.1_
  - _Boundary: ResultSerializer_

- [ ] 4.3 コマンドラインエントリポイントを実装する
  - 設定ファイルと出力先を引数に取り、掃引を実行して結果ファイルを書き出す実行経路を用意する
  - 機体パラメータのみを別ファイルから取り込む指定を用意し、ホイール径の異なる構成を1オプションで差し替えられるようにする
  - 設定ファイルの未知のキーを黙って無視せず、パラメータ不正として報告する
  - **常駐しない。** サーバ・ソケット・監視ループを持たない
  - 観測可能な完了状態: 設定ファイルを指定した実行で出力ファイルが生成され、不正な設定では出力ファイルが生成されずにエラー終了することをテストで固定する
  - _Requirements: 7.5, 11.2_
  - _Depends: 4.2_
  - _Boundary: Cli_

- [ ] 4.4 実行可能な設定ファイル一式を用意する
  - 60mm ホイール前提と 48mm ホイール前提の機体パラメータを、**それぞれ独立したデータファイル**として用意する（どちらになるか未決であるため両方を置く）
  - 持ち時間 × 必要移動量を軸とする到達可否掃引の設定を用意する
  - 投擲レイアウト候補（投擲位置・方向・距離・待機位置）を軸とする掃引の設定を用意する
  - キャッチ方針を軸に含め、停止方針と通過方針が同一掃引で比較できるようにする
  - 各パラメータの出所を「想定値」として明示し、実測値との区別が出力に現れるようにする
  - 観測可能な完了状態: 4本の設定ファイルがそのまま 4.3 の実行経路で通り、それぞれ有効な出力ファイルを生成する
  - _Requirements: 4.8, 5.6, 10.3_
  - _Depends: 4.3_
  - _Boundary: configs/trajectory_sim_

## 5. 結合と検証

  - 同条件で全経路評価の成否が到達可否評価と一致することを検証し、**2つの評価器が食い違わない**ことを固定する
  - ハードウェア非接続・ネットワーク非接続で全経路が完走することを検証する

  - 予測経路に決定性を弱める要素が入っていないこと（上流が依存ゼロのまま呼ばれていること）を確認する
  - 観測可能な完了状態: 決定性・順序非依存・Replay 一致の3テストが通る
  - _Requirements: 8.2, 8.3, 8.4, 8.6_
  - _Depends: 4.4_

## Implementation Notes

- `tests/` 配下に `__init__.py` が無く pytest が prepend インポートモードのため、`tests/trajectory_sim/test_*.py` のベース名が `tests/prediction_core/test_*.py` と重複すると `import file mismatch` で収集が失敗する（1.1, 1.2 で発生・確認済み）。既知の衝突名: `test_packaging.py`（1.1 で `test_trajectory_sim_packaging.py` へ回避済み）、`test_units.py`（1.2 で `test_trajectory_sim_units.py` へ回避済み）、**`test_boundaries.py`（5.4 で衝突する見込み。着手時に `test_trajectory_sim_boundaries.py` 等へ改名すること）**。`--import-mode=importlib` への変更は `tests/prediction_core` 側の既存テスト（`test_predictor.py` 等の `import analytic`）を壊すため不採用。
- 1.5 で `PARAMETER_PATHS` の要素型 `ParameterPath` を design.md 未定義のまま実装した（design.md は `Mapping[str, ParameterPath]` としか書いていない）。`src/trajectory_sim/params.py` で `path: str` / `unit: str` / `component: str | None` / `field_name: str` を持つ frozen dataclass として定義済み。3.2（SweepEngine）と 4.1（ResultSerializer）はこの形に従うこと。
- 1.5 の `replace_by_path` は enum 系パス（`catch.policy` / `calibration_stage`）へ不正な文字列を渡すと `SweepDefinitionError` ではなく素の `ValueError`（enum コンストラクタ由来）を送出する。3.2（SweepEngine / `AxisSpec` 値検証）はこの値を検証時に `SweepDefinitionError` へラップし直すこと。
- 2.2 の `min_time_to_stop_at`（台形分岐）で、三角形/台形の境界distance付近では `v_peak_unsat` と `d1+d2` がIEEE754丸め誤差で最大機械イプシロン程度食い違い、`d_cruise` が微小負値になることがある（約0.5%のランダムパラメータで再現）。`assert d_cruise >= 0` ではなく `d_cruise = max(0.0, distance_mm - d1 - d2)` でクランプ済み。2.3（数値積分 `simulate`）・3.2（掃引の格子点が境界distanceに一致しうる）でも同種の境界丸め誤差に注意すること。
- 2.5 の `run_prediction` は `extra` 引数を「呼び出し側が既に `{"sim": {"sim_extra_version": "1.0", "cell_index": ..., "trial_index": ...}}` の形に整えたもの」として素通しするだけで、名前空間の組み立て自体は行わない（design.md の Responsibilities 文と Precondition 文が矛盾していたため、より具体的な Precondition 側を採用）。**3.1（ScenarioEvaluator）・3.2（SweepEngine）はこの `extra` 辞書を自分で組み立ててから `run_prediction` へ渡すこと。**`final_prediction` は最後に成立した有効予測（`tracker.first_valid` ではない）。
- 3.1 で `evaluate_throw` に design.md 未記載の5番目の引数 `extra: Mapping[str, object]`（既定は空）を追加した（`record_id` から cell_index/trial_index を逆算できないため）。**3.2（SweepEngine）は `record_id` と `extra` を同じ cell_index/trial_index から組み立て、両方を `evaluate_throw` へ渡すこと。**
- 3.1 で判明: `evaluate_reachability` の通過方針（PASS_THROUGH）判定は「持ち時間内に到達可能な累積距離」のみを見ており、「落下時刻ちょうどにその位置にいるか」は見ていない。通過方針は減速しないため、余裕のある持ち時間では目標を通り過ぎて離れてしまい、全経路評価（`evaluate_throw`）の成否と食い違うことがある（`drivetrain.py` の PASS_THROUGH 設計上の性質であり実装バグではない）。**5.1（誤差ゼロ E2E 検証）はこの不一致が停止方針（STOP_AND_WAIT）でのみ保証される前提で書くこと。** `drivetrain.align_to_control_tick_ms`（新規公開関数）は `_active_target` の切り替え境界と同じ式（ceil）を提供する。
- 3.2 のレビューで判明: `params.replace_by_path` は enum 系パス（`catch.policy`/`calibration_stage`）へ不正な文字列を渡すと素の `ValueError` を送出する（1.5 の申し送り事項）。`sweep.py` は `_validate_spec` の時点で全軸の全値を `replace_by_path` で事前に1回ずつ検証し、この `ValueError` を `SweepDefinitionError` へ包んで「1件も評価する前に」拒否する。**4.x（設定ファイル・CLI）で軸を持たない単発のenum値検証が必要になった場合も、同じ`ValueError`→`SweepDefinitionError`変換パターンに倣うこと。**
- 2.3 のレビューで判明: 閉形式一致テストの許容誤差を緩く取りすぎると、積分順序（速度更新→速度上限クランプ→位置更新の順）のバグを検出できないことがミューテーションテストで確認された。以降の数値積分系タスクでは、許容誤差をバイアス量から解析的に導出するか、少数ステップの厳密な手計算値（`abs=1e-9`級）で固定するテストを併用すること。
