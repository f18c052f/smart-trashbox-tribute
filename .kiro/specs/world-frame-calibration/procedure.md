# 設置手順書: world-frame-calibration

> 本書は `.kiro/specs/world-frame-calibration/tasks.md` タスク 7.4（要件 7.2, 7.3,
> 7.5, 7.6, 11.3）の成果物であり、**設置のたびに実施する手順**を定める
> （`requirements.md` A-3「一度きりの作業として設計しない」）。
>
> 対象読者はシステムの設置者であり、本書だけを読めば、計画ファイルの作成から
> 検証の合否判定までを実行できる状態を目指す（tasks.md タスク 7.4「観測可能な
> 完了状態」）。コマンドの正確な引数一覧は、本書の例に加えて必ず
> `python -m world_frame_calibration.cli <サブコマンド> --help` でも確認すること
> （引数は今後 CLI 側の変更で増減しうるため、`--help` が常に一次情報である）。

## 0. 全体の流れ

```
1. 物理準備（マーカー・検証点の設置）
2. 計画ファイル（plan.json）の作成
3. calibrate（床平面推定 → マーカー観測 → World frame 確立 → 保存）
4. show（現在の入力元との整合性確認）
5. verify（独立検証。★ 必須。ここを経ていない結果は運用に使わない）
6. 合否の読み方・レポートの読み分け
7. （推奨）再現性の確認：2回実施して compare、measurements.md へ記録
8. 移動体オドメトリ原点の初期化（手順のみ。実装は M3）
```

検証（手順5）を経ていない結果は、**運用に用いてよい状態として扱わない**
（要件 7.3）。`calibrate` サブコマンドは保存直後に必ず

```
検証は未実施（verify サブコマンドを実行するまで運用に用いないこと）。
```

と表示する。この表示が出た結果を、検証なしでそのまま下流（`flying-object-tracking`
/ `m1-prediction-validation`）へ渡してはならない。

## 1. 物理準備

### 1.1 マーカーの置き方

World frame の確立には2つのマーカーが要る（`requirements.md` A-2 / 要件 2）。

| マーカー | 役割 | 置き場所の目安 |
|---|---|---|
| 原点マーカー | World frame の原点になる | 運用上はゴミ箱の待機位置 |
| 方向マーカー（+X 軸） | 原点から見た +X 方向を決める | 運用上は投擲方向（投擲者 → キャッチ領域）に一致させる |

マーカーに**特定の色・柄・既知寸法は不要**である（要件 2.6）。必要なのは
「床の上に置かれた、周囲の床面から区別できる高さを持つ物体」であることだけ
である。理由は次の2点（`requirements.md` A-2）:

- **色を使わない**: `sensing-foundation` は既定で Color ストリームを切っている。
  マーカー観測が色に依存すると、その既定を壊すか、キャリブレーションだけ
  別設定で走らせることになる
- **高さを既知にしない**: マーカーの観測点は床平面へ法線方向に投影してから
  使うため、マーカーの高さそのものは結果に影響しない。既知寸法を要求すると、
  運用のたびに同じ物体を用意する制約が増えてしまう

計画ファイル（`plan.json`）側では、各マーカーに `region`（探索する画素範囲）と
`height_band_mm`（床平面からの高さの下限・上限）を指定する。`height_band_mm`
は「床面のノイズ」と「マーカー」を高さで区別するための帯であり、置いた
マーカーの実際の高さを覆うように設定すること。

### 1.2 基線長（マーカー間距離）の目安と、下限が存在する理由

原点マーカーと方向マーカーの床平面上の距離（基線長）には**下限**がある
（`plan.py` の `PlanLimits.min_baseline_mm`、既定値 800.0mm）。この下限は
**暫定値**であり、実測による裏付けはまだない（実測は tasks.md タスク 8.3 が
担う）が、次の根拠から置かれている（`plan.py` docstring をそのまま引く）:

> 原点マーカーと方向マーカーの観測位置には、それぞれ**観測誤差約 10 mm**
> 程度のばらつきがあり得る。基線長（マーカー間距離）が短いほど、この誤差が
> +X 軸の向きへ与える角度誤差（ヨー誤差）が増幅される。目安として、
> **距離 2 m（2000 mm）先で横ずれ約 25 mm** となる基線長を下限として置いた。

言い換えると、マーカーを近づけて置くほど、わずかな観測誤差が +X 軸の向き
（＝投擲方向の基準）を大きく振ってしまう。基線長を延ばすことは、この
ヨー誤差の増幅を抑える最も簡単な手段である。**目安として基線長は 800mm 以上、
できればそれより十分長く取ること。** 確立結果には基線長から算出した
「ヨー感度」（`yaw_sensitivity_deg_per_mm` / `lateral_error_mm_per_mm_at_1000mm`）
が含まれており、`show` コマンドの出力でこの値を確認できる。

基線長が下限を下回ると、`calibrate` は **+X 軸が不安定である旨とともに
失敗し、変換を返さない**（要件 2.7, 5.3。縮退条件は警告ではなく失敗として
扱われる）。

### 1.3 床探索範囲（`floor_region`）の取り方

`plan.json` の `floor_region` は、床平面推定に使う Depth 画像上の画素範囲
（`x0_px, y0_px, x1_px, y1_px` の半開区間）である。

- **床面だけを含み、壁・天井・什器を含まない範囲**を選ぶこと。壁や天井が
  範囲に入ると、誤った平面をつかんでしまう可能性がある
- 範囲は全画素である必要はなく、平面推定に十分な点数（既定の下限
  `min_inlier_points=2000` 点、`min_inlier_ratio=0.5`）が確保できれば足りる。
  本 Spec は**全画素の3次元展開を必須としない**設計であるため、範囲を
  絞ることは計算量の観点でも推奨される（`development-environment.md §4`）
- 実際の設置における「範囲の取り方」の知見（壁・天井を誤って含めた事例など）
  は、実機作業（タスク 8.1）が進んだ時点で `measurements.md` へ蓄積し、
  本書へ反映していく

### 1.4 検証点の配置とメジャー実測の記録

独立検証（手順5）には、**World frame の確立に使ったマーカー以外の点**が
最低1点必要である（要件 4.3）。確立に使った点（原点マーカー・方向マーカー
自身）を検証点に使っても、`result.transform` はその点を定義上誤差ゼロで
再現するため、検証にならない（自己言及であり、座標系が本当に正しいことの
証拠にはならない）。

検証点を置く際は次を行う:

1. 床上、または既知の高さの位置に対象物を置く（マーカーと同様、色・柄・
   既知寸法は不要。ただし床面から区別できる高さが要る）
2. その点の **World 座標をメジャー（巻尺・測距器など）で実測**し、
   `plan.json` の `verification_points[].truth_world_mm`（`[x_mm, y_mm, z_mm]`）
   に記録する。床上の点なら `z_mm = 0` でよい（要件 4.9 は、床上の点に加えて
   既知の高さを持つ点も同じ形式で扱えることを求めている）
3. 実測手段を `verification_points[].truth_source` に必ず記録する（例:
   `"巻尺実測"` `"三脚高さ計測"`）。この項目は空欄を許さない必須項目である
4. 検証点の `label` は原点マーカー・方向マーカーのラベルと重複させない

**推奨する検証点の数と配置**: 少なくとも1点（独立検証が成立する最小数）
だが、実機での本格運用（タスク 8.2 が定める基準）では**3点以上、うち1点は
想定される投擲距離の端**に置くことを推奨する。理由は、検証レポートが
「距離帯ごとの誤差」（手順6の読み分け規則を参照）を報告するためであり、
近距離の点だけでは Depth の距離依存誤差（遠方ほど大きくなる特性）を
検出できない。

## 2. 計画ファイル（plan.json）の作成と保管

### 2.1 plan.json の内容

計画ファイルは `CalibrationPlan`（`src/world_frame_calibration/plan.py`）の
JSON 直列化であり、次を1つにまとめる:

- `plan_format_version`（現在 `"1.0"`）
- `floor_region` — 床探索範囲
- `origin_anchor` / `x_axis_anchor` — 原点・方向マーカーの `region` と
  `height_band_mm`
- `verification_points` — 検証点ごとの `region` / `height_band_mm` /
  `truth_world_mm` / `truth_source`
- `limits` — 縮退条件の下限群（`PlanLimits`。既定値はすべて暫定。
  `min_inlier_points` / `min_inlier_ratio` / `plane_inlier_threshold_mm` /
  `min_incidence_angle_deg` / `min_baseline_mm` / `min_anchor_samples` /
  `ransac_success_probability` / `ransac_outlier_ratio` / `rng_seed`）
- `tolerance` — 検証の合否判定に使う許容値（`horizontal_mm` / `vertical_mm` /
  `provisional` / `source`）。未定なら `null` でよい（合否は判定せず、
  誤差の実測値のみが報告される。要件 4.7）
- `expected_baseline_mm` — 原点・方向マーカー間の距離のメジャー実測値
  （World frame の定義には使わず、スケールの独立確認にのみ用いる）
- `notes` — 自由記述

サンプルとして最小構成を示す（値は仮のものであり、実際の設置に合わせて
必ず作り直すこと）:

```json
{
  "plan_format_version": "1.0",
  "floor_region": {"x0_px": 40, "y0_px": 200, "x1_px": 600, "y1_px": 460},
  "origin_anchor": {
    "label": "origin",
    "region": {"x0_px": 280, "y0_px": 300, "x1_px": 340, "y1_px": 360},
    "height_band_mm": [30.0, 200.0]
  },
  "x_axis_anchor": {
    "label": "x_axis",
    "region": {"x0_px": 280, "y0_px": 60, "x1_px": 340, "y1_px": 120},
    "height_band_mm": [30.0, 200.0]
  },
  "verification_points": [
    {
      "label": "vp_near",
      "region": {"x0_px": 200, "y0_px": 180, "x1_px": 260, "y1_px": 240},
      "height_band_mm": [30.0, 200.0],
      "truth_world_mm": [500.0, 300.0, 0.0],
      "truth_source": "巻尺実測"
    },
    {
      "label": "vp_far",
      "region": {"x0_px": 400, "y0_px": 80, "x1_px": 460, "y1_px": 140},
      "height_band_mm": [30.0, 200.0],
      "truth_world_mm": [2800.0, -150.0, 0.0],
      "truth_source": "巻尺実測"
    }
  ],
  "limits": {
    "min_inlier_points": 2000,
    "min_inlier_ratio": 0.5,
    "plane_inlier_threshold_mm": 15.0,
    "min_incidence_angle_deg": 10.0,
    "min_baseline_mm": 800.0,
    "min_anchor_samples": 50,
    "ransac_success_probability": 0.999,
    "ransac_outlier_ratio": 0.5,
    "rng_seed": 0
  },
  "tolerance": null,
  "expected_baseline_mm": null,
  "notes": "サンプル。実際の設置ごとに画素範囲・実測値を作り直すこと。"
}
```

`limits` の既定値はコード側（`PlanLimits` の dataclass 既定値）から省略しても
補われるが、根拠を意識するためにも明示しておくことを推奨する。

### 2.2 保管上の最重要事項: 計画は設置ごとに作り直す

**`plan.json` は設置のたびに新しく作り直すものであり、前回設置の計画
ファイルをそのまま使い回してはならない。** マーカーの画素上の位置
（`region`）や床探索範囲は、カメラの設置位置・向き・解像度が変われば
当然変わり、検証点の実測座標（`truth_world_mm`）も設置ごとの物理配置に
紐づく。前回の plan ファイルを流用すると、実際には別の場所を指している
`region` に対して「たまたま」有効なマーカーが観測されてしまう、あるいは
検証点の真値が現在の物理配置と食い違ったまま検証が走る、という事故に
つながる。

運用上は、設置ごとに新しい `plan.json` をその設置専用のファイル名
（例: `plan_2026-08-22_desk-mount.json`）で作成し、過去の plan ファイルは
参照用として残しておく（上書きしない）ことを推奨する。

## 3. 実行順序

以下はすべて `python -m world_frame_calibration.cli <サブコマンド> ...`
の形で実行する。各サブコマンドの正確な引数は `--help` で確認できる
（下記の例は本書執筆時点の `src/world_frame_calibration/cli.py` を確認して
書いている）。

### 3.1 calibrate — 確立

```
python -m world_frame_calibration.cli calibrate \
    --plan plan.json \
    --source live \
    --frames 10 \
    --out var/calibration/my_result.json
```

- `--source` は `live` / `recorded` / `simulated` のいずれか（既定 `live`）。
  実機が無い環境では `recorded`（`--session` で再生対象のセッション
  ディレクトリを指定）を使う。**`simulated` は本 Spec の実測パイプラインを
  通せない**（合成入力にはカメラ内部パラメータの概念が無く、本 Spec は
  内部パラメータを独自の固定値で補わない設計であるため。実機なしでの
  end-to-end 確認は自動テスト側の合成データ経路が担う）
- `--frames` は収集するフレーム数（既定 10。初期評価候補であり暫定）
- `--out` を省略すると `var/calibration/<calibration_id>.json` に保存される
- `--log-path` / `--no-log` で構造化ロギングの出力先・有効無効を制御できる

内部では「収集 → 平面推定 → マーカー観測（原点） → マーカー観測（方向）
→ frame 確立 → 保存」の順に進み、**いずれかの段が失敗すればその場で停止
する**（縮退条件は警告ではなく例外として扱われ、部分的な結果は返らない。
要件 5）。実行が成功すると、結果の要約・保存先とともに次が表示される:

```
検証は未実施（verify サブコマンドを実行するまで運用に用いないこと）。
```

**この時点の結果は、まだ運用に用いてはならない。**

### 3.2 show — 整合性の確認（推奨）

```
python -m world_frame_calibration.cli show \
    --calibration var/calibration/my_result.json \
    --source live
```

保存済み結果を読み込み、現在の入力元のストリーム設定・カメラ内部パラメータ
と一致するかを検査する（内部的には `check_compatibility` を呼ぶ）。解像度
や fps が保存時と食い違っていれば、ここで不一致として検出され、非ゼロの
終了コードとともにエラーメッセージが標準エラーへ出る。`calibrate` の直後に
`show` を挟むことで、続く `verify` の前に設定不一致を早期に発見できる。

### 3.3 verify — 検証（★ 必須。省略しない）

```
python -m world_frame_calibration.cli verify \
    --plan plan.json \
    --calibration var/calibration/my_result.json \
    --source live \
    --tolerance-horizontal-mm 30.0 \
    --tolerance-vertical-mm 20.0 \
    --tolerance-source "暫定目標値（実測前）" \
    --out var/calibration/my_result.verification.json
```

**検証は手順の必須段階であり、省略してはならない**（要件 7.3）。検証を
経ていない `calibrate` 直後の結果を、そのまま `flying-object-tracking` /
`m1-prediction-validation` へ渡す運用は許されない。

- `--plan` の検証点（`verification_points`）を現在の入力元から観測し、
  保存済み結果の変換を適用して World 座標を算出、実測値との誤差を
  算出する
- `--tolerance-horizontal-mm` / `--tolerance-vertical-mm` は**同時に**
  指定する。省略した場合は `plan.json` の `tolerance` を用い、それも
  無ければ「未判定」として扱われる（誤差の実測値そのものは、許容値の
  有無に関わらず必ず出力される。要件 4.7）
- `--tolerance-source` は与えた許容値の出典説明、`--tolerance-final` を
  付けると「実測由来（暫定でない）」ことを明示する。付けなければ
  「暫定」として扱われる
- `--out` を省略すると `var/calibration/<calibration_id>.verification.json`
  に検証レポートが保存され、対象の `CalibrationResult` にも検証要約が
  関連付けられて再保存される（`verification_state` が `not_verified` から
  `passed` / `failed` / `not_judged` のいずれかへ遷移する）

**終了コードの意味**（これは本 CLI で最も安全性に関わる契約である）:

| 状況 | 終了コード |
|---|---|
| 許容値を指定していない（未判定 `not_judged`） | `0`（成功） |
| 許容値を満たした（合格 `pass`） | `0`（成功） |
| 許容値を満たさなかった（不合格 `fail`） | `0` 以外 |

「判定していないこと」と「不合格」は明確に区別される。**許容値を与えずに
実行した `verify` が終了コード 0 を返しても、それは合格を意味しない。**
標準出力のレポート先頭の「判定」行を必ず確認すること（手順4参照）。

### 3.4 compare — 再現性の確認（手順7で使用）

```
python -m world_frame_calibration.cli compare result_a.json result_b.json
```

2つの保存済みキャリブレーション結果ファイルだけを引数に取り、入力元や
計画ファイルを必要としない。詳細は手順7を参照。

## 4. 合否の読み方とレポートの読み分け規則

`verify` の標準出力（および保存される検証レポート）の先頭3行は、
**判定・最大誤差・バイアス**の順に固定されている。まずこの3行を確認する:

```
判定: 合格 (pass) / 不合格 (fail) / 未判定 (not_judged)
最大誤差: 全体=... 水平=... 垂直=...
バイアス: x=... y=... z=...
```

続けて「ばらつき(残差RMS)」「許容値（暫定か実測由来かを併記）」
「独立点数」「距離帯ごとの集計」が出力される。

### 4.1 誤差の内訳をどう読むか

検証レポートは誤差を3つの軸へ分解して報告する（要件 A-4 / 4.4 / 4.5）。
**この読み分け規則は本 Spec の中心的な価値**であり、`verify.py` /
`report.py` の docstring がそのまま定めているものを以下に引く:

> バイアス支配なら座標系、ばらつき支配なら観測、遠方だけ大きいなら
> Depth の距離特性。

- **バイアス（全検証点に共通して乗っている軸ごとの平均オフセット）が
  支配的に大きい**場合: World frame の確立（座標系）そのものに系統的な
  ずれがある可能性が高い。原点マーカー・方向マーカーの観測や、床平面
  推定を見直す
- **ばらつき（バイアスを除去した残差の RMS）が支配的に大きい**場合:
  個々の観測（マーカー観測・Depth のランダムノイズ）のばらつきが原因で
  ある可能性が高い。観測手順（サンプル数・観測範囲の取り方）を見直す
- **距離帯ごとの集計のうち、遠方の帯だけ誤差が大きい**場合: Depth
  センサの距離依存誤差特性（測距誤差が距離に応じて増大する性質）が
  原因である可能性が高い。近距離側は問題ないため、座標系そのものを
  疑う前にこの可能性を検討する

この3層の切り分けこそが、`docs/requirements.md §6.2` が警告する「予測が
悪いようにしか見えない座標系ずれ」を、検出・予測を一切動かさずに
最初に切り分けるための仕組みである（`requirements.md` A-1, A-4）。

### 4.2 スケール確認（併せて確認する）

`--tolerance-*` の合否とは別に、`expected_baseline_mm`（`plan.json` に
メジャー実測の基線長を記録していれば）を指定していれば、レポートは
「スケール確認」として、World frame の確立に使ったのと**独立な**距離
（マーカー間の絶対距離）の実測値と算出値の差も報告する。この差が大きい
場合も座標系の疑いの材料になる。

## 5. 再現性の確認（推奨）

`requirements.md` A-3 は「再実施した結果どうしを比較でき、再現性を数値で
確認できること」を求めている（要件 7.4）。実施方法:

1. 同一の物理配置（マーカー・カメラともに動かさない）で `calibrate` を
   もう一度実行し、別のファイル（例: `result_run2.json`）へ保存する
2. `compare` サブコマンドで2つの結果を比較する:

   ```
   python -m world_frame_calibration.cli compare \
       var/calibration/my_result.json \
       var/calibration/result_run2.json
   ```

3. 出力される差分（原点のずれ・全体回転角・Z軸のずれ・ヨーのずれ）を
   確認する。**Z軸のずれは平面推定の再現性、ヨーのずれはマーカー設置の
   再現性を表す**（`result.py` / `report.py` の読み分けと同じ）:
   - Z軸のずれが大きい → 床平面推定（`FloorPlaneEstimator`）が安定して
     いない
   - ヨーのずれが大きい → マーカー観測・設置そのものが安定していない
4. 実機でこの手順を行った場合は、比較結果を `measurements.md` の該当節へ
   記録する。マーカーを置き直した場合の再現性と、置いたままでの再現性は
   分けて記録すること（タスク 8.3 が定める）

`compare` は保存済みの結果ファイル2つだけで完結し、入力元・計画ファイル
のいずれも必要としない。

## 6. 移動体オドメトリ原点の初期化（手順のみ。実装は M3 の範囲）

`requirements.md` A-8 / 要件 7.5 が定める事項である。

**World frame の原点は、物理的には原点マーカーを置いた位置そのもの**
である（要件 2.2: 原点マーカーの観測点を床平面へ投影した点が World 原点）。
したがって、**移動体（ゴミ箱）を原点マーカーの位置に置き、+X 方向
（＝方向マーカーへ向かう向き、運用上は投擲方向）へ正しく向ければ、
移動体自身のオドメトリ原点が World 原点と一致する**、という物理的な
関係が成り立つ。

> ⚠️ **この関係を実際にソフトウェアとして実装し、移動体のオドメトリを
> World frame へ初期化する処理そのものは、本 Spec の範囲外であり
> M3（結合）の担当である。** 本 Spec が持つのはこの物理的な関係の
> 定義と、設置者が理解すべき手順の記述までであり、初期化の実装方法・
> タイミング・移動体側の座標変換ロジックには立ち入らない
> （`design.md` Out of Boundary「移動体オドメトリの実装、目標座標の送信、
> 移動体側のすべて（M3 以降）」/ 要件 11.3）。

設置者としては、原点マーカーの物理位置を「移動体の待機位置」としてそのまま
運用に用いる、という理解だけを持っていればよい。原点マーカー自体は
キャリブレーション実施後も同じ位置に残しておくと、この物理的な基準点が
明確なまま保たれる。

## 7. 再実施（再キャリブレーション）が必要な条件

次のいずれかが発生した場合、**手順全体を再実施すること**（要件 7.6）。
古い結果を使い続けると、設定が変わったまま古い結果を使い続ける事故に
つながる（保存された結果は `show` / `verify` 実行時に現在の入力元との
整合性が自動検査され、ストリーム設定・カメラ内部パラメータが食い違えば
`PROFILE_MISMATCH` として検出されるが、**マーカーやカメラの物理的な移動は
この検査では検出できない**ため、以下は運用者自身が判断する必要がある）:

- **カメラが移動した**（設置位置・向きが変わった。三脚を蹴った、壁固定を
  外して付け直した、など）
- **設置形態が変わった**（壁固定 ⇔ 三脚の切り替えなど。OQ-06 は未決着で
  あり、どちらでも成立する方式ではあるが、切り替えれば再実施が要る）
- **ストリーム設定（解像度・fps）が変わった**（解像度が変わればカメラ
  内部パラメータも変わるため、古い結果の使い回しは静かにずれる）
- **マーカーの位置が変わった**（原点マーカー・方向マーカーを置き直した）
- **床が変わった**（床材の張り替え、設置場所そのものの変更など、床平面
  の実際の高さ・傾きが変わりうる変更）

## 参考: 各コマンドの失敗時の挙動

いずれのサブコマンドも、縮退条件（平面推定の失敗、マーカー未検出、基線長
不足など）に該当すると、部分的な結果や既定値で埋めた結果を返さずに
失敗する（要件 5.5）。失敗時は理由（`FailureReason`）と文脈情報
（実測値・判定に用いた下限など）が必ず標準エラーへ出力される。エラー
メッセージに従って、物理配置・計画ファイルの該当箇所を見直すこと。
