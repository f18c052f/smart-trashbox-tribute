# Research & Design Decisions: world-frame-calibration

## Summary

- **Feature**: `world-frame-calibration`
- **Discovery Scope**: New Feature（既存コードなし）＋ Complex Integration（上流 `sensing-foundation` の契約に乗る）
- **Key Findings**:
  - **面内3自由度（原点 x, y とヨー）は床平面フィッティングだけでは決まらない。** 平面推定が拘束するのはロール・ピッチ・高さの3自由度だけである。残る3自由度を何で決めるかが OQ-03 の実質的な争点であり、ここを曖昧にしたまま実装すると「床平面は合っているのに座標が数 cm ずれる」という、まさに `docs/requirements.md §6.2` が警告した状態になる
  - **マーカーの高さを既知にする必要はない。** 観測点を床平面へ法線方向に投影すれば高さは消える。これにより「特定の校正治具を毎回用意する」制約が消え、`brief.md` の「設置のたびに実施する。一度きりの作業として設計しない」を満たしやすくなる
  - **単点の Depth は信用できないが、面と統計は信用できる。** D435 の Depth 誤差は距離とともに増大する（ベンダ公称値ベース。自分の個体では未実測）。したがって平面は数千点の当てはめで、マーカーは範囲内の多数画素のロバスト代表値で決める。単画素の値をそのまま使う設計にしない
  - **OpenCV は不要。** 必要な演算は最小二乗平面当てはめ（SVD）、RANSAC、ピンホール逆投影、正規直交化、統計量のみで、いずれも NumPy で完結する
  - **検証の価値は「誤差の大きさ」ではなく「誤差の分解」にある。** 平均オフセット（＝座標系のずれ）とばらつき（＝Depth ノイズ）と距離依存性を分けて出さないと、切り分けの道具にならない

## Research Log

### 上流契約: `sensing-foundation` が何を渡してくるか

- **Context**: 本 Spec は Depth を自前で取得しない。何が手に入り、何が手に入らないかを確定させないと設計できない
- **Sources Consulted**: `.kiro/specs/sensing-foundation/design.md`（Boundary Commitments / Dependency Direction / File Structure Plan / CoreTypes / FrameSource / SessionReader / StructuredLogger）
- **Findings**:
  - 入口は `for frame in source.frames():` の1本。`CaptureFrame` は `depth`（`numpy.uint16`, shape=(h, w), **読み取り専用**）、`profile`（`StreamProfile`: 解像度・fps・`depth_scale_mm`・`color_enabled`・`intrinsics`）、`t_capture_ms`、`source`（`SourceKind`）を持つ
  - `CameraIntrinsics` は `fx_px` / `fy_px` / `ppx_px` / `ppy_px` / `model` / `coeffs`（5要素）を持つ。**逆投影の関数は提供されない**
  - 構造化ログは NDJSON。予約 stage は `system` / `capture` / `record` のみで、**下流は自分の stage 名を足してよい**（`logger.stage(...)` / `logger.timed(...)`）
  - 記録セッションは `manifest.json` + `frames.ndjson` + `depth.bin` + `summary.json`。`SessionReader` 経由で読め、**SDK も実機も無い環境で再生できる**
  - `sensing_foundation` は OpenCV を**意図的に導入していない**。宣言済みのサードパーティ依存は `numpy` のみで、extras として宣言されている
- **Implications**:
  - **逆投影（画素 + Depth → カメラ座標）は本 Spec が実装する。** これは上流の欠落ではなく境界の置き方の結果であり、`pyrealsense2` に依存しないという利点がある
  - **Depth 配列を in-place で書き換えない。** 平均化・マスク処理はすべて新しい配列を確保する。破ると Replay の再現性が壊れる
  - stage 名は `calibrate` を使う。予約名と衝突しない
  - recorded セッションだけで全機能を動かせるため、**要件 9（ハードウェア非依存の検証可能性）は上流の設計によって既に道が開いている**

### 床平面推定の手法選定

- **Context**: D435 に IMU が無いため、床平面 ＝ カメラ姿勢の唯一の情報源になる（`docs/bom.md §A` の選定根拠）
- **Findings**:
  - 平面当てはめの標準手順は「点群の重心を引いて 3×N 行列の SVD を取り、最小特異値に対応する特異ベクトルを法線とする」。これは総最小二乗（直交回帰）であり、z 方向の残差だけを最小化する回帰より平面に対して素直である
  - 床面には家具の脚・ケーブル・ゴミ箱本体などの外れ値が乗るため、素の最小二乗だけでは引きずられる。RANSAC で内点集合を選び、**内点だけで最終の SVD をやり直す**構成が一般的で、実装量も小さい
  - 反復回数は「必要な成功確率 p、外れ値率 e、最小サンプル数 s」から `N = log(1-p)/log(1-(1-e)^s)` で決まる。s=3 の平面では外れ値率 50% でも N は数十回で足りる。**固定値をハードコードせず、この式から導く**（`tech.md` 開発標準1「根拠のない固定値をコードに埋め込まない」）
  - Open3D / PCL / OpenCV いずれも不要。SVD は `numpy.linalg.svd`、RANSAC の候補抽出は `numpy.random.Generator` で足りる
- **Implications**:
  - **NumPy のみで完結する。** `sensing_foundation` が引いた「OpenCV は `flying-object-tracking` の道具」という線を越えずに済む
  - RANSAC の乱数は**シードを設定・記録可能**にする。要件 9.4（同一入力に同一結果）を満たすため

### 面内3自由度をどう決めるか（OQ-03 の核心）

- **Context**: 床平面はロール・ピッチ・高さしか拘束しない。原点（x, y）とヨーを何で決めるかを選ぶ必要がある
- **Findings**（候補と評価は下の [Architecture Pattern Evaluation](#architecture-pattern-evaluation) を参照）:
  - カメラ基準（原点＝カメラの床面投影、+X＝光軸の床面投影）は完全自動だが、**カメラを動かすたびに World frame が動く**。移動体のオドメトリ原点を合わせる手順（`docs/requirements.md §6.2` 手順3）が成立しない
  - チェッカーボード等の平面校正パターンは面内3自由度を一発で決められるが、**Color stream と OpenCV が要る**。`sensing-foundation` は Color を既定で切っており（`docs/development-environment.md §13.2` の改善順序1）、その既定を壊す
  - 床上に置いた**2つの物体マーカー**なら Depth だけで観測でき、Color も既知寸法も不要。マーカーの観測点を床平面へ投影するため、**高さが未知でも影響しない**
- **Implications**: 物体マーカー方式を採用する。詳細は [Decision 1](#decision-1-world-frame-の面内3自由度を床上の2マーカーで決める-oq-03)

### Depth の誤差特性と、それが設計に与える制約

- **Context**: 「数 cm のずれ」が問題になる Spec なので、そもそも Depth 単点でどこまで出るのかを把握しておく必要がある
- **Findings**:
  - RealSense D4xx 系のステレオ Depth 誤差は原理的に**距離の二乗に比例して増大**する（視差の量子化誤差が距離の二乗で効く）。ベンダは D435 について「2 m で 2% 未満」の水準を公称している
  - ⚠️ **これはベンダ公称値であり、本プロジェクトの個体・設置条件での実測値ではない。** `tech.md` 開発標準1 に従い、合否条件として使わない。設計上の「単点を信用しない」判断の根拠としてのみ用いる
  - 一方、平面当てはめは数千点の平均化に相当するため、ランダム誤差は点数の平方根で縮む。マーカー観測も範囲内の多数画素の中央値を取れば同様
  - 系統的な歪み（キャリブレーション由来のバイアス、温度ドリフト）は平均化で消えない。**これこそが検証で捕まえたい対象**である
- **Implications**:
  - 平面は面で、マーカーは範囲で決める。**単画素の Depth をそのまま使う経路を作らない**
  - 複数フレームの平均化を用意する（時間方向のランダム誤差の低減）
  - 検証レポートは**距離帯ごとに**誤差を示す。「遠方だけ大きい」＝ Depth 誤差、「全域で一様」＝ 座標系ずれ、という切り分けを可能にする

### ヨー誤差の増幅と、マーカー間距離の下限

- **Context**: +X 軸を2マーカーから決めるなら、マーカーが近いほど角度誤差が大きくなる。どこまで許すかを設計時に決める必要がある
- **Findings**:
  - マーカー観測の位置誤差 `e`、マーカー間距離（基線長）`b` に対し、ヨー誤差はおよそ `atan(e / b)`
  - このヨー誤差は、原点から距離 `r` の点で `r · e / b` の横方向誤差を生む。**原点から遠いほど増幅される**
  - 例: `b = 300 mm`, `e = 10 mm` のとき、`r = 2000 mm` の点では約 67 mm の横ずれ。`b = 800 mm` なら約 25 mm
  - つまり**基線長は「短くても動くが、静かに精度を殺す」典型的な罠**であり、警告ではなく拒否とレポートの両方で扱う価値がある
- **Implications**:
  - 基線長の下限を設定可能なパラメータとして持ち、下回ったら**失敗させる**（要件 2.7 / 5.3）
  - 基線長から算出した**ヨー感度**を確立結果に含め、レポートに出す（要件 2.8）。これは「なぜこの誤差が出たのか」を後から説明できる唯一の材料になる
  - 既定値 800 mm は上の計算から置いた**暫定値**であり、根拠を併記して実測で見直せるようにする

### 逆投影とレンズ歪みの扱い

- **Context**: `sensing-foundation` は `CameraIntrinsics` を渡すが逆投影関数は提供しない。歪み係数をどう扱うかを決める必要がある
- **Findings**:
  - ピンホールの逆投影は `x = (u - ppx) / fx · z`, `y = (v - ppy) / fy · z`。`z` は Depth の生値 × `depth_scale_mm`
  - RealSense の Depth ストリームはステレオ演算の前段で整流されているため、**Depth ストリームの歪み係数は 0 であることが通例**である。SDK 側も、歪みモデルによっては逆投影を拒否する実装になっている
  - 歪み係数が非ゼロの場合、正しい逆投影には反復解法かモデル固有の逆変換が要る。これを本 Spec で実装すると、検証されないコード経路が増える
- **Implications**:
  - **歪み係数が厳密に 0 の場合のみ対応し、非ゼロならモデル名を添えて失敗させる**（要件 3.5 / 5 系）。無視して黙って進む選択肢は、本 Spec の趣旨（静かに間違えない）に真っ向から反する
  - 逆投影は本 Spec の `deproject` モジュールが持つ。`pyrealsense2` に依存しないため、WSL 上でも記録データで完全に動く

### 検証の設計: 何をもって「検証した」と言えるか

- **Context**: `brief.md` が「検証ステップを最初に作る」と要求している。ここが本 Spec の中心
- **Findings**:
  - **確立に使った点で照合しても、必ず一致する。** 原点マーカーは定義上 (0,0,0) に、方向マーカーは定義上 y ≈ 0 に落ちる。これは検証ではなく恒等式の確認である
  - したがって検証点は**確立に使っていない独立な点**でなければならない。統計でいうホールドアウトにあたる
  - 誤差の分解には最低3種類の見方が要る:
    1. **バイアス**（全点共通のオフセット）— 原点・軸のずれ。**座標系の誤りはここに出る**
    2. **ばらつき**（バイアスを引いた残差）— Depth ノイズ、マーカー設置の再現性
    3. **距離依存**（カメラからの距離帯ごとの誤差）— Depth 誤差の増大か、スケール誤差か
  - 加えて**スケールの独立確認**が取れる: 原点マーカーと方向マーカーの間の距離をメジャーで実測し、算出値と比べる。この距離は World frame の定義に使われていない（向きだけを使っている）ため、**独立な検証量になる**
- **Implications**:
  - 検証点が確立用マーカーと重複していたら、その点を**集計から除外して重複として報告**する。全点が重複なら検証として成立しないので失敗させる（要件 4.3）
  - レポートはバイアス・ばらつき・距離帯の3層で出す（要件 4.4 / 4.5）
  - 検証は「保存済みのキャリブレーション結果」＋「検証点の観測」だけで完結させる。**フレーム取得すら必須にしない**（記録済みセッションでも走る）

### 合否判定と「未実測の数値を合否条件にしない」の両立

- **Context**: `tech.md` 開発標準1 は最重要ルールだが、要件 4 は単体で合否が出ることを求めている
- **Findings**:
  - `sensing-foundation` は同じ矛盾に「判定基準を絶対値ではなく、OFF 条件自身のばらつきに対する相対量で定義する」という形で答えている
  - 本 Spec ではその手が使えない。座標系の正しさは相対量では表せず、物理的な mm で判定するしかない
  - 別の解き方: **判定そのものは行うが、判定に使った許容値を結果とともに必ず記録し、暫定か実測由来かを明示する**。実測値は常に無条件で出す
- **Implications**:
  - `ToleranceSpec` に `provisional: bool` と `source: str` を必須で持たせ、レポートに埋め込む（要件 4.6）
  - 許容値が与えられなければ判定を `NOT_JUDGED` にし、実測値だけを出す（要件 4.7）
  - 既定の許容値（水平 30 mm）は暫定。導出根拠は「想定される狙い誤差 0.3〜0.8 m（`product.md`）に対し、座標系ずれはその一桁下に抑えたい」であり、**実測後に見直す前提**

### 再現性の測り方

- **Context**: 「設置のたびに実施する」なら、実施ごとの再現性が分からないと運用できない（要件 7.4）
- **Findings**:
  - 2つの変換の差は、単一のスカラでは表せない。原点のずれ（mm）と回転のずれ（deg）は独立に効く
  - 回転のずれもさらに分けたほうがよい: **Z 軸のずれ**（床平面推定の再現性）と**ヨーのずれ**（マーカー設置の再現性）は原因が別物である
- **Implications**: `TransformDifference` に `origin_shift_mm` / `z_axis_angle_deg` / `yaw_angle_deg` / `axis_angle_deg` を持たせる

## Architecture Pattern Evaluation

### 面内3自由度の決定方式

| Option | Description | Strengths | Risks / Limitations | 判定 |
|---|---|---|---|---|
| **床上の2物体マーカー** | 原点マーカーと方向マーカーを床に置き、Depth で観測して床平面へ投影 | Color 不要・既知寸法不要・OpenCV 不要。マーカーを同じ場所へ置けば**カメラを動かしても同じ frame が再現**する。M3 のオドメトリ原点合わせが物理的に成立する | マーカー設置の再現性が誤差になる。基線長が短いとヨー誤差が増幅 | **採用** |
| カメラ基準（光軸投影） | 原点＝カメラの床面投影、+X＝光軸の床面投影 | 完全自動。マーカー不要。単体テストが書きやすい | **カメラを動かすと World frame が動く。** 再設置のたびに原点が物理的にどこか分からず、移動体のオドメトリ原点を合わせられない | **補助として保持**（平面推定のみの疎通確認とテスト用。既定にしない） |
| チェッカーボード等の平面パターン | 校正パターンを床に置き、面内3自由度を一括で決める | 実績が多い。精度が高い | **Color stream と OpenCV が必須。** `sensing-foundation` の既定（Color 無効）を壊す。印刷物の平面度と設置が新たな誤差源 | 不採用 |
| 3点以上のマーカーで最小二乗 | 3点以上を置いて過決定にし、最小二乗で frame を決める | 冗長性があり、1点の誤りに強い。残差が出る | 運用の手間が増える。**2点で足りる自由度に対して過剰** | 不採用（ただし検証点として3点以上を置く運用は推奨する） |
| 手入力（メジャー実測値から変換を直接記述） | 設置者が数値を入力する | 実装がほぼ不要 | 人が三角関数を手計算することになり、間違いが検出できない。**本 Spec の存在意義を否定する** | 不採用 |

### モジュール構成の方針

| Option | Description | Strengths | Risks / Limitations | 判定 |
|---|---|---|---|---|
| **幾何コアと上流アダプタの分離** | 幾何演算は NumPy のみ、`sensing_foundation` に触れるのは1モジュールだけ | 幾何コアが上流なしで単体テストできる。境界違反を静的テストで検出できる。`prediction-core` の階層規律を踏襲 | 値オブジェクトを一部写経することになる | **採用** |
| 単層構成 | 全モジュールが `sensing_foundation` を自由に import | 写経が不要 | 幾何のテストに上流のモックが要る。境界が実行時にしか分からない | 不採用 |

## Design Decisions

### Decision 1: World frame の面内3自由度を、床上の2マーカーで決める（OQ-03）

- **Context**: 床平面はロール・ピッチ・高さしか拘束せず、原点（x, y）とヨーが残る。`docs/requirements.md §6.1` は「原点＝ゴミ箱の待機位置、X 軸＝投擲方向」を候補として挙げているが具体値は空欄
- **Alternatives Considered**: 上表のとおり（カメラ基準 / チェッカーボード / 3点以上 / 手入力）
- **Selected Approach**:
  - 原点 ＝ **原点マーカー**の観測点を床平面へ投影した点。運用上はゴミ箱の待機位置に置く
  - +X ＝ 原点マーカーから**方向マーカー**へ向かうベクトルの床平面成分。運用上は投擲方向に一致させる
  - +Z ＝ 床平面の法線のうちカメラ側、+Y ＝ Z × X（右手系）
  - マーカーは「床から区別できる高さを持つ物体」であればよく、色・柄・寸法を問わない
- **Rationale**:
  - **カメラ設置に依存しない**ため、再設置・三脚のずれ・設置形態の変更（OQ-06 未決）を跨いで同じ World frame を再現できる
  - Depth だけで観測できるため、`sensing-foundation` の Color 無効の既定を壊さない
  - 床平面へ投影するのでマーカー高さが結果に入らず、運用の制約が最小になる
  - 原点が**物理的に指させる床上の1点**になるため、M3 で移動体をそこへ置けばオドメトリ原点が World 原点と一致する（`docs/requirements.md §6.2` 手順3 の前提が成立する）
- **Trade-offs**:
  - マーカーを毎回置き直すため、その設置再現性がそのまま系の再現性になる。→ 要件 7.4 の比較手段で数値化して見えるようにする
  - 基線長が短いとヨー誤差が増幅する。→ 下限で拒否し、感度をレポートする
- **Follow-up**: 実機で「同じ場所に置き直したときの再現性」を実測し、`measurements.md` に記録する

### Decision 2: 検証は「確立に使っていない独立点」に対してのみ有効とする

- **Context**: `brief.md` が最重要と位置付ける手順4
- **Alternatives Considered**: 1) 確立に使ったマーカーで照合する、2) 独立点を必須にする、3) 両方を出す
- **Selected Approach**: 独立点を必須とする。確立に使った点が検証点に混ざっていたら、その点を**集計から除外して重複として明示**し、独立点が1つも無ければ検証を失敗させる
- **Rationale**: 確立に使った点は定義上一致するため、照合しても情報がゼロである。**「検証したのに間違っていた」という最悪の結末を構造的に防ぐ**
- **Trade-offs**: 運用の手間が増える（メジャーで実測した検証点を用意する必要がある）。ただしこれは手順の本質であって省略できない
- **Follow-up**: 手順書に「検証点は最低3点、うち1点は遠方（想定投擲距離の端）」を推奨として書く

### Decision 3: 誤差はバイアス・ばらつき・距離依存の3層に分解して報告する

- **Context**: `docs/requirements.md §6.2` の「系統誤差か予測誤差かを即座に分離できる」を実現する
- **Selected Approach**: `VerificationReport` に `bias_mm`（軸ごとの平均オフセット）、`scatter_rms_mm`（バイアス除去後）、`range_buckets`（距離帯ごとの平均・最大）を持たせる
- **Rationale**: 合計値だけでは「30 mm ずれている」が座標系のせいかノイズのせいか分からない。3層に割れば、バイアスが支配的なら座標系、ばらつきが支配的なら観測、遠方だけ大きいなら Depth 距離特性、と読み分けられる
- **Trade-offs**: レポートの項目が増える。→ 人間可読の要約と機械可読の全量を分けて出す（要件 4.8）

### Decision 4: 縮退条件は警告ではなく失敗にする

- **Context**: `brief.md` と要件 5
- **Selected Approach**: 平面の内点不足・入射角過小・マーカー未検出・基線長不足・非対応の歪みモデル・保存結果と現設定の不一致を、いずれも識別可能な理由付きの失敗として扱い、変換を返さない
- **Rationale**: 座標系のずれは症状が「予測が悪い」にしか見えない。**部分的に正しい結果を返すことが、このプロジェクトで最も高くつく失敗**である
- **Trade-offs**: 現場で「動かない」ことが増える。→ 失敗理由を分岐可能な列挙値にし、何を直せばよいかをレポートに出す

### Decision 5: 幾何コアを NumPy のみに閉じ、`sensing_foundation` への接点を1モジュールに集約する

- **Context**: `flying-object-tracking` と並行実装するため、境界が実行時にしか分からない構造は避けたい
- **Selected Approach**: `upstream.py` だけが `sensing_foundation` を import する。幾何・変換・検証・永続化は NumPy と標準ライブラリのみに依存する。この規則を静的テストで回帰検証する
- **Rationale**: `prediction_core` が `test_boundaries.py` で依存方向を静的に守っている先例に揃う。幾何コアが上流なしでテストできるため、実機どころか `sensing_foundation` の実装完了すら待たずに着手できる
- **Trade-offs**: `CameraIntrinsics` / `StreamProfile` に対応する値オブジェクトを本 Spec 側にも持つことになる。→ 変換は `upstream.py` の1箇所に閉じ、**フィールド名を上流と一致させて**写経ミスを起こしにくくする

### Decision 6: `prediction_core` に依存しない

- **Context**: 下流の `m1-prediction-validation` は World 座標のサンプル列を `prediction_core.Sample` にして渡す
- **Alternatives Considered**: 1) 本 Spec が `Sample` を組み立てる便利関数を持つ、2) 持たない
- **Selected Approach**: 持たない。本 Spec は「カメラ座標 → World 座標」までを返し、`Sample` への組み立ては `m1-prediction-validation` が行う
- **Rationale**: 依存を増やすと、`prediction_core` の `SCHEMA_VERSION` 変更が本 Spec の再検証トリガに入ってしまう。**時刻の扱い（`t_ms` の基準）は追跡側の関心事**であり、座標変換の責務ではない
- **Trade-offs**: 下流に数行の組み立てコードが残る。境界の明確さのほうが価値が高い

### Decision 7: 出力形式は JSON（機械可読）＋ テキスト要約（人間可読）の2本立て

- **Context**: 要件 4.8 / 6.1 / 6.2
- **Selected Approach**: キャリブレーション結果と検証レポートを JSON で保存し、同じ内容の要約を標準出力に整形して出す。JSON は `allow_nan=False` とし、欠測は**キーごと省く**
- **Rationale**: `sensing-foundation` が NDJSON / JSON で統一しており、`prediction_core` も `allow_nan=False` を採る。ここだけ別形式にする理由がない。欠測を 0 で埋めない方針も上流と揃う
- **Trade-offs**: なし（形式版を持たせて将来の変更に備える）

## Risks & Mitigations

- **マーカー設置の再現性が系の再現性を支配する** — 手順書で設置方法（床に印を残す等）を定め、要件 7.4 の比較手段で毎回数値を残す
- **基線長が短い設置で静かに精度が落ちる** — 下限で失敗させ、ヨー感度を結果に埋め込む
- **`sensing-foundation` が未実装の間、本 Spec の上流アダプタが検証できない** — 幾何コアを上流非依存にし、アダプタは薄い写経に留める。アダプタのテストは上流の公開型を模した最小のダブルで行い、実装完了後に結合テストで確かめる
- **`pyproject.toml` を `flying-object-tracking` と同時に編集して衝突する** — 追記位置を `[tool.hatch.build.targets.wheel].packages` と `[project.optional-dependencies]` の2箇所に限定し、既存記述を書き換えない。**`[project].dependencies` は空のまま触らない**
- **暫定の許容値が既成事実になる** — `ToleranceSpec.provisional` をレポートに必ず出し、`--help` と docstring にも明記する
- **記録セッションの Depth を平均化する際に元配列を壊す** — 平均化は新しい `float64` 配列へ確保する。境界テストで in-place 変更が無いことを確かめる
- **入射角が浅い設置（壁の高い位置から床を舐めるように見る）で平面推定が劣化する** — 入射角を推定品質に含め、下限を下回れば失敗させる
