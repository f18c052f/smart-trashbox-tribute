# Brief: world-frame-calibration

## Problem

**このプロジェクトで最も時間を奪われる可能性が高い箇所。**

`requirements.md §6.2` が明示している問題:

> 予測が完璧でも座標系が数 cm ずれていれば必ず外す。
> しかも症状は「予測が悪い」ようにしか見えないため、**原因の切り分けに最も時間を奪われる箇所**になる。

D435 は IMU を持たない。これは「カメラ固定運用だから不要」と判断した結果であり、
**その代償として、床平面と姿勢を Depth から自力で推定する必要がある**（`bom.md §A` の選定根拠）。

## Current State

- World frame の**原点・軸方向ともに未定**（OQ-03）
- 「床平面は Depth の平面フィッティングで推定する」という方針だけが確定
- Z 軸は床面から鉛直上向きが正、単位は mm / ms、これも確定
- キャリブレーション手順は**未定義**。コードも存在しない

## Desired Outcome

- **設置のたびに実施する手順**が定義され、実行できる
  1. 床平面推定（＝カメラ姿勢の取得）
  2. World frame の原点・軸の決定
  3. （移動体登場後）オドメトリ原点の World frame への初期化
  4. **検証**: 既知の位置に物体を置き、検出側が算出する座標と一致するか確認
- 手順4 により、**系統誤差か予測誤差かを即座に分離できる**

## Approach

**検証ステップ（手順4）を最初に作る。**

キャリブレーションの実装より先に「合っているかを確かめる手段」を用意する。
そうしないと、キャリブレーション自体が正しいかを判定できないまま下流を作ることになる。

床平面は Depth の平面フィッティング（RANSAC 等）で推定し、
そこから World frame の原点・軸を決める。原点の候補は「ゴミ箱の待機位置」、
X 軸の候補は「投擲方向」だが、**具体値はこの Spec で決める**（→ OQ-03）。

## Scope

- **In**:
  - Depth からの床平面推定（カメラ姿勢の取得）
  - World frame の原点・軸方向の**決定**（→ OQ-03）
  - カメラ座標系 → World frame の変換（FR-3）
  - **検証手順**: 既知位置との照合と誤差レポート
  - 設置のたびに実行する手順の文書化
  - キャリブレーション結果の保存・読み込み
- **Out**:
  - 物体検出（→ `flying-object-tracking`）
  - 予測（→ `prediction-core`）
  - **移動体オドメトリ原点の初期化の実装**。手順としては定義するが、
    移動体が存在しないため**実装は M3 側**

## Boundary Candidates

- **床平面推定**（Depth → 平面パラメータ）
- **World frame 定義**（平面 + 基準点 → 座標系）
- **座標変換**（カメラ座標 → World 座標）
- **検証**（既知位置との照合と誤差の定量化）

## Out of Boundary

- 移動体のオドメトリ（FR-6）そのもの
- カメラを移動させる運用。**カメラは固定運用**であり、
  エゴモーション補正は対象外（D435 に IMU が無い前提と整合）
- 設置形態（壁固定 / 三脚）の決定（→ OQ-06）

## Upstream / Downstream

- **Upstream**: `sensing-foundation`（Depth フレームの取得と記録）
- **Downstream**:
  - `flying-object-tracking`（検出結果を World 座標へ変換する）
  - `m1-prediction-validation`（予測誤差と系統誤差の分離に検証結果を使う）
  - **M3**（結合前の必須前提。`requirements.md M3` の優先度3）

## Existing Spec Touchpoints

- **Extends**: なし
- **Adjacent**: `flying-object-tracking` と**並行実装できる**。
  向こうはカメラ座標系までを持ち、World への変換は本 Spec が持つ。
  **この境界を曖昧にすると、どちらが誤差の原因か分からなくなる**

## Constraints

- **⚠️ この手順が未定義のまま M3（結合）に進まない**（`requirements.md §6.2`）
- **手順4（検証）を先に用意する。** 後回しにすると切り分け手段を失う
- 単位は mm / ms
- 再設置のたびに実施する前提。**一度きりの作業として設計しない**
- Pi 4 の資源制約: **毎フレーム巨大な Point Cloud を作らない**。
  平面推定はキャリブレーション時のみの処理であり、常時実行しない
