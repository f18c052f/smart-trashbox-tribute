# Technology Stack

## Architecture

**固定側（知能）と移動体側（身体）を分離し、目標座標データだけで繋ぐ2ノード構成。**

```
RealSense D435 → Raspberry Pi 4 Model B → (小さいデータ) → ESP32 → 3輪オムニ移動体
        └──────── 固定側：検出・予測 ────────┘   └──── 移動体側：駆動制御 ────┘
```

**不変の原則**:
- Raspberry Pi は**固定側**に置く。ゴミ箱本体へ搭載しない
- ESP32 へ送るのは予測結果（目標座標・到達時刻）**のみ**。画像・Depth フレームは送らない
- 送信データは `{ x_mm, y_mm, t_impact_ms }` が現在の最小形（距離 mm / 時刻 ms）

## Core Technologies

| 層 | 技術 | 備考 |
|---|---|---|
| 検出 | Intel **RealSense D435** | グローバルシャッター。IMU 無し（カメラ固定運用のため不要） |
| 固定側計算機 | **Raspberry Pi 4 Model B** | 手持ち。継続可否は実測で判断（性能達成を断定しない） |
| 固定側ソフト | **Python** + OpenCV / pyrealsense2 | |
| 移動体 MCU | **ESP32 DevKit** | PCNT ×3（エンコーダ）＋ LEDC（PWM/方向） |
| 移動体ソフト | **C++**（Arduino / ESP-IDF 系） | |
| 可視化 | **TypeScript** + Canvas / WebGL | **表示のみ。アルゴリズムを持たない** |
| 主開発環境 | Windows + **WSL2** | Claude Code もここで使用 |

**駆動系**: 3輪オムニ・120°配置（確定）。JGB37-520 ×3 / AE-TB67H450 ×3 / 3S LiPo。
**型番・数量の正は `docs/bom.md`。**

## Development Standards

### 1. 未実測の数値を合否条件にしない ★最重要

このプロジェクトの数値は**ほぼすべて暫定目標値**である。

- 数値には**必ず導出根拠を併記する**。根拠が崩れれば数値も見直す
- **根拠のない固定値をコードに埋め込まない**（例: `ENCODER_COUNTS_PER_WHEEL_REV` は M2a-0 で実測校正する）
- 合否は NFR-7 のみで判定する。部分指標の未達を理由に方針を変えない

> 過去に「最高速度 ≥ 1.5 m/s」「≥ 60 fps 相当」「加速度 2〜3 m/s²」を要件として置き、
> いずれも根拠不足で撤回した経緯がある（`docs/decisions.md` D-1 / D-2）。**同じ失敗を繰り返さない。**

### 2. 安全系は「その段階に入る前」に実装する ★事故に直結

| 実装順 | 保護 | 期限 |
|---|---|---|
| ① | モータロック保護（エンコーダ速度≈0 かつ PWM 高） | **M2a より前** |
| ② | LiPo 低電圧保護（移動平均・時間判定・ヒステリシス） | **M2a より前** |
| ③ | PWM 上限（バッテリ電圧を考慮） | **M2a より前** |
| ④ | **指令ウォッチドッグ**（一定時間指令が更新されなければ停止） | **M2a より前** |
| ⑤ | 動作領域制限／ジオフェンス | **M3 より前** |

- **FR-10（通信途絶フェイルセーフ）は ④ の入力元差し替えとして実現する。**新規実装ではない。
  そのため ④ は「コントローラ固有の処理」ではなく
  **「最後に有効な指令を受けてからの経過時間」だけを見る形**で実装する
- **無線に依存する停止手段（テレオペのデッドマン、ブラウザからの停止）は安全装置ではない。**
  Wi-Fi/BT が落ちる状況＝まさに暴走しうる状況。**物理スイッチと混同しない**
- ハードウェアヒューズ（10A）は短絡・配線事故用。**1モータのストール（約2.3A）では溶断しない**

### 3. 本番アルゴリズムを2言語で二重実装しない

シミュレータの予測ロジックを TypeScript で書き直すと、
**検証しているのは TS 実装であって実際に載る Python 実装ではない。**
両者は必ずズレていき、しかも**ズレに気付けない。**

| 層 | 言語 |
|---|---|
| 物理モデル・予測アルゴリズム・パラメータ掃引 | **Python のみ**（本番と同一コード） |
| 可視化・インタラクティブ操作 | TypeScript（Python が出力した JSON を**表示するだけ**） |

同様に、移動体側では**テレオペ用と本番用でファームウェアを分けつつ、下位層は共有する**。
分離するのは最上位の指令生成（パッド入力 → (vx,vy,ω)）だけで、
逆運動学・速度PID・PWM 出力・保護①〜④は共通にする。

> ESP32 の BT Classic と Wi-Fi は 2.4GHz を time-share するため、
> **BT スタックを本番ファームへ持ち込まない**（ビルドフラグで排他）。

### 4. 部品を替える前に、設定とソフトウェアで詰める

性能不足でも**すぐに高価な部品へ交換しない。** 調査順序が定義されている。

- 駆動系: スリップ → 電圧降下 → PWM/PID → 軽量化 → 重心 → 剛性 → **レイアウト見直し** → 容量 → 最後にモータ
- 固定側: Color 削減 → 解像度 → ROI → fps → 画像処理削減 → PointCloud 回避 → アルゴリズム簡略化 → 最適化 → 最後に HW 変更

### 5. 計測が計測対象を歪めないこと

- ログ送出は **fire-and-forget**（完了を待たない）。集計・可視化は Pi 上で行わない
- 計測は**実行時に無効化できる**こと
- **ON/OFF で end-to-end latency が有意に変化しないことを実測で確認する**
- ESP32 は走行中 RAM にバッファし、**走行後に吸い出す**（走行中の Wi-Fi 送信は制御ループにジッタを乗せる）

### 6. Record / Replay を前提に設計する

RealSense 実機を毎回使わずにアルゴリズムを改善できる構成を目指す。
入力層を **live / recorded / simulated** の3種で差し替え可能にし、下流（検出・追跡・予測）は共通にする。

### Testing

- WSL 上で**単体テストと Replay テスト**を実施し、Git 経由で Pi へ持ち込む
- 投擲は**ばらつきが大きく再現性が低い**。実機で毎回投げ直して比較する方式は成立しない
- **人間の入力で定量評価しない**（テレオペで NFR-1 を判定しない）。定量計測は必ずスクリプト化する

## Development Environment

| 環境 | 位置付け | RealSense 接続 |
|---|---|---|
| Windows + WSL2 | **メイン開発環境** | **標準フローでは接続しない** |
| Raspberry Pi 4 Model B | **実機ターゲット** | **接続する** |

WSL の USB passthrough で RealSense を繋ぐことは可能かもしれないが、
**RealSense / USB / WSL 仮想化の問題が混在するとデバッグが困難**なため標準フローにしない。

```
WSL で開発 → Git push → Pi で pull → 実機テスト・実データ記録 → WSL へ持ち帰り解析
```

Pi 上で直接コードを編集して差分が迷子になる運用は避ける。

> **コミットメッセージは日本語で記述する。**

## Key Technical Decisions

| 決定 | 理由 |
|---|---|
| 3輪オムニを部品から自作 | 円形ゴミ箱は向き維持が不要でメカナムの利点が無効。既製ベースは 0.6 m/s 級で結局モータ換装が要る |
| D435（D435i ではない） | IMU はカメラ移動案でのみ有用。固定運用なので不要。床平面は Depth のフィッティングで推定 |
| AE-TB67H450（BTS7960 ではない） | 試作1号機に 43A は過剰。ただし余裕が小さいため**ソフトウェアロック保護が必須**という条件付き |
| ROS 2 を導入しない | Pi 4 の資源制約に対して重い。柱3 見送り・柱2b 保留で肩代わりできる部分がほぼ残らない |
| Hono を使わない | Python が JSON を出力しブラウザが描画するだけなら常駐サーバが不要。**使いたい技術に用途を作らない** |
| AI モデルを最初から必須にしない | Depth 差分・背景差分・ROI 等の軽量方式を先に実測する |

> ⚠️ **ESP-NOW を Raspberry Pi から直接使える前提にしない。** ESP32 間の方式であり Pi からの利用は未検証。
> そのため「固定側に ESP32 を1台置いて Bridge にする」案を候補として残している。
