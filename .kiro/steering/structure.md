# Project Structure

## Organization Philosophy

**現時点でコードは存在せず、リポジトリの実体は `docs/` の設計ドキュメントである。**
したがって当面の構造上のルールは、コード配置ではなく**ドキュメントの単一情報源（Single Source of Truth）**にある。

原則: **各ドキュメントは「現在どうなっているか」だけを書く。**
「昔どうだったか」と「まだ決まっていないこと」は専用ファイルへ外出しする。

## Documentation Patterns

### 仕様書（現在の状態）

| ファイル | 責務 | 正となる範囲 |
|---|---|---|
| `docs/requirements.md` | 共通要件（FR / NFR / マイルストーン / インターフェース） | **要件とマイルストーンの正** |
| `docs/drivetrain-spec.md` | 駆動系（モータ・ドライバ・電源・保護・テレオペ実装方針） | **駆動系の設計の正** |
| `docs/bom.md` | 部品表 | **型番・数量の正** |
| `docs/development-environment.md` | 開発環境・実行環境・責務分担 | **環境の正** |
| `docs/original-features.md` | 独自機能（柱1〜柱4）の方針 | **独自機能スコープの正** |

### 横断ファイル（状態ではなく履歴・課題）

| ファイル | 責務 |
|---|---|
| `docs/open-questions.md` | **未決事項の唯一の正**。OQ-01〜OQ-40 |
| `docs/decisions.md` | **決定と不採用案の記録**。方針転換（D-1〜）＋旧案アーカイブ |

## Documentation Rules ★これを守らないと元の混乱に戻る

### 1. 未決事項は `open-questions.md` にしか書かない

- 各仕様書には **項目名と `OQ-nn` の索引表**だけを置く。**決め方・確定条件を複製しない**
- **ID は永続。** 決着しても番号を再利用せず欠番にする
- 新規は**末尾に採番**する。途中に挿入して繰り下げない
- 決着したら open-questions.md の行を削除し、**決定内容と理由を `decisions.md` へ移す**。
  同時に本文側の `→ OQ-nn` も外す
- 「決め方」が書けない項目は**まだ課題として成立していない**。何を測れば決まるのかを先に書く

> かつて未確定リストが5ファイル・7箇所に分散し、主要項目が3〜4箇所に重複していた。
> 決定が1つ下りるたびに複数ファイルの編集が必要で、
> **直し忘れが「決まっているのに未確定と書いてある箇所」を生んだ**（`docs/decisions.md` D-7）。

### 2. 版差分ブロックを本文に置かない

変更履歴は git と `decisions.md` が持つ。
**仕様書の冒頭に「vX からの変更」を積み上げない**（本文を読む前に履歴を読まされる状態になる）。

ただし「なぜその数値なのか」「なぜその案を採らなかったか」は**履歴ではなく根拠**なので本文に残す。

### 3. 数値の導出根拠と ⚠️ 注記を削らない

**「数値だけが残って根拠が消える」状態が最悪。** 数ヶ月後に再検討され、間違った結論に至る。
⚠️ 注記は「過去に踏みかけた罠」の記録として扱う。

### 4. 同じ事実を2箇所に書かない

食い違ったときにどちらが正か分からなくなる。重複しそうな場合は**正を宣言してリンクする**。

- 部品の型番・数量 → `bom.md` が正（他は参照のみ）
- 要件・マイルストーン → `requirements.md` が正
- 駆動系の設計判断 → `drivetrain-spec.md` が正

## Naming Conventions

| 対象 | 規則 | 例 |
|---|---|---|
| ドキュメント | kebab-case `.md` | `open-questions.md` |
| 要件 ID | `FR-n`（機能） / `NFR-n`（性能） / `CON-n`（制約） | `FR-13`, `NFR-1` |
| 未決事項 ID | `OQ-nn`（ゼロ埋め2桁、永続） | `OQ-01` |
| 決定 ID | `D-n` | `D-4` |
| マイルストーン | `M1`〜`M4`。分割時は英小文字を付す | `M2a`, `M2b`, `M2a-0` |
| 単位 | 距離 **mm** / 時刻 **ms**（インターフェース） | `x_mm`, `t_impact_ms` |

**マイルストーン名は必ず段階まで書く。** 「M2 で実測」は M2a か M2b かで意味が変わる。

## Cross-Reference Conventions

- ドキュメント間は**相対リンク＋アンカー**で結ぶ（`./bom.md#e-機構3dプリンタ活用`）
- 見出しに `（）` `、` `:` を多用すると**アンカーが壊れやすい**。ID を含む見出しは簡潔にする
- 改行コードは **CRLF** で統一されている。一括編集時に混在させない

## Future Code Layout（案・未確定 → OQ-40）

実装着手時に改めて決める。現時点で**ディレクトリを作らない**。

```
docs/          設計ドキュメント
.kiro/         steering（プロジェクト知識） / specs（個別機能の仕様）
（以下は将来案・未作成）
  入力層        RealSense live / recorded / simulated data の読み出し
  処理層        detection / tracking / 3D position / prediction
  通信層        ESP32 への送信
  移動体側      ESP32 ファームウェア（テレオペ用と本番用は排他ビルド）
  観測基盤      Throw Record の記録・可視化・評価
```

### Code Organization Principles（実装時に効かせる）

- **入力層を live / recorded / simulated で差し替え可能にし、下流を共通にする**（Record/Replay の前提）
- **1投擲 = 1レコード（Throw Record）**の粒度を崩さない。スキーマは柱1 が必要とする最小形から始める
- **可視化レイヤを Raspberry Pi 上で動かさない**（開発PC 上で動かす）
- **TypeScript 側に本番と重複するアルゴリズムを置かない**（→ `tech.md` 標準3）
