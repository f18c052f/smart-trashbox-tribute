### 駆動系トラックの起点（2026-08-23 追加）

固定側がハード待ちに入ったため、**移動体側を本ファイルの Scope へ追加した**（従来は Out）。

着手方針:

- **1本目はハード非依存の駆動コア**とする。`drivetrain-spec.md §10.1.2` の層構造がそのまま境界になる。
  上段（パッド入力 → `(vx, vy, ω)`）は使い捨てだが、下段（逆運動学・速度PID・PWM出力・保護①〜④）は
  M2b・M3 と完全に共有される
- 根拠: `drivetrain-spec.md §10` が **「M2a（初通電走行）より前に ①モータロック保護 ②LiPo低電圧保護
  ③PWM上限 ④指令ウォッチドッグ を実装する」**と明記している。
  **実機に通電する前に書き終えていなければならないコードが、既に仕様として確定している**
- `prediction-core` と同じ作り方ができる。逆運動学も保護の状態機械も純関数・状態機械に落ちるため、
  ペリフェラル（PCNT / LEDC / BT）を薄いアダプタへ隔離すればホスト側で単体テストできる
- **見張るべき seam**: `trajectory_sim.drivetrain` が既に「等方な質点＋加速度上限」の運動モデルを持つ。
  M2b の実測値を `DrivetrainParams` へ戻す口を最初に決めておかないと、
  シミュレータのキャッチ可能領域を実機由来の数字で更新できなくなる。**後付けでは繋がらない**
- ~~**部品制約**: ホイール・ハブが未着~~ → **2026-08-30 に解消。駆動系の部品はすべて手元にある。**
  `drivetrain-spec.md §11` の現物採寸 #1（付属ブラケット実寸）・#2（取付穴ピッチ）・#3（最低地上高）と
  OQ-07（フレーム外形＝ホイール間隔）・整備スタンドの支持形状が**すべて着手可能**になった

#### ファームウェア構成の決定（2026-08-23 の技術検証で確定）

⚠️ **これらは調査で判明した罠に基づく決定である。根拠ごと残す。**

| 項目 | 決定 | 理由 |
|---|---|---|
| フレームワーク | **`framework = espidf` + Arduino-as-component を両ビルドで使う** | Bluepad32 は `framework = arduino` の `lib_deps` として導入できず、改造コアとして組み込まれる。片方だけ espidf にすると `main/` と `src/` でレイアウトが割れる |
| PlatformIO プラットフォーム | **`pioarduino` フォークをリリース zip で pin** | 公式 `platformio/platform-espressif32` は 7.0.1（2024年5月）で凍結され Arduino 3.x 非対応。⚠️ pioarduino は実質1人規模のため `stable` / `#develop` を使わない |
| 出発点 | `esp-idf-arduino-bluepad32-template` | 公式ルート。IDF 5.4.x 系 |
| パーティション | テレオペビルドは `huge_app`（3MB / OTA 無し） | Arduino core + BTstack BR/EDR HID host で約 1.0〜1.4MB。既定の 4MB スキーム（1.31MB × 2）では溢れる |
| MCU | **classic ESP32 に固定。S3 / C3 / C6 / H2 は不可** | DualSense は BR/EDR のみで BLE 非対応。PCNT ユニット数も classic 8 / S3 2 / C3 0。**将来 S3 へ乗り換える選択肢は無い**（`bom.md` #8 は型番未指定 → 明記が要る） |
| エンコーダ | **`driver/pulse_cnt.h`（IDF 5.x 新 API）で自前アダプタを書く** | `ESP32Encoder` は非推奨 legacy API 上。方向反転時のパルス落ちも報告あり。自前化はアダプタ隔離方針とも一致 |
| ホストテスト | **時刻源を注入する。固定幅整数型（`int32_t`/`int64_t`）を初日から使う** | ホストに `millis()`/`micros()` は無い。ホストは 64-bit で `long` が 8 バイト、ESP32 は 4 バイト。⚠️ **カウンタと PID 積分項のオーバーフロー挙動がホストテストで再現されない** |
| テスト配置 | 純ロジックは `lib/control/`。`test/` は `test_native/` と `test_embedded/` に分け `test_filter` で振り分ける | `test_build_src` は既定 `no` でテストから `src_dir` が見えない。`test/` は全環境向けにビルドされる |

**ライセンス**: Bluepad32 本体は Apache-2.0 だが、依存する **BTstack はオープンソースではない**
（「個人的利益のためのみ。商用目的・金銭的利得のためには使用不可」条項付き。商用は BlueKitchen 社の有償ライセンス）。
趣味プロジェクトとしての使用は問題ないが、**GitHub 公開時にトップレベル LICENSE が
BT 版ファームまで自由に再利用可能だと誤読させてはいけない。**
本番ファームは BT を落とすため、**encumbrance をテレオペビルドに封じ込めれば本番成果物はクリーンに保てる。**
これは「テレオペFWと本番FWを排他にする」既存の決定に、2.4GHz 共存とは**別の根拠を追加する**。

**実装時に踏みやすい罠**（Spec 設計時に必ず拾う）:

- ⚠️ **PCNT のハードウェアカウンタは符号付き 16bit（±32767）。**
  watch point ＋ 64bit ソフトウェアアキュムレータで桁上げを累積しないと、
  **「数秒走るとオドメトリが壊れる」形で現れる**
- ⚠️ **ADC1 を使う**（ADC2 は Wi-Fi 動作中に使用不可 = 本番ビルドで効く）。
  ESP32 の生 ADC は両端で非線形なので**カーブフィッティング補正を入れる** — LiPo カットオフ精度に直結
- DualSense のマルチペアモードで無言のペアリング失敗が既知。レガシー手順（Create/Share + PS 長押し）を使う。
  リンクキーの残留が再接続失敗の頻出原因なので、**「Bluetooth キー消去」操作をファームに用意する**
- DevKit の電波は弱く数 m 程度。**リンク断での停止を前提に置く**（④ が必要な理由がもう一つ増える）
- GPIO 34〜39 は入力専用で内部プルアップが無い

> ✅ 調査が指摘した「Windows に MSYS2 + MinGW が必要」は**本プロジェクトには該当しない**。
> 開発は WSL2 側で行うため gcc は標準で使える。

### 機構トラックの起点（2026-08-30 追加）

`drivetrain-core` の実装が完了し、駆動系の部品もすべて揃った。
**次に不足しているのはソフトではなく機体そのものである。**
`teleop-bringup/brief.md` は既に「ゴミ箱本体・固定アダプタの設計（**機構トラック側**）」を
Out of Boundary として委譲しており、**宛先の無い参照が存在する状態だった。**
それを引き受けるのが本トラックである。

着手方針:

- **2 Spec に分ける。** 判断基準は下記 Boundary Strategy に従い、**③下流の消費者が違う**ことと
  **④1 Spec が 20 タスクに収まらない**こと。
  ⚠️ 部品が揃った時点で「①ブロック要因（ハード待ちの有無）」では切れなくなったため、
  当初検討していた「ハード不要／採寸待ち」の切り方は**採用していない**
- `catch-mechanism` の下流は `trajectory_sim`（`position_tolerance_mm`）、
  `chassis-mechanism` の下流は `teleop-bringup`（整備スタンドと機体）。**消費者が別物である**

#### 技術検証で確定した前提（2026-08-30）

⚠️ **これらは調査で判明した罠に基づく決定である。根拠ごと残す。**

| 項目 | 決定 | 理由 |
|---|---|---|
| 造形機 | **Bambu Lab A1 mini**（180×180×180mm） | 保有機。⚠️ **φ180 超の部品は分割必須**。円は正方形の対角線（254mm）を使えないため斜め配置でも入らない |
| 材料 | **PETG が実質の上限。** ASA / ABS / PC / PA / CF・GF は不可 | エンクロージャ無し・ベッド上限 80℃。公式スペックが not recommended と明記。⚠️ **荷重部材で最も欲しい ASA が選べず、後から材料でリカバリできない** |
| 継手 | **貫通ボルト＋金属ヒートインサート＋広い当たり面。ダボは位置決め専用** | FDM は層間強度が弱く、**樹脂だけで荷重を渡す継手（ダボ・蟻継ぎ）は層間剥離モードで落ちる**。接合面の法線が層方向と一致する配置は禁忌 |
| 形状の正 | **build123d（Python / OCCT カーネル）** | `.py` そのものがモデル。git 差分・CI・現物採寸値の後入れが同時に素直に解決する |
| **`.FCStd` の扱い** | **git 管理しない（`.gitignore`）。再生成可能なスクラッチとして扱う** | ⚠️ **「最終微調整は結局 FreeCAD になる」を構造で潰すため。** 正になり得ない場所に置けば、正になりようがない。成果物の正は `.py` と生成した STEP / STL / 3MF のみ |
| 二重管理の検出 | **CI で `.py` から再生成した STEP の体積・バウンディングボックスをコミット済みの値と照合する** | FreeCAD で手を入れた形状は `.py` から再生成できないため、**検査が落ちることで二重管理が可視化される** |
| FreeCAD の役割 | **組立確認・干渉チェック・図面のみ。形状の正を持たない** | 下記 TNP。⚠️ **Python API で書いても TNP は回避されない**（面を `Face6` 等の生成名で参照するカーネル側の問題であり、GUI 操作の問題ではない） |
| 分割形状 | 中心ハブ＋放射状3アーム | `drivetrain-spec.md §6.2` の「中央プレート＋3つのモータ取付部のモジュラー構造」と一致する |
| PLA の扱い | **常時荷重のかかる構造部材に使わない** | PLA は Tg 以下でもクリープする。2kg 級機体を支えると時間経過で垂れる。PETG も耐クリープ性は高くない |

**FreeCAD を形状の正にしない根拠**（いずれも未修正 issue）:

- [#26084](https://github.com/FreeCAD/FreeCAD/issues/26084) **Spreadsheet のセル値を変えるだけで
  SubShapeBinder の参照面が別の面へ飛ぶ。1.1.0rc1 で再現・open。**
  Spreadsheet 集中管理は FreeCAD でパラメータ運用する際の定石であり、**その定石そのものがバグ経路**
- [#17041](https://github.com/FreeCAD/FreeCAD/issues/17041) recompute 後に face/edge ID が変わる。
  Confirmed・open（ラベルは "Toponaming fixed in **V2**"）
- [#31040](https://github.com/FreeCAD/FreeCAD/issues/31040) その **V2 アルゴリズム本体が
  2026-06 起票で未完了**。FreeCAD 1.0 の TNP 緩和は公式ブログ自身が
  「適用は Sketcher と PartDesign のみで完全解決ではない」と明記している
- `.FCStd` はバイナリ zip で、形状の実体は `*.brp`（BREP）。**寸法を 1mm 変えると BREP の
  エントリ番号が総入れ替えになり、git 差分は非圧縮保存でも意味を成さない。**
  テキスト化要求（#5585 / #9432）は未実装。`textconv` 回避策はマシンごとの再設定が必要で
  リポジトリに同梱できない

#### ゴミ箱の選定基準（購入前に確定させる）

**「百均で適当に買う」を許さない。開口径はプロジェクトの合否条件の入力だからである。**

> **2026-08-30 の実売調査で確定した基準。** 当初の推奨（φ220〜260 を狙う／強いテーパー不可）は
> **実売品の実態と合っていなかったため訂正済み。** 経緯は下表の「実態」欄に残す。

**買い物の判断ルールは1行**: **「丸型・5L 以上・フタなし」を選ぶ。**
3L 以下は φ180 未満で不可。5L → 6.9L → 8L は**径がほぼ頭打ちで高さだけ伸びる**ため、
**5L〜6.9L がスイートスポット**である。

| 項目 | 基準 | 実態・根拠 |
|---|---|---|
| 形状 | **円形（ほぼ必須）** | 角形だと有効開口が方向依存になる。3輪オムニは全方向等方なのに受け口だけ異方だと、スカラーの `position_tolerance_mm` と型が合わない |
| 開口内径 | **φ215〜225**（実質これが上限）／**最低 φ200**／**φ180 未満は不可** | ⚠️ **当初「φ220〜260 を狙う」としたが、100均の丸型は φ215〜225 で頭打ちであり φ240 以上は存在しない。** `許容誤差 = D/2 − 32.5mm` → **φ220 で ±77.5mm**（`params.py` の暫定値 67.5mm より約15%広い側へ着地する） |
| 価格帯 | **110円で足りる。220円以上へ上げない** | 5〜7L 帯は4チェーンとも110円で φ215〜225 を満たす。⚠️ **220円以上の帯は蓋・スイング・折りたたみ等の不要な機構が付く傾向で、要求には不利** |
| 重量 | **300g 以下** | 実測 228g（山田化学 No.335）。同クラス推定 180〜250g で**余裕がある**。⚠️ 300g 超になりやすいのは**蓋付き・スイング機構付き・厚肉の小型品**。⚠️ **軽さを求める理由は転倒ではなく加速性能である**（下記「性能の律速要因」） |
| 高さ | 200〜300mm | 実売は H220〜250mm でこの範囲に収まる。空き缶（約120mm）が寝て収まる深さは要る |
| 底 | **脚付き・丸底でないこと。テーパーは緩いものを選ぶ** | ⚠️ **当初「強いテーパー不可」としたが、100均の丸型はほぼ全品がネスティング（入れ子）前提でテーパーを持ち、完全な円筒はまず無い。** 「不可」は要件として成立しないため**「緩いものを選ぶ」へ緩和**。目安: 上φ220→底φ158 程度（片側 約7°）は可、上φ225→底φ145（約10°）は強すぎる |
| 縁 | 外向きリムがあるものが望ましい | 3Dプリントのワイドリム／固定アダプタを引っ掛けられる。無い場合は挟み込み式になり設計が増える |
| 付属品 | **フタなしを選ぶ**（外せるなら可） | 蓋・スイングトップ・内枠はいずれも有効開口を狭める |

**第一候補**（重量が実測で判明している唯一の品）:
**キャンドゥ「ダストボックス丸」＝ 山田化学 No.335**（JAN 4965534335027）。
**φ220 × H244mm・6.9L・PP再生樹脂・228g・フタなし・110円。**
⚠️ **同一品がアスクル等で単品約160円で入手できる**ため、**壊しても同スペックで再調達できる**
（試作では効く。100均は在庫が入れ替わると同じ物が二度と買えない）。
次点: セリア「ブルックリン調ダストボックス」（φ215 × H220mm・5L）。
⚠️ **ワッツ「Re.B」は上φ225→底φ145 の強テーパーのため非推奨。**

**購入時に測って記録する値**（そのままパラメータになる）:
**開口内径**（外径ではなく内径。縁の巻き込み分を引く）／上端外径／**底の外径と平面部径**／
高さ／**実測重量**／底の肉厚／**テーパー角**。

> ⚠️ **テーパーは設計へ2方向に効く**（`catch-mechanism` / `chassis-mechanism` の両方で拾う）:
> **(1) 固定アダプタは「円錐台を受ける座」になる。円筒前提で設計すると合わない。**
> **(2) FR-12 に対しては不利側** — 傾いた壁は跳ね返った缶を**開口へ向けて上外へ弾く**。
> 垂直壁のほうが保持性は高い。⚠️ 一方で**テーパーは漏斗として FR-7 には有利**であり、
> **同じ形状が FR-7 と FR-12 で逆向きに効く。** ここは机上で釣り合いを取る対象である。

> ⚠️ 転倒限界の数値は**概算**である（`a > g·R/(2h)`、ホイール配置半径 R=120mm、
> バッテリ最下部配置を仮定）。`tech.md` 開発標準1 に従い**合否条件には使わない**。
> 実測は `drivetrain-spec.md §11 #12（重心位置）/ #13（実車重量）`。

#### 性能の律速要因（2026-08-30 の実データで見直し）

⚠️ **当初「重量が効くのは転倒のため」と書いたが、実データを入れると結論が変わった。記録として残す。**

ホイール実重量 **80g/個（アルミ合金）= 3輪で240g** が判明し、**車軸高さ 30mm にあるため重心を下げる側に効く。**
これに `bom.md` の実部品を積むと合成重心は **約55mm**（従来の概算80mmより低い）:

| 部位 | 質量 | 高さ | 出典 |
|---|---|---|---|
| ホイール ×3 | 240g | 30mm | **実データ** |
| モータ ×3 | 約600g | 30mm | 推定 |
| バッテリ 3S 1500mAh | 約130g | 20mm | 推定（最下部配置） |
| 造形構造物 | 約400g | 45mm | 推定 |
| 電子部品 | 約150g | 55mm | 推定 |
| ゴミ箱（No.335） | 228g | 182mm | **実データ** |

**3つの上限を並べると順序がはっきりする**（いずれも概算。合否条件にしない）:

| 律速要因 | 上限 | 根拠 |
|---|---|---|
| **駆動力（定格トルク）** | **約 5.4 m/s²** | 2.2 kg·cm ÷ 0.03m = 7.2N/輪。3輪オムニの並進合力は方向によらず `1.5 × F` ≈ 10.8N ÷ 約2.0kg |
| 駆動力（最大トルク） | 約 7.6 m/s² | 3.1 kg·cm 基準。連続使用の前提にしない |
| **摩擦（トラクション）** | **約 2.9〜5.9 m/s²** | `a ≤ μg`。ナイロン／PE ローラー × フローリングで μ≈0.3〜0.6 と仮定 |
| 転倒 | 約 10.8 m/s² | 重心 55mm・R=120mm |

> ⚠️ **転倒は律速していない。** 律速するのは**トラクションと駆動力**であり、
> **`§11 #8（発進時ホイールスリップ）が NFR-1 の主要な調査対象になる**ことを意味する
> （`§12` の性能不足時の調査順序とも整合する）。
> **ゴミ箱を軽くする理由は「総質量が使える加速度をそのまま割る」から**であって、転倒対策ではない。
> ⚠️ アルミホイールの回転慣性による等価質量増は約120g で、影響は小さい。

**受け口の深さは FR-12 に対して両方向に効く**（`catch-mechanism` で机上判断する）:
浅い＝衝突エネルギーが小さいが跳ね返ると脱出しやすい／深い＝衝突エネルギーが大きいが脱出しにくい。
⚠️ `decisions.md` D-9 により `trajectory_sim` は `bounce_out` を**明示的にモデル外**としているため、
**この判断はシミュレータからは出せず、機構側が持つしかない。**

## Overview

**M1「予測の可視化」と、柱1「軌道シミュレータ」を2トラック並行で進める。**

M1 は「飛来するゴミを検出・追跡し、落下地点を予測してプロットする」段階であり、移動体は登場しない。
実機（Raspberry Pi 4 / RealSense D435）が未セットアップのため、ハード待ちが発生する。
その間に着手できるハード不要の作業として、柱1 シミュレータを並行トラックに置く。

両トラックは **`prediction-core`（予測アルゴリズム）を共有する。**
これは `original-features.md` の原則「予測は本番と同一コードを使う。ブラウザ側に複製しない」を
構造として担保するためであり、**この共有こそが2トラックを1つの roadmap に置く理由**である。

**2026-08-23 に第3のトラックとして駆動系（M2a / M2b）を追加した。**
固定側のハード非依存な実装が枯れ、残りが Pi 4 / D435 のセットアップ待ちに一本化されたためである。
駆動系トラックも同じ形の共有を持つ: **`trajectory_sim.drivetrain` の運動モデルと実機の駆動制御は、
`DrivetrainParams`（最高速度・加速度上限・減速度上限）を介して繋がる。**
M2b の実測値をここへ戻すことで、シミュレータのキャッチ可能領域が机上値から実機由来の値へ置き換わる。

## Approach Decision

- **Chosen**: 予測コアを最初に独立して切り出し、そこへ「合成データ（シミュレータ）」と
  「実データ（M1）」の2系統を接続する構成
- **Why**:
  - 予測コアはハード不要で**今すぐ着手できる**唯一の中核部品
  - `development-environment.md §7` の「入力元が live / recorded / simulated のどれでも下流は同じ」を
    最初から満たせる
  - M1 がシミュレータ全体の完成を待たずに済む
- **Rejected alternatives**:
  - **M1 を単一 Spec にする**: OS 選定・カメラ導通・キャリブレーション数学・検出・追跡・
    フィッティング・ロギング・可視化を1本にすると 30 タスク超。
    さらに「予測が外れたとき座標系ずれか検出誤差か予測誤差かを分離できない」という
    `requirements.md §6.2` が警告する事態を、Spec 境界の面でも招く
  - **柱1 を後回しにする**: 実機未セットアップの期間が完全な待ち時間になる。
    また予測コアの設計が M1 側の都合だけで決まり、シミュレータ接続時に作り直しになる
  - **予測コアをシミュレータに内包する**（docs の着手順序どおり）: M1 がシミュレータ完成に依存する。
    共有部品であることが構造に現れない

  - **駆動系トラック: M2a（手動テレオペによるブリングアップ）・M2b（短時間応答の自動計測）、柱4（手動テレオペ）**

## Constraints

- **対象物は空き缶に固定**（φ65mm 程度の剛体）。M1 の実験条件を確定させるための決定
- 実機は**未セットアップ**。OS 選定・USB3 認識・給電安定性から始める必要がある
- 固定側は Python。可視化のみ TypeScript で、**アルゴリズムを持たせない**
- Raspberry Pi 4 の性能達成を断定しない。**設定・ソフトで詰めてからハード変更を検討する**
- 数値は暫定目標値として扱い、**未実測の値を合否条件にしない**
- 移動体は ESP32。**駆動コアはホストで単体テストできる形に保ち、ペリフェラル（PCNT / LEDC / BT）は
  薄いアダプタへ隔離する。** `prediction-core` と同じ「実機なしで検証できる中核」の作り方を踏襲する
- ~~**駆動系の部品は全部は揃っていない**~~ → **2026-08-30 時点で駆動系の部品はすべて揃っている。**
  制約は「部品が無いこと」ではなく **「機体（機構）がまだ存在しないこと」** へ移った。
  ⚠️ **整備スタンドが無いと `drivetrain-spec.md §11 #15〜#18` の台上確認を安全に行えない**ため、
  機構は M2a のクリティカルパス上にある
- **M2a（初通電走行）より前に保護①〜④を実装する**（`drivetrain-spec.md §10`）。
  この順序は安全要件であり、スケジュール都合で入れ替えない

## Boundary Strategy

- **Why this split**:
  - `development-environment.md §12` の段階検証（取得 → 記録 → 検出 → 3D位置 → 追跡 → 予測）が
    そのまま責務の切れ目になっている
  - **キャリブレーションを独立させる**ことが最重要。`requirements.md §6.2` は
    「座標系が数 cm ずれていても症状は『予測が悪い』にしか見えない」と警告している。
    検証ステップを持つ独立 Spec にしないと、M1 の誤差要因を分離できない
  - 検出（`flying-object-tracking`）とキャリブレーション（`world-frame-calibration`）は
    **並行可能**。検出はカメラ座標系まで、World への変換はキャリブレーション側が持つ
- **Shared seams to watch**:
  - **`prediction-core` の入力契約**: `(t, x, y, z)` サンプル列。
    ここに RealSense 固有の型を漏らすと simulated 入力が繋がらなくなる
  - **Throw Record スキーマ**（OQ-31）: `prediction-core` が最小形を定義し、
    `sensing-foundation` の記録形式（OQ-32）と `m1-prediction-validation` の計測が従う。
    **別々に決めない**
  - **構造化ロギングの計測点**: `sensing-foundation` が基盤を作るが、
    段階別レイテンシ（`development-environment.md §13.1`）は各 Spec が自分の区間を計測する
  - **`DrivetrainParams` の意味論**（駆動系トラック）: `trajectory_sim` の
    最高速度・加速度上限・減速度上限・制御周期・指令反映遅れと、`drivetrain-core` が扱う量の
    **単位と定義を揃える**。`m2-motion-validation` が実測値をここへ翻訳して戻すため、
    ずれると**シミュレータの結論が静かに間違う**。
    ⚠️ ただし**コードは共有しない** — シミュレータの質点モデルと実機の逆運動学は別物であり、
    `tech.md` 標準3 が禁じる「本番アルゴリズムの二重実装」には当たらない
  - **ウォッチドッグの入力元**（駆動系トラック）: ④ は「コントローラ固有の処理」ではなく
    **「最後に有効な指令を受けてからの経過時間」だけを見る形**で実装する。
    FR-10 は M3 でこの入力元を差し替えるだけにする。**新規実装にしない**
  - **開口径 → `position_tolerance_mm`**（機構トラック）★: `catch-mechanism` が確定させる受け口の
    開口径は、`許容誤差 = 開口半径 − 対象物半径` として
    `trajectory_sim.CatchCriteria.position_tolerance_mm` の値になる。
    現在の既定値 67.5mm は **φ200mm 開口を仮定した暫定値**であり、
    `src/trajectory_sim/params.py` の docstring 自身が「開口寸法自体がまだ確定していない」と明記している。
    ⚠️ **ここはコードではなく設定ファイルの値で繋ぐ。** `catch-mechanism` は
    `src/trajectory_sim/` のコードに触れない。`DrivetrainParams` と同じ形の還元経路である
  - **CAD 基盤の単独所有**（機構トラック）: build123d による形状の正・寸法パラメータの単一の正・
    A1 mini の造形制約は `catch-mechanism` が単独で所有し、`chassis-mechanism` は消費する。
    ⚠️ **二重に定義しない。** `sensing-foundation` の `geometry.py` と同じ扱いとする
  - **実効ホイール径 → `wheel_diameter_mm`**（機構トラック）★: ホイールは **Nexus 14145 の
    相当品であり純正ではない**（2026-08-30 判明）。`chassis-mechanism` が実測した実効ホイール径は、
    `configs/trajectory_sim/drivetrain-wheel60.json` の `wheel_diameter_mm` と、
    ファーム側のオドメトリ（FR-6）の**両方**へ効く。
    ⚠️ 公称 60mm でも実測 58.5mm なら **2.5% の系統誤差**になり、
    **「予測は合っているのに届かない」という最も切り分けにくい形で現れる。**
    ⚠️ さらに**ハブ穴が丸穴だとイモネジだけでトルクを受けて空転する**が、
    これは**制御側からは検出できない**（エンコーダはモータ軸側で回り続ける）
